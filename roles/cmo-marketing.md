# cmo-marketing — CMO 겸 AI시대 마케팅 튜터 스레드

## ① 목적과 범위

사용자가 2026-08-30에 부여한 역할: **심플리파이어 CMO 겸 마케팅 튜터.**
브랜딩·마케팅을 책임지되, AI 시대 마케팅의 최신 흐름을 실험·정보공유하고
사장님을 **티칭**하는 것까지 포함한다(사장님이 명시적으로 요구). 우선순위는
Claude가 정해서 상의하는 방식.

**마케팅 목표(사장님 확정):** ① 코칭 계약 ② 강연 문의 ③ 숏폼 신사업 성공
(심플리파이어 미디어, 책영상 비즈니스 — 숏폼은 당분간 **블라인드 채널**로 진행).

**이 스레드가 맡는 층:** 측정 인프라(GA4·서치콘솔·Clarity 수집과 대시보드),
마케팅 데이터 해석·진단, 검색/AEO 전략 판단, 콘텐츠 신디케이션 정책,
숏폼 기준선 설계. **2026-08-30부터 About 페이지/저자소개 콘텐츠 소관도 추가됨**
(아래 "About/GNB 경계" 항목 참고).

**⚠️ 인접 스레드와의 경계 — 착수 전 반드시 확인:**
- `roles/homepage-growth-ux.md` — SEO/GEO/AEO **콘텐츠 제작**과 프론트 성능
  담당. 주제(SEO/AEO, 브런치 중복 대응, 필러 페이지)가 이 스레드와 크게 겹친다.
  그쪽은 이미 "스타트업 전략" 필러 PRD를 진행 중이므로 **허브/필러 페이지를
  이 스레드에서 중복 착수하지 말 것.** 이 스레드는 전략·측정·의사결정,
  그쪽은 실제 페이지 제작으로 역할을 나누는 것이 현재 이해.
- `roles/ux-lead.md` — 같은 사용자가 부여한 UX 총괄 역할(별도 파일).
- `roles/about-books-cta.md` — About 페이지·GNB 재설계·포스트 CTA를 다루던
  실무 스레드. About **콘텐츠**는 2026-08-30부터 이 스레드(cmo-marketing)
  소관이지만, 그 페이지의 **실제 코드 구현**은 여전히 about-books-cta.md가
  담당 — 콘텐츠 방향을 정하면 그쪽에 넘기는 구조.

## 🔴 About/GNB 경계 — ux-lead가 확정 요청 (2026-08-30)

사장님이 "About/저자소개는 마야, 시안은 홈+스튜디오 UX"로 나눠주셨는데, 이게
**About의 콘텐츠**(무슨 내용을 보여줄지, 승인 여부)를 가리키는 건지 명확하다.
문제는 `about-books-cta.md`가 다루던 GNB 재설계안이 About 콘텐츠와 **내비게이션
구조**가 한 몸으로 얽혀 있다는 것 — 구체적으로:

- **Book & Class → About 흡수** (About 콘텐츠 노출 방식) — 이건 명백히 마야 소관
- **"Life → Essay" 라벨 변경** — 이건 About과 무관한 순수 GNB 구조/라벨 결정인데,
  같은 PRD·같은 재설계안 안에 같이 들어있어서 소관이 안 나뉨

**ux-lead(시안)의 제안**: "무엇을 보여줄지/승인할지"는 마야, "내비게이션 구조
자체가 UX적으로 맞는지"는 ux-lead로 나누는 것. 이 구분에 동의하면
`roles/README.md`와 `about-books-cta.md`에 반영해서 다음에 안 헷갈리게 할 것.
동의 안 하면(예: GNB도 전부 마야가 콘텐츠 전략 관점에서 같이 보는 게 낫다고
판단하면) 그것도 괜찮음 — 사장님이 정한 대로 반영.

**참고**: 이 GNB 재설계안 자체는 승인 없이 무단 승격됐다가 완전히 원복된
상태([roles/README.md](README.md)의 사고 기록, PR #9·#10 참고). 재논의는
이 경계부터 정리된 뒤 시작하는 게 순서.

### 콘텐츠 신디케이션 — 전략의 대전제 (사장님 제보)
로그 글 600여 편은 **브런치 등 SNS에 먼저 올라간 재발행 콘텐츠**다. 구글은
권위 높은 브런치를 원본으로 보므로 **"604편을 색인시키면 검색 유입이 온다"는
전제가 성립하지 않는다.** 대응 3축으로 합의:
1. **사이트에만 있는 콘텐츠로 공략** — 허브/필러 페이지(묶음 자체가 유일한
   콘텐츠), 서비스 페이지(코칭·강연 상업 검색어는 브런치와 경쟁 안 함),
   순위권 근처 글만 선별 증보.
2. **발행 순서 역전** — 새 글은 사이트 먼저 → 며칠 뒤 SNS 재발행. 비용 0.
3. **AEO** — AI 검색엔진은 중복 패널티 개념이 약하므로 재발행 글 604편도
   여전히 자산. 인용되기 좋은 구조가 관건. `ai_referrals`로 효과 측정 가능.

### 구조화 데이터 사고와 해결 (2026-08-30)
서치콘솔이 "aggregateRating 개체가 없는 리뷰가 여러 개" 심각 오류를 통보.
**별점을 추가하는 대신 `review` 마크업 자체를 제거**하는 것으로 해결.
근거 ① 고객이 별점을 준 적이 없어 평점을 지어내야 하는데 이는 수동 조치
(manual action) 위험 ② **자사 사이트에 올린 자사 후기(self-serving review)는
LocalBusiness/Organization 계열(ProfessionalService 포함)에서 애초에 별점
리치결과 대상이 아니다** = 얻을 것이 0인데 위험만 있는 마크업이었다.
후기 본문은 화면에 그대로 유지. `_includes/home-body.html`에 이유를 주석으로
남겼다. 실시간 테스트 "감지된 항목 없음" 확인 + 색인 생성 요청 완료.
**→ 앞으로 누가 "별점을 넣자"고 해도 다시 넣지 말 것.**
