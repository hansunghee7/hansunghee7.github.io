# ux-lead — Simplifier UX 총괄 스레드 요약

## ① 목적과 범위
공개 홈페이지(simplifier.co.kr)와 관리자 전용 심플리파이어 스튜디오
(`insight-7b3e9f2c/`) **양쪽의 UX 일관성을 회사 목표에 맞게 유지하는 총괄
역할**. 개별 수정 요청을 처리하는 게 아니라, "그 변경이 다른 화면과 전체
일관성에 어떤 영향을 주는지"를 먼저 판단하고 규칙으로 만들어 정본 문서에
남기는 것이 이 스레드의 방식.

정본 문서 두 개가 이 스레드의 산출물이 모이는 곳:
- [docs/UX_GUIDE.md](../docs/UX_GUIDE.md) — 양쪽 화면 공통 정본
- [insight-7b3e9f2c/STYLE_GUIDE.md](../insight-7b3e9f2c/STYLE_GUIDE.md) — 스튜디오 세부 정본

`site-repo-ops`([roles/site-repo-ops.md](site-repo-ops.md))가 저장소 운영·사고
대응이라면, 이 스레드는 **UX 표준 수립**을 맡는다. 그쪽 문서에 나오는 "너비
정책/Studio UX 작업 스레드"가 바로 이 스레드다.

## ② 확정된 주요 결정사항

**너비 정책 (2026-08-30 확정, 이 스레드 최대 산출물)**
- **최상위 원칙: 페이지 컨테이너는 표준형(`--width-content`, 유동 1200px)이 기본.**
  예외는 "그 페이지에서 실제로 폭을 쓰는 콘텐츠가 뭔가"라는 질문 하나로 판정하며
  아래 셋뿐 — 네 번째 숫자를 새로 만들지 않는다.
  1. **혼합형**(표·갤러리와 읽는 텍스트가 공존): 컨테이너는 표준형 그대로,
     러닝 텍스트만 `--width-prose`(720px)로 좁힘. `.doc` 문서 5개, 블로그 글 본문.
  2. **텍스트 전용**(넓게 쓸 콘텐츠가 아예 없음): 컨테이너 자체를 읽기형으로. `ask.html`.
  3. **데이터 전용**(표·스파크라인이 화면을 지배): 컨테이너 자체를 `--width-data`
     (1600px)로. `book-insight.html`이 유일.
- **고정 px가 아니라 유동값**(`min()`/`clamp()`)을 쓴다 — "표준 모니터가 몇 px이냐"는
  논쟁 자체를 없애기 위함. 토큰 정의는 **딱 두 곳**: `insight-7b3e9f2c/studio.css`
  (스튜디오)와 `_includes/width-tokens.html`(홈페이지, Jekyll include).
  **컨테이너급 하드코딩 px는 저장소 전체에 0건** — grep으로 회귀 감시 가능.
- `var(--width-content, 1200px)` 형태로 **폴백을 명시**한다. 배포 직후 HTML은 새 버전인데
  CSS는 브라우저 캐시로 옛 버전인 시차에 변수가 미정의되면 `max-width`가 통째로 무효화돼
  텍스트가 화면 전체로 퍼지는 사고가 실제로 발생했다.
- **`.doc` 문서형 너비 규칙은 `studio.css`에 둔다**(페이지 인라인 아님).
  `shorts-process/playbook/roles/visual-grammar` 4개는 저장소 밖 `shorts-lab`
  파이프라인이 덮어쓰므로 페이지에 쓰면 날아간다. `.wrap:has(> .doc)`(특이도 0,2,0)로
  생성기의 `.wrap{max-width:760px}`(0,1,0)를 **순서와 무관하게** 이기게 해뒀다 —
  옛 규칙을 뒤에 배치한 최악 조건으로 브라우저 검증 완료.
- 컴포넌트 내부 텍스트 블록(히어로 헤드라인 1060px, 인용구 680px 등)과 모달(600·640px)은
  **정책 대상 밖** — 편집 리듬이라 디자이너 재량으로 남긴다.

**스튜디오 사이드바 (2026-08-30)**
- 메뉴를 **사용 목적·빈도 순 4그룹**으로 재편: 인사이트(사이트→검색·UX→SNS→북) →
  제작(글쓰기→멀티 퍼블리싱→숏폼→뉴스레터→필러, 실제 작업 순서) → 대화 → 참조
  (시스템 구조·통합 UX 가이드). 이전엔 만든 순서대로 쌓여 참조 문서가 인사이트
  사이에 끼어 있었다.
- `studio.js`의 `STUDIO_NAV` 배열에 `group` 필드 한 줄만 추가하면 소제목이 자동으로
  붙는다 — 메뉴 추가·이동은 그 배열 한 곳만 고친다.
- 그룹 소제목은 **초록(`--good`)** — 회색은 메뉴 텍스트와 톤이 비슷해 경계가 안 읽혔다.
  새 색을 들이지 않고 기존 팔레트를 재사용.
- **간격 34px를 타이틀 아래와 그룹 사이에 동일 적용** — 값이 제각각이면 눈이 "이 여백은
  무슨 의미지"를 계속 해석해야 한다. 같은 값이면 "큰 여백 = 새 구획" 규칙 하나만 남는다.

**인사이트 카드·그래프 표준 (2026-08-30)**
- 사이트/검색·UX/북/SNS 인사이트가 각자 카드 CSS를 복붙하다 테두리(`--line` vs
  `--line-soft`)·숫자 굵기(500 vs 700)·크기(32 vs 30px)·델타(12 vs 13px)가 어긋나 있었다.
  `.tile`을 **studio.css로 승격**하고 변형 둘을 정의: `.tile-sm`(고밀도 화면 전용,
  북 인사이트), `.tile-accent`(합계·대표 지표). 각 페이지는 고유 요소만 선언한다.
- **그래프는 모양 취향이 아니라 데이터 성격으로 고른다** — 누적 상태의 추이(팔로워·
  판매지수·순위)는 라인 스파크라인, 일별 발생량(방문·노출·클릭)은 막대.

**데이터 기반 의사결정**
- `scripts/fetch_ga4.py`에 **데스크톱 화면 해상도 분포 수집**을 추가하고 사이트 인사이트
  "유입 상세"에 위젯으로 노출 — 폭 정책의 실측 참고선.
- **`0x0`은 집계에서 제외**한다. 첫 실측(2026-08-30)에서 데스크톱 세션 75건 중 17건(23%)이
  `0x0`(헤드리스 브라우저·크롤러가 화면 크기를 보고 못 할 때 GA4가 남기는 값)이었고,
  이걸 분모에 넣으면 "1280px 이상 72%"로 실제보다 낮게 나와 폭 정책을 잘못 판단하게 된다.
  제외 후 **93%** — 유동형 너비 정책이 실측으로도 타당함이 확인됐다. 제외 건수는
  `excluded_invalid_sessions`로 남기고 화면에도 함께 표시해 숫자를 조용히 예쁘게 만들지 않는다.

**작업 관행**
- 스튜디오 작업 후 **`python scripts/check_studio_style.py` 실행은 필수**(FAIL 0건 확인).
  단 문자열 패턴만 보므로 여백 같은 시각 문제는 미리보기 서버로 직접 봐야 한다.
- **GitHub Pages는 CSS를 약 10분 캐시**한다. 배포 직후엔 "서버는 새것, 내 화면은 옛것"
  시차가 늘 생기므로 **확인은 항상 Ctrl+F5**로. 이걸 몰라 "적용이 안 됐다"고 세 번 반복 확인함.

## ③ 진행 중이거나 남아있는 작업
- [ ] **`shorts-lab` 생성기 정리 (선택, 우선순위 낮음)** — `build_docs_pages.py`가 아직
  옛 너비 규칙을 쓴다. 다만 위 `.wrap:has(> .doc)` 특이도 장치로 **화면은 이미 안전**하므로
  급하지 않다. 이 저장소 밖 프로젝트이고 **노트북엔 폴더 자체가 없음**(드라이브 전체 검색으로
  확인) — 본 PC 세션에서만 가능.
- [ ] **GA4 해상도 데이터 축적 관찰** — 90일 창이라 표본이 더 쌓이면 재확인. 지금 표본
  (유효 58건)은 참고선 수준이고, `2560x1440`이 62%로 압도적인데 관리자 본인 방문이
  섞였을 가능성이 있어 해석에 주의.
- [x] **`title=` 죽은 툴팁 4건 — 2026-08-30(클라우드 세션) 판단 완료.**
  `book-insight.html` x2, `pillar-manage.html`은 `.label-text`/`.intro-cell`에
  `overflow:hidden; text-overflow:ellipsis`가 걸려 있고 title 내용이 화면에 이미
  보이는 텍스트와 완전히 같음 — 말줄임 보조용이라 그대로 둠. `write.html`은
  `<iframe title="글쓰기">`로 애초에 이 체크리스트가 말하는 "설명 툴팁"이 아니라
  iframe의 접근성 이름(필수 속성)이라 대상 자체가 아님. **`sns-insight.html`만
  실제 문제**였다 — SNS 바로가기 링크(`<a>↗</a>`)가 아이콘만 있는데 `title`만
  있고 `aria-label`이 없어 스크린리더/터치 사용자에게 유일한 설명 통로가
  불안정했음. `aria-label` 추가로 고쳤고(`title`은 마우스 툴팁용으로 유지),
  `docs/UX_GUIDE.md` 1.4절의 "아이콘 전용 버튼 aria-label 필수" 규칙을
  **아이콘 전용 링크**까지 명시적으로 확장해 정본에 남김. `check_studio_style.py`는
  문자열 패턴만 보므로 여전히 4건을 "확인필요"로 보고하는데, 이는 정상 —
  스크립트가 title= 유무만 잡고 판단은 사람 몫이기 때문. 앞으로 이 4개 파일에서
  같은 title= 보고가 뜨면 재검토할 필요 없이 이 항목을 참고하면 됨(단, 새로운
  title= 추가나 아이콘 전용 링크/버튼이 새로 생기면 그때마다 다시 판정).
