# ux-lead — Simplifier UX 총괄 스레드 요약

## ① 목적과 범위
공개 홈페이지(simplifier.co.kr)와 관리자 전용 심플리파이어 스튜디오
(`insight-7b3e9f2c/`) **양쪽의 UX 일관성을 회사 목표에 맞게 유지하는 총괄
역할**. 개별 수정 요청을 처리하는 게 아니라, "그 변경이 다른 화면과 전체
일관성에 어떤 영향을 주는지"를 먼저 판단하고 규칙으로 만들어 정본 문서에
남기는 것이 이 스레드의 방식.

**2026-08-30 범위 확정(사장님 직접 지시)**: About 페이지/저자소개 콘텐츠는
CMO 마야 스레드로, **이 스레드(튜터명 "시안")는 홈페이지+스튜디오의 UX
전체**를 맡는다. 같은 날 `simplifier-studio.md`가 갖고 있던 **UX/거버넌스
영역**(STYLE_GUIDE.md 정본 관리, ⓘ info-dot 패턴, studio.css/js 공용
인프라, `.doc` 문서형 패턴)도 이 스레드로 흡수됐다 — 두 스레드가 사실상
같은 일(스튜디오 UX 표준)을 각자 이름으로 하고 있었기 때문. `simplifier-studio.md`는
**저장소 위생**(이미지·시크릿·GitHub Actions 감사) 전담으로 범위가 좁혀졌으니,
그쪽 일은 그 파일을 계속 정본으로 본다.

정본 문서 두 개가 이 스레드의 산출물이 모이는 곳:
- [docs/UX_GUIDE.md](../docs/UX_GUIDE.md) — 양쪽 화면 공통 정본
- [insight-7b3e9f2c/STYLE_GUIDE.md](../insight-7b3e9f2c/STYLE_GUIDE.md) — 스튜디오 세부 정본

`site-repo-ops`([roles/site-repo-ops.md](site-repo-ops.md))가 저장소 운영·사고
대응이라면, 이 스레드는 **UX 표준 수립**을 맡는다. 그쪽 문서에 나오는 "너비
정책/Studio UX 작업 스레드"가 바로 이 스레드다.

## ② 확정된 주요 결정사항

**너비 정책 (2026-08-30 확정, 이 스레드 최대 산출물)**
- **최상위 원칙: 페이지 컨테이너는 표준형(`--width-content`, 유동 1200px)이 기본.**
  예외는 "그 페이지에서 실제로 폭을 쓰는 콘텐츠가 뭔가"라는 질문 하나로 판정하며
  아래 셋뿐 — 네 번째 숫자를 새로 만들지 않는다.
  1. **혼합형**(표·갤러리와 읽는 텍스트가 공존): 컨테이너는 표준형 그대로,
     러닝 텍스트만 `--width-prose`(720px)로 좁힘. `.doc` 문서 5개, 블로그 글 본문.
  2. **텍스트 전용**(넓게 쓸 콘텐츠가 아예 없음): 컨테이너 자체를 읽기형으로. `ask.html`.
  3. **데이터 전용**(표·스파크라인이 화면을 지배): 컨테이너 자체를 `--width-data`
     (1600px)로. `book-insight.html`이 유일.
- **고정 px가 아니라 유동값**(`min()`/`clamp()`)을 쓴다 — "표준 모니터가 몇 px이냐"는
  논쟁 자체를 없애기 위함. 토큰 정의는 **딱 두 곳**: `insight-7b3e9f2c/studio.css`
  (스튜디오)와 `_includes/width-tokens.html`(홈페이지, Jekyll include).
  **컨테이너급 하드코딩 px는 저장소 전체에 0건** — grep으로 회귀 감시 가능.
- `var(--width-content, 1200px)` 형태로 **폴백을 명시**한다. 배포 직후 HTML은 새 버전인데
  CSS는 브라우저 캐시로 옛 버전인 시차에 변수가 미정의되면 `max-width`가 통째로 무효화돼
  텍스트가 화면 전체로 퍼지는 사고가 실제로 발생했다.
- **`.doc` 문서형 너비 규칙은 `studio.css`에 둔다**(페이지 인라인 아님).
  `shorts-process/playbook/roles/visual-grammar` 4개는 저장소 밖 `shorts-lab`
  파이프라인이 덮어쓰므로 페이지에 쓰면 날아간다. `.wrap:has(> .doc)`(특이도 0,2,0)로
  생성기의 `.wrap{max-width:760px}`(0,1,0)를 **순서와 무관하게** 이기게 해뒀다 —
  옛 규칙을 뒤에 배치한 최악 조건으로 브라우저 검증 완료.
- 컴포넌트 내부 텍스트 블록(히어로 헤드라인 1060px, 인용구 680px 등)과 모달(600·640px)은
  **정책 대상 밖** — 편집 리듬이라 디자이너 재량으로 남긴다.

**스튜디오 사이드바 (2026-08-30)**
- 메뉴를 **사용 목적·빈도 순 4그룹**으로 재편: 인사이트(사이트→검색·UX→SNS→북) →
  제작(글쓰기→멀티 퍼블리싱→숏폼→뉴스레터→필러, 실제 작업 순서) → 대화 → 참조
  (시스템 구조·통합 UX 가이드). 이전엔 만든 순서대로 쌓여 참조 문서가 인사이트
  사이에 끼어 있었다.
- `studio.js`의 `STUDIO_NAV` 배열에 `group` 필드 한 줄만 추가하면 소제목이 자동으로
  붙는다 — 메뉴 추가·이동은 그 배열 한 곳만 고친다.
- 그룹 소제목은 **초록(`--good`)** — 회색은 메뉴 텍스트와 톤이 비슷해 경계가 안 읽혔다.
  새 색을 들이지 않고 기존 팔레트를 재사용.
- **간격 34px를 타이틀 아래와 그룹 사이에 동일 적용** — 값이 제각각이면 눈이 "이 여백은
  무슨 의미지"를 계속 해석해야 한다. 같은 값이면 "큰 여백 = 새 구획" 규칙 하나만 남는다.

**인사이트 카드·그래프 표준 (2026-08-30)**
- 사이트/검색·UX/북/SNS 인사이트가 각자 카드 CSS를 복붙하다 테두리(`--line` vs
  `--line-soft`)·숫자 굵기(500 vs 700)·크기(32 vs 30px)·델타(12 vs 13px)가 어긋나 있었다.
  `.tile`을 **studio.css로 승격**하고 변형 둘을 정의: `.tile-sm`(고밀도 화면 전용,
  북 인사이트), `.tile-accent`(합계·대표 지표). 각 페이지는 고유 요소만 선언한다.
- **그래프는 모양 취향이 아니라 데이터 성격으로 고른다** — 누적 상태의 추이(팔로워·
  판매지수·순위)는 라인 스파크라인, 일별 발생량(방문·노출·클릭)은 막대.

**데이터 기반 의사결정**
- `scripts/fetch_ga4.py`에 **데스크톱 화면 해상도 분포 수집**을 추가하고 사이트 인사이트
  "유입 상세"에 위젯으로 노출 — 폭 정책의 실측 참고선.
- **`0x0`은 집계에서 제외**한다. 첫 실측(2026-08-30)에서 데스크톱 세션 75건 중 17건(23%)이
  `0x0`(헤드리스 브라우저·크롤러가 화면 크기를 보고 못 할 때 GA4가 남기는 값)이었고,
  이걸 분모에 넣으면 "1280px 이상 72%"로 실제보다 낮게 나와 폭 정책을 잘못 판단하게 된다.
  제외 후 **93%** — 유동형 너비 정책이 실측으로도 타당함이 확인됐다. 제외 건수는
  `excluded_invalid_sessions`로 남기고 화면에도 함께 표시해 숫자를 조용히 예쁘게 만들지 않는다.

**작업 관행**
- 스튜디오 작업 후 **`python scripts/check_studio_style.py` 실행은 필수**(FAIL 0건 확인).
  단 문자열 패턴만 보므로 여백 같은 시각 문제는 미리보기 서버로 직접 봐야 한다.
- **GitHub Pages는 CSS를 약 10분 캐시**한다. 배포 직후엔 "서버는 새것, 내 화면은 옛것"
  시차가 늘 생기므로 **확인은 항상 Ctrl+F5**로. 이걸 몰라 "적용이 안 됐다"고 세 번 반복 확인함.
- **모바일 오버플로 테스트는 반드시 `playwright.devices` 프리셋(isMobile:true)으로
  한다 — 데스크톱 브라우저의 뷰포트 리사이즈는 모바일 에뮬레이션이 아니다.**
  자세한 이유는 아래 "스튜디오 모바일 GNB 진짜 원인" 참고. 이 착각으로 실제
  버그를 "확인했다"고 잘못 보고한 적이 있다(PR #16 → #21).

**스튜디오 모바일 가로 스크롤(깨짐) 수정 — 1차 (2026-08-30, 클라우드 세션)**
- 사장님이 "스튜디오 화면 및 GNB가 모바일에서 깨진다"고 요청, Playwright로
  16개 페이지 전부 375~390px 실측 → **13개 페이지가 실제로 페이지 전체 가로
  스크롤이 생기는 상태**였음을 확인(PR [#16](https://github.com/hansunghee7/hansunghee7.github.io/pull/16)).
- **원인 1 (거의 전 페이지)**: ⓘ 말풍선(`.info-text`)이 `position:absolute` +
  기본 왼쪽 앵커라서, 닫혀 있어도(`visibility:hidden`이지 `display:none`이
  아님) 뷰포트 밖으로 나간 채 `scrollWidth`를 늘리고 있었다. 로드 시점 + resize
  + `MutationObserver` 시점에도 전체 ⓘ를 미리 계산하는 `positionAllInfoDots()`를
  추가해 해결(당시 검증으로는).
- **원인 2 (`.doc` 문서형 페이지)**: 인라인 코드나 공백 없이 붙은 링크가 줄바꿈
  지점이 없어 그대로 넘쳤다. `overflow-wrap:anywhere` 추가.
- 당시 검증: 헤드리스 데스크톱 Chromium의 뷰포트를 390px로 **리사이즈**해서
  `scrollWidth==clientWidth`만 확인 — **이 검증 방법 자체에 결함이 있었다(아래
  "2차" 참고).**

**스튜디오 모바일 GNB 진짜 원인 — 2차, PR #16 검증 방법의 결함 발견 (2026-08-30)**
- 사장님이 **시크릿 모드로도 북 인사이트 햄버거가 화면 밖에 있다**고 재확인해줘서
  PR #16의 검증 자체를 의심 → Playwright의 실제 모바일 기기 에뮬레이션
  (`playwright.devices['Pixel 5']`, `isMobile:true`)으로 재검증(PR
  [#21](https://github.com/hansunghee7/hansunghee7.github.io/pull/21)).
- **진짜 원인**: 실제 모바일 기기는 뷰포트보다 넓은 콘텐츠가 있으면
  `window.innerWidth` 자체가 그 콘텐츠 폭을 따라 늘어난다(레이아웃 뷰포트가
  넓어짐 — 실측: 실제 화면 393px인데 `innerWidth`가 454px로 보고됨). PR #16의
  `positionInfoText()`가 "넘쳤는지" 판정 기준으로 `window.innerWidth`를 썼는데,
  이게 넘친 콘텐츠를 따라 같이 늘어나는 값이라 **판정 자체가 순환 오류**였다 —
  아무리 넘쳐도 "안 넘쳤다"고 판정했다. **데스크톱 Chromium은 뷰포트를
  리사이즈해도 이 현상이 없어서(레이아웃 뷰포트가 고정) PR #16 검증 때는
  전혀 재현이 안 됐다** — "모바일 테스트"라고 생각했지만 실제로는 이 버그
  클래스를 볼 수 없는 방법이었다.
- 이게 ⓘ 말풍선뿐 아니라 **스튜디오 자체 GNB(`#adminShellNav`)까지** 밀어냈다 —
  `position:fixed;left:0;right:0`인 그 nav bar 자체가 늘어난 레이아웃 뷰포트
  폭을 그대로 따라가 393px가 아니라 454px로 렌더링됐고, 그 안에서 오른쪽
  정렬된 햄버거 버튼이 화면 밖(x=408~440, 보이는 화면은 0~393)으로 밀려났다.
- 수정: 판정 기준을 `window.innerWidth` → `document.documentElement.clientWidth`
  (콘텐츠 오버플로와 무관하게 뷰포트 meta 기준 실제 화면 폭 유지)로 교체.
  추가로 `.h2note-text` 보정 로직이 "0px로 리셋 후 재측정"하는 방식이었는데,
  `.h2note-text`의 `transform` transition(.15s)과 경합해서 재계산할 때마다
  전환 중간값을 측정해 보정량이 절반만 적용되는 별개의 버그도 같이 발견 —
  리셋 없이 현재 shift를 대수적으로 역산하는 방식으로 교체, `index.html`의
  `.h2note-text` transition에서도 `transform` 제거(경합 자체를 없앰).
  덤으로 `pillar-manage.html`의 표가 `.tablebox` 패턴 없이 그냥 들어가 있어서
  페이지 전체가 4px씩 밀리던 것도 같이 발견해 감쌌고, `.tablebox`/`table` 공용
  패턴을 studio.css로 승격(index.html·search-insight.html 중복 제거).
- 재검증: 16개 페이지 전부 Pixel 5 에뮬레이션으로 `innerWidth === visualViewport.width`
  확인, 햄버거 전부 화면 안에 위치 확인.
- **디버깅 교훈(갱신)**: 이전 항목의 교훈("overflow-x:auto 컨테이너 안 요소는
  false positive")은 여전히 유효하지만, **그 이전에 애초에 "모바일 뷰포트"를
  제대로 흉내내고 있는지부터 의심해야 한다.** 데스크톱 브라우저 뷰포트 리사이즈
  ≠ 모바일 기기 에뮬레이션. 앞으로 모바일 오버플로/레이아웃 버그는 반드시
  `playwright.devices` 프리셋(`isMobile:true`)으로 검증한다.
