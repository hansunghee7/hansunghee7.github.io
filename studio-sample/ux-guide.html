통합 UX 가이드

2026-08-29 통합 · docs/UX_GUIDE.md 기준

이 저장소는 성격이 다른 두 화면을 동시에 갖고 있습니다 — 고객과 만나는 공개 홈페이지와, 관리자 전용 심플리파이어 스튜디오. "통합"이 색상까지 똑같이 맞춘다는 뜻은 아닙니다. 목적이 다른 화면은 다르게 생기는 게 맞습니다. 대신 (1) 목적과 무관하게 지켜야 할 공통 원칙, (2) 각 화면의 실제 규칙, (3) 의도적 차이와 아직 정리 안 된 차이를 구분해서 기록합니다.

1. 공통 원칙 — 양쪽 다 지킬 것

새 페이지나 컴포넌트를 어느 쪽에 만들든 아래는 지킵니다.

1.1 타이포그래피 페어링: 제목=세리프, 본문/UI=Pretendard

제목류 — 공개 사이트는 'Noto Serif KR'(로그 글 커버) 또는 'Boska','Source Serif 4'(about·book·pillar·home), 스튜디오는 'Noto Serif KR'. 표기는 달라도 "제목은 명조/세리프" 원칙은 동일합니다.
본문/UI — 공개 사이트는 'Noto Sans KR'(글 본문) 또는 'Pretendard Variable'(nav·카드·UI), 스튜디오는 전부 'Pretendard Variable'. 새 화면을 만들 때도 이 조합을 유지하고, 완전히 다른 서체군(고딕 단독, 손글씨체)을 새로 들이지 않습니다.

1.2 점진적 정보 노출 (Progressive disclosure)

핵심 정보는 항상 보이게, 부가 설명·재고성 정보는 숨겨뒀다 필요할 때만 보여줍니다. 구현 방식은 화면마다 다르고 다르게 두는 것이 맞습니다: 공개 사이트는 <details>/<summary>(필러 페이지 "더보기", book.html 목차, 모바일 GNB 아코디언 — 검색엔진 크롤러는 닫혀 있어도 읽습니다), 스튜디오는 ⓘ info-dot 버튼(hover/탭 토글). 메커니즘은 다르지만 배치 원칙은 공통입니다 — 그 정보가 설명하는 대상 바로 옆/아래에 둔다, 링크 끝이나 화면 구석으로 밀어두지 않습니다.

1.3 고정 테마 — 사용자 다크모드 대응 없음

두 화면 다 prefers-color-scheme을 쓰지 않습니다. 대신 페이지 유형별로 테마를 고정합니다(공개: 대부분 다크 #080808+#f5f3ee, book.html만 예외적으로 라이트 크림 톤 / 스튜디오: 전체 라이트 고정). 도입하려면 두 화면 전체에 영향을 주는 별도 논의가 필요합니다.

1.4 접근성 기본선

장식용 이미지(연관글 썸네일 등)는 alt="", 의미 있는 이미지는 실제 설명 텍스트 — 빈 값도 아니고 원본 CDN URL 토큰이나 파일명을 그대로 넣는 것도 안 됩니다(2026-08-29 블로그 본문 3개 글에서 실제로 발견해 수정한 사고 — 아래 6장 참고). 아이콘 전용 버튼(닫기, 이전/다음, 메뉴 열기, ⓘ 등)에는 aria-label 필수입니다.

1.5 브랜드 표기

로고·타이틀·메타데이터는 영문 "Simplifier", 본문 서술은 한글 "심플리파이어". 대표 개인명은 한글 본문 "한성희", 영문/저자 표기 "Han Sunghee"로 통일합니다.

로고 이미지는 배경에 맞는 버전을 씁니다 — 다크 배경엔 log_assets/images/logo_white.png, 라이트 배경엔 검정 로고(logo_black.png). 문서·브리핑형 페이지의 로고 배치는 헤더(제목 줄) 우측 끝 — 제목과 같은 행에 두고 날짜·메타 텍스트는 아래 행으로 분리합니다. 메타와 한 줄에 섞으면 화면 폭에 따라 로고가 애매한 위치로 밀립니다(2026-08-30 모닝 브리핑 미리보기에서 실제 발생해 수정). 로고엔 alt="Simplifier" 필수. 공개 사이트 GNB 로고는 좌측(홈 링크 관례)이라 이 규칙과 다른 게 맞습니다 — 문서형에만 적용.

1.6 노출 범위를 먼저 정하고 시작한다

새 페이지를 만들기 전에 "고객이 검색해서 찾아와야 하는가, 관리자만 봐야 하는가"부터 정합니다. 공개 성격이면 sitemap.xml 포함·JSON-LD/OG 메타 채움·검색엔진 노출 극대화가 원칙, 관리자 전용이면 noindex,nofollow,noarchive + no-referrer + 공개 nav 노출 금지 + 주소 자체를 유일한 자물쇠로 씁니다(스튜디오가 지금 이 방식).

2. 공개 홈페이지 — 실제 규칙

공개 사이트엔 공유 :root 디자인 토큰 파일이 없습니다 — 스타일은 각 레이아웃/include의 인라인 <style>에 있고, 레이아웃마다 거의 독립된 팔레트·타이포 세트를 씁니다. 아래는 두 파트로 나눠 정리했습니다: 2.1 홈페이지(index.html/home-body.html, 오늘 실측한 상세값 + 미리보기)와 2.2 그 외 레이아웃(블로그 글·필러·book.html 등, 코드에서 확인한 값 요약).

홈페이지는 딥블랙 배경 위에 크림 텍스트를 쓰는 다크 톤 하나로 통일돼 있습니다(예외는 아래 2.2의 book.html — 유일하게 밝은 크림 톤).

실제로 있었던 사고 — Fontshare에서 Boska를 로드할 때 이탤릭 스타일을 따로 요청하지 않으면(font-style:italic을 줘도) 업라이트로 렌더링됩니다. 이탤릭이 필요하면 요청 weight를 기본weight + 1로 걸어야 합니다(200→201, 300→301, 400→401 — Fontshare 자체 규칙). 히어로 강조 텍스트가 기울어지지 않고 그대로 나온 실제 버그였습니다(2026-08-26).

스타트업 인사이트 완결

홈페이지 새 페이지·섹션을 만들 때 체크리스트

  1. 색은 위 팔레트에서만 고른다 — 새 hex 값을 추가하지 않는다.
  2. 헤드라인은 Boska, 서술형 문장은 세리프, 태그·라벨·버튼 같은 기능적 UI 텍스트는 Pretendard.
  3. Boska를 이탤릭으로 쓰면 weight+1 로드를 잊지 않는다.
  4. 섹션 간격은 130 / 96 / 72px 리듬, 좌우 거터는 32 / 16px.
  5. index.html처럼 스테이징과 짝을 이루는 페이지는 반드시 공유 include로 뽑는다(_includes/home-body.html 사례). 반대로 about·speaking처럼 짝이 없는 단독 layout: null 페이지는 톤(색·폰트)만 같으면 충분하고, 값 자체를 억지로 공통 파일로 뽑지 않는다 — 실제로 비교해보면 페이지마다 여백·크기가 의도적으로 다르게 튜닝돼 있어서, 억지로 합치면 불필요한 추상화만 늘어난다.
  6. 새 시각 컴포넌트를 만들기 전에 위 컴포넌트 목록에 재사용할 게 있는지 먼저 확인한다.

레이아웃 구조: default.html의 .cover-wrap은 index-mode(22vh 배너)와 post-mode(100vh sticky 히어로) 두 모드로 분기. GNB는 글 페이지 전용 .log-nav(68px, 그라데이션 스크림)와 홈/목록 전용 header.html(sticky, 드롭다운) 두 종류. 브레이크포인트: 1024px(카드 3열) → 860px(nav 버거 전환) → 768px(카드 2열) → 700/760px(패딩 축소) → 600/560/480px(카드 1열, 모바일 세부조정).

공통 컴포넌트: header.html(데스크톱 드롭다운 GNB + 모바일 <details> 아코디언, "Contact" pill), contact_modal.html(다크 모달, 문의유형 3버튼 + Formspree 연동, GA4/Clarity 이벤트 트래킹 내장), post_cta.html/post_nav.html/related_posts.html(글 하단 카테고리별 CTA·이전/다음글·연관글 카드), .card-item/.card-grid(로그 목록·pillar 공용 카드, 4→3→2→1열 반응형).

정보 노출 패턴: ⓘ 버튼은 없음(전체 0건) — 대신 <details> 접기/펼치기, 완결 시리즈는 .cat-done pill 배지, 이미지 로딩 중엔 shimmer 스켈레톤. 내비게이션 구조: GNB 카테고리 — Startup(스타트업 인사이트 / 대한민국 스타트업 미국진출을 묻다·완결 / 코치S·완결) · FieldPlay(기획일상, UX의 언어들, Be the PO / 기획자의 프레임웍·PO의 프레임웍·AI의 언어들·잉크드인대 기획학과·완결) · Life(심플리파이어 라이프, 토크세션) · About(소개, 책 2종, 외부 클래스 링크). 각 카테고리는 _data/pillars.yml 기반 필러 허브로 연결됩니다.

3. 심플리파이어 스튜디오 — 요약

세부 규칙의 정본은 insight-7b3e9f2c/STYLE_GUIDE.md입니다. 새 스튜디오 페이지를 만들거나 고칠 땐 그 문서를 먼저 읽으세요 — 여기는 공개 사이트와 대조하기 위한 요약만 남깁니다.

공유 studio.css/studio.js 한 쌍으로 디자인 토큰·nav·ⓘ 버튼·새로고침 버튼 동작을 전부 통일합니다(공개 사이트와 가장 크게 다른 지점 — 공개 사이트는 레이아웃마다 스타일이 따로 있는 반면 스튜디오는 파일 하나만 고치면 전체에 반영됩니다). 라이트 고정 테마이고, python scripts/check_studio_style.py로 구조적 규칙 위반을 기계적으로 점검합니다.

스튜디오 안에도 화면 밀도가 다른 두 하위 패턴이 있습니다. 같은 studio.css/js를 쓰지만 목적이 달라 레이아웃 폭과 정보 밀도가 다르게 보입니다 — 지금 이 페이지가 "사이트 인사이트"나 "시스템 구조"와 다르게 생긴 이유가 바로 이겁니다. 버그가 아니라 이 두 번째 패턴입니다.

대시보드형 — 사이트 인사이트, SNS/북 인사이트, 시스템 구조, 필러 관리 등. .wrap 1100~1600px, 표·타일·스파크라인으로 데이터 밀도 우선.
문서형(.doc 패턴) — 이 페이지(통합 UX 가이드), 숏폼 공정 정본·연출 사전·제작진 역할·파일럿 매뉴얼. .wrap 760px로 좁혀 가독성 우선, 문서 원문을 그대로 렌더.

두 번째 패턴의 구현 규칙(마크다운 렌더 방식, 상대링크 재작성, H1 중복 방지 등)은 STYLE_GUIDE.md의 ".doc 패턴" 절이 정본입니다.

4. 의도적 차이 vs 아직 정리 안 된 차이

의도적 차이 (그대로 둘 것)

색상 팔레트 — 공개 사이트는 브랜드 감성(다크+웜톤 오프화이트, book만 크림 라이트), 스튜디오는 기능적 라이트(데이터 가독성 우선). 목적이 다른 화면이라 억지로 하나로 맞추지 않습니다.
정보 노출 메커니즘 — 공개는 <details>(SEO 친화적), 스튜디오는 ⓘ 버튼(비공개 도구라 SEO 고려 불필요).
노출 정책 — 공개는 검색엔진에 최대한 노출, 스튜디오는 검색엔진에서 완전히 숨김.

아직 정리 안 된 차이 (의도했다기보다 그때그때 만들다 보니 이렇게 됨)

스튜디오는 공유 CSS 파일(studio.css) 하나로 통합돼 있는데, 공개 사이트는 레이아웃마다(default/pillar/book/home-body) 인라인 <style>이 따로 있고 공유 :root 토큰 파일이 없습니다. 색상 하나를 바꾸려면 여러 파일을 각각 찾아 고쳐야 합니다.

5. 정리 후보

지금 당장 바꾸자는 제안이 아니라, 나중에 필요해지면 참고할 수 있도록 남겨두는 기록입니다.

  • 공개 사이트 공유 디자인 토큰 파일화 — _includes/design-tokens.html 같은 걸 만들어 다크 팔레트와 book.html의 크림 팔레트를 변수로 뽑아 각 레이아웃이 include 해서 쓰게 하면, 스튜디오처럼 한 곳만 고쳐도 전체에 반영됩니다. 다만 Jekyll {% include %}로 CSS 변수를 주입하는 방식과 캐싱/빌드 영향을 먼저 검토해야 합니다 — 결정하지 않고 후보로만 남깁니다.
  • 공개 사이트에도 ⓘ 패턴이 필요한 지점이 있는지 점검 — book.html의 긴 설명이나 pillar 페이지의 통계 수치처럼 <details>로 펼치기엔 과하고 짧은 보조 설명이면 충분한 자리가 있는지. 현재는 필요성이 확인된 사례가 없어 미룹니다.

6. 실제로 있었던 사고 (재발 방지용 기록)

Boska 이탤릭 업라이트 렌더링 — 2장 타이포그래피 항목 참고. Fontshare weight+1을 안 걸면 기울어지지 않습니다.
카드 태그가 세로로 찌그러짐 — 카테고리 태그를 flex 컨테이너 안에 넣으면서 flex-shrink:0과 white-space:nowrap을 안 줬더니, 옆의 다른 요소에 밀려 태그 폭이 26px까지 줄어들고 글자가 세로로 줄바꿈됐습니다. flex 안에 텍스트 라벨을 넣을 땐 항상 이 두 속성을 같이 준다(2026-08-29).
모달 트리거가 모달 앞에 떠 보임 — <details>를 CSS 모달로 쓸 때, 열려 있는 동안 summary의 z-index가 backdrop/모달카드보다 높으면 트리거 버튼이 모달 위에 떠 보입니다. 열려 있는 동안 summary는 backdrop에 자연스럽게 가려지게 두고, 닫기는 모달 안의 별도 버튼/Esc가 담당하게 한다(2026-08-29).
이미지 alt에 깨진 URL 토큰 — 블로그 본문 이미지를 로컬라이즈하는 과정에서 alt 텍스트에 원본 CDN URL 토큰이 그대로 남은 글이 3개 발견됐습니다. 이미지 처리 스크립트를 만들거나 고칠 때 alt 필드를 반드시 사람이 읽을 설명으로 채워야 합니다(2026-08-29).
