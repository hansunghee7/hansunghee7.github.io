스레드 작업 규약

정본은 CLAUDE.md — 스레드 생애주기와 관련된 절만 뽑아 정리한 빠른 참고용입니다. CLAUDE.md 해당 절이 바뀌면 이 페이지도 함께 고치세요.

이 저장소는 여러 기기(PC·노트북)와 여러 대화창에서 클로드 코드 세션("스레드")이 동시에 작업합니다. 각 스레드는 시작(하이)·작업 중(진행)· 마무리(바이) 세 시점마다 아래를 확인합니다. 세부 근거·예외 조항은 전부 CLAUDE.md에 있습니다 — 여기는 그걸 생애주기 순서로 재배열한 요약입니다.

하이세션을 시작할 때

  • git fetch origin --prune로 원격 상태부터 확인. 브랜치를 여러 개 나열해서 git fetch origin <A> <B> 식으로 받지 않기 — 그중 하나라도 원격에 없으면 전체가 조용히 실패한다.
  • 로컬이 origin/main보다 뒤처져 있으면 git pull --ff-only origin main으로 먼저 따라잡은 뒤에 새 작업을 시작한다(다른 기기·다른 스레드가 먼저 병합했을 수 있음).
  • project memory·CLAUDE.md를 훑어 진행 중이던 맥락(누가 뭘 하고 있었는지)을 파악한다.

진행작업 중 지킬 것

  • 본인 작업 브랜치에만 커밋·push한다(예: claude/..., feat/...). main에 직접 push하지 않는다 — 룰셋이 필수 검사 (build-check)를 요구해서 어차피 거절된다.
  • 스레드가 여러 개 동시에 돌 때는 가급적 스레드마다 영역을 나눈다 (예: Studio / 블로그 콘텐츠 / 인프라). 같은 파일을 두 스레드가 고치면 PR이 있어도 충돌 해소는 사람 몫이다.
  • 되돌리기 어려운 액션(강제 push, 브랜치 삭제, 파일 대량 삭제 등)은 사장님 확인 없이 진행하지 않는다.

바이세션을 마무리할 때

  • 작업이 끝나면 PR을 열고 auto-merge(squash 또는 merge)를 켠다 — build-check가 통과하면 GitHub이 알아서 병합한다. 통과 못 하면 병합이 안 되니 실패 원인을 고쳐 다시 push한다.
  • 병합된 브랜치는 삭제해서 목록을 깨끗하게 유지한다.
  • 인프라를 바꿨다면(워크플로 추가·삭제, 외부 서비스 연동·해지, 자동화 Routine 등) 같은 세션에서 시스템 구조 페이지도 함께 갱신한다 — 스냅샷 문서는 낡는 순간 신뢰를 잃는다.

예외

사장님 본인의 직접 커밋(CMS 글 발행, SNS 크롬 확장)과 자동화 워크플로 (github-actions)의 커밋은 PR 없이 main에 들어간다 — 콘텐츠/데이터 커밋이라 의도된 예외다.
