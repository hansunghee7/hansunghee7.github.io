씬을 "어떻게 역동적으로, 정보 있게" 만들지의 정본은 VISUAL_GRAMMAR.md(연출 사전) — 씬 플랜 작성·검증 시 항상 같이 참조. 공정을 "누가·어떤 관점에서" 수행할지의 정본은 PRODUCTION_ROLES.md(제작진 역할 문서) — 게이트별 참여 역할과 결정 방식. "지금 뭘 해야 하지?"는 이 세 문서가 아니라 PILOT_PLAYBOOK.md를 본다 — 이 문서들은 Claude가 내부적으로 참조하는 엔진 설계도, PILOT_PLAYBOOK.md는 사용자가 실제로 반복하는 7단계 루프 실행 매뉴얼.

미션

벤치마크 채널을 흉내 내는 게 아니라, 왜 그 포맷이 작동하는지 원리부터 검증하고 가장 효과적인 AI 숏폼 생성 공정을 처음부터 만든다. 제로투원 접근 — 대본 구조, 음성, 비주얼, 합성 각 단계를 근본부터 검증하고, 검증된 것만 공정에 편입한다.

운영 원칙

  1. 외부 정보·비판은 수용도 무시도 하지 않는다. 다른 AI/커뮤니티/기사의 주장은 항상 독립 검증(검색·계산·실제 테스트) 후 채택을 결정한다. 근거 없는 확신에 흔들리지 않되, 알맹이가 있으면 프레이밍이 과장됐어도 반영한다.
  2. 유료보다 무료·저비용 경로를 먼저 검증한다. 안 될 때만 유료로 넘어가고, 판단 근거를 결정 로그에 남긴다.
  3. 모든 주요 결정과 이유를 결정 로그에 기록한다.
  4. 이 문서는 매 세션 최신 상태로 갱신한다.

설계 의도: 콘텐츠(channels/)와 공정(pipeline/)의 분리. 공정 개선은 전 에피소드에 즉시 적용되고, 에피소드 데이터는 공정이 바뀌어도 그대로 재사용된다(캐시 재사용으로 재실행 비용 최소화). episode.json이 각 에피소드의 단일 진실 소스 — 코드가 이 매니페스트만 읽으므로 폴더 구조가 코드에 하드코딩되지 않는다.

공정 흐름 (게이트 + 배치 원칙)

G0 소재 → G1 대본 → G2 음성 → G3 정렬 → G4 씬 → G5 합성 → G6 발행
  • 게이트별 통과 조건은 templates/episode/CHECKLIST.md (에피소드마다 복사됨).
  • 배치 원칙: 규모가 생기면 에피소드 단위가 아니라 공정 단위로 묶어서 처리한다 — 소재 10개 검증 → 대본 10개 → 음성 10개 몰아 녹음 → … 같은 작업의 컨텍스트 전환 비용이 사라지는 것이 물량 공정의 핵심 (업계 배치 워크플로우 관행과 일치).

스튜디오 현황판: 모든 episode.json을 스캔해 채널별 에피소드와 7게이트 진행 상태를 한 페이지로 렌더링. 두 가지 출력 — ① 아티팩트(studio.html), ② 심플리파이어 스튜디오 메뉴(simplifier.co.kr/insight-7b3e9f2c/shorts-studio.html, 사이트의 다른 스튜디오 페이지들과 같은 디자인). 관리 데이터는 매니페스트가 유일한 원본이고 현황판은 뷰일 뿐 — 별도 상태를 갖지 않아 어긋날 수 없다.

오디오 처리 방침

  • Veo 3.1은 영상 생성 시 오디오(48kHz, 대사·환경음·효과음)를 함께 만든다. 프롬프트에 오디오 지시가 없으면 무엇이 나올지 통제 불가.
  • 모든 씬 프롬프트에 환경음/효과음 명시 + "No dialogue, no voice, no music" 고정 문구 필수 — 우리는 별도 녹음한 한국어 나레이션을 쓰므로, Veo가 자체적으로 대사/음성을 넣으면 충돌한다.
  • 클립의 생성 오디오는 나레이션보다 훨씬 작은 볼륨으로 배경에 믹스한다 (합성 파이프라인 TODO — 클립 수신 후 구현).

자막(캡션) 스펙 — 확정 (실측 데이터 + 화면 재확인 기반)

레퍼런스 숏츠 실제 SRT 자막(DownSub 추출, 98개 큐) 통계 + 모바일 뷰포트로 화면 재검증. 인포그래픽 라벨과는 별개 레이어. - 위치: 화면 세로 기준 약 65~70% 지점(중하단, 하단에 가까움). 주의: 데스크톱 브라우저 패널이 낮으면 세로 영상 하단이 잘려서 안 보일 수 있고, 그 상태에서 유튜브 자체 CC UI(페이지 상단, 영상 프레임 바깥)를 실제 자막으로 착각하기 쉽다 — 반드시 모바일 뷰포트(resize_window preset mobile)나 전체화면으로 세로 프레임 전체를 확인할 것. - 스타일: 흰색 굵은 글씨 + 그림자/외곽선(경우에 따라 반투명 검은 배경도 관찰됨) - 큐 길이: 평균 1.86초, 전부 3초 미만(1.2~2.76초 범위) — 문장이 안 끝나도 시간 되면 무조건 다음 캡션으로 전환 - 캡션당 글자 수: 평균 14.4자(공백 제외), 4~17자 범위 — 한국어 약 5~7어절 - 캡션 사이 간격: 0초 — 끊김없이 바로 다음 캡션으로 이어짐(97/97 = 100%) - 표시 속도: 초당 약 7.9자(여유있게 읽히는 속도, 지나치게 빠르지 않음) - 청크 단위: 문장 전체가 아니라 위 수치(14자/1.86초) 기준으로 자름 — Whisper 단어별 타임스탬프(align_and_build.py에서 이미 확보)를 시간·글자 수 기준으로 묶어 구간 생성 - 구현 시점: 클립 합성(오디오+영상 결합) 단계, 씬 생성 프롬프트에는 영향 없음(화면 내 텍스트 생성 금지 원칙 유지) - 레퍼런스 자막 사용 원칙: 추출한 자막은 구조 분석(길이·타이밍·패턴)에만 쓰고, 문장 자체를 우리 대본에 그대로 옮기거나 짜깁기하지 않는다.

인포그래픽 씬별 적용 — ep01 완료 (19/45 씬)

scene_plan.json 각 씬에 overlay 필드(type/text/note) 추가, 씬 플랜 페이지에 빨간 칩으로 표시. 밀도는 레퍼런스처럼 매 씬이 아니라 용어 등장·강조 비트에만(19/45 ≈ 42%). ep01은 point_tag·hero_text 위주(EPS·TPS·기계실 등 용어, "콘크리트 무덤"·"심장" 등 강조구), dimension_label은 킬러 넘버 부재로 1곳(B1~옥상)만. 프롬프트(Veo 전달용)에는 넣지 않음 — 화면 내 텍스트 생성 금지 원칙 유지, 합성 단계 후반 작업 가이드로만 사용.

영상 생성: 초 단위 정확도 리서치 결론

Veo/Kling/Runway/Pika/Luma API 전수 조사 — 임의의 정확한 초 단위 생성을 지원하는 모델은 현재 없음(전부 4/6/8/10초 등 고정 프리셋, API도 "목표치일 뿐 보장 아님"). 유료/API 여부와 무관한 업계 공통 한계로 확정. 대응: 실사용 길이보다 크거나 같은 최소 프리셋으로 요청, 결과 길이 무관하게 합성 단계에서 클립 0초부터 실사용 길이만큼 ffmpeg로 자르는 것으로 자동화 원칙 확정(배속·구간판단 없음). Veo Fast(8초 고정)·Omni 1.1 Flash(모션 부족) 기각 후 Lite/Quality 테스트 예정.

인포그래픽 스펙 — 3종 (재분석 기반, 후반 합성 대상)

  • 치수/측정 라벨: 빨간 화살표·선 + 빨간 굵은 숫자+단위(예: "10m"). 고정 위치가 아니라 실제로 측정하는 대상 옆에 동적으로 붙는다(카메라가 움직이면 라벨도 그 위치를 따라감).
  • 포인트 태그: 빨간 알약형 배지 + 지시선으로 특정 구조물/장소 이름을 짚어준다.
  • 히어로 텍스트: 흰색 대형 입체 글자가 장면 안에 실제로 서 있는 것처럼 렌더링(연도·핵심 키워드 하나). 일반 대사 자막 자리를 대체하는 강조 비트로 보임.
  • 화면의 역동성 일부는 이 인포그래픽 요소들이 등장하는 애니메이션(팝인·확대·그려짐) 자체에서도 나온다 — 컷 밀도·장면 내 액션에 이은 세 번째 요인.
  • ep01은 킬러 넘버가 없어 치수/측정 라벨 활용도가 낮음 — EPS/TPS 같은 용어는 포인트 태그로, 차기 에피소드는 G0 게이트에서 확보한 스케일 숫자를 치수 라벨로 적극 활용.

씬 프롬프트 합격 조건 (G4 게이트 — 생성 전 필수 통과)

시행착오를 줄이기 위해, 크레딧을 써서 실제로 생성해보기 전에 아래 조건을 전수 점검한다. 기계적으로 검증 가능한 항목은 pipeline/validate_scene_plan.py가 자동 검사하고(사람이 놓치기 쉬운 반복 패턴을 100% 잡아냄), 논리적 일관성은 사람(또는 나)이 최종 판단한다. 이 리스트 자체가 지금까지의 모든 실측·리서치·실패 사례(Omni 모션 부족, 다중 컷 불안정, 부정어 프롬프트 부작용 등)를 조건으로 압축한 것.

A. 카메라 - A1. camera가 언급되면 근처에 명확한 동작 동사(push-in/orbit/rise/pan/swoop/pull back 등)가 있다. - A2. 카메라가 "도착 후 정지"로만 끝나지 않는다 — 정지로 끝나려면 반드시 장면 내 지속 액션이 동반된다. - A3. 카메라 근처에 slow/calm/quiet류 속도-완화 수식어가 없다(smooth=흔들림 없음은 허용).

B. 장면 내 콘텐츠 액션 - B1. 화면 묘사부에 -ing형 지속 동작 동사가 최소 1개 있다(정적 명사 나열 금지). - B2. 그 액션 동사 근처에 soft/gently/quiet/calm/faint/muted류 수식어가 없다(단, 스타일 선언절의 "soft archviz style"은 스타일 모드명이라 예외). - B3. 액션이 한 번(one-shot)으로 끝나지 않고 지속/반복임을 나타내는 단어(steadily/continuously/rapidly/in sequence 등)가 있다.

C. 길이·컷 규칙 - C1. veo_duration이 4 또는 6(허용 프리셋)이다. - C2. 1프롬프트 = 1컷 — "cut to" 같은 다중 컷 지시가 없다(cutaway/cross-section 같은 스타일어는 예외). - C3. 실사용 길이(end-start)가 veo_duration 이하이고, 5.5초를 넘지 않는다.

D. 부정어·화면 텍스트 - D1. 고정 문구("No dialogue, no voice, no music.") 외에 "no X" 형태의 화면 콘텐츠 부정 표현이 없다. - D2. text/number/label/sign이 언급된다면 "blank/unmarked" 등 화면 내 텍스트 생성 금지 원칙에 맞게 서술됐다.

E. 스타일 키워드 배치 - E1. 프롬프트가 "Clean 3D architectural..." 또는 "Monochrome white clay..."로 시작한다(모델이 앞부분에 가중치를 두는 특성 활용).

F. 사운드 - F1. "Ambient sound:" 절이 있다. - F2. "No dialogue, no voice, no music." 고정 문구가 있다. - F3. (사운드 절 안에서는 soft/quiet/faint 허용 — 나레이션을 방해하지 않는 배경음이 목적이므로 시각적 역동성 규칙과 무관.)

G. 오버레이 논리 일관성 (사람 판단) - G1. overlay가 있으면 text/note가 프롬프트 속 시공간과 실제로 맞는다(예: 카메라가 도달하지 않은 곳을 표시하지 않음 — 씬33/34에서 실제로 걸린 문제). - G2. overlay 밀도가 적절하다 — 매 씬이 아니라 용어 등장·강조 비트에만.

H. 레퍼런스 대조 - H1. 컷 길이가 레퍼런스 실측(2~3초/컷) 대비 크게 벗어나지 않는다(우리 목표 3~5초대). - H2. 기각된 스타일(실사/2D 블루프린트/UE5 네온 등) 키워드가 재등장하지 않는다.

실행: python pipeline/validate_scene_plan.py channels/<channel>/episodes/<ep> — A3/B2/C1-C3/D1/E1/F1-F2를 자동 검사해 04-scenes/validation_report.txt에 위반 씬만 기록(재생성 가능한 산출물이라 git 추적 제외). A1/A2/B1/B3는 휴리스틱으로 후보만 표시. G/H는 스크립트가 못 잡으므로 생성 전 마지막에 사람이 훑는다.

검증된 기술적 제약 (재사용할 것)

  • Veo 3.1은 1회 생성당 최대 8초 (4/6/8초 프리셋만). 씬 실사용 길이는 항상 8초 이하로 설계.
  • 1프롬프트 = 1컷. "세 개의 빠른 컷" 같은 다중 컷 지시는 불안정 — 씬을 분리한다.
  • 부정어 프롬프트("no legible text") 금지 — 모델이 언급된 개념에 주의를 기울여 역효과. 긍정 서술("blank placard")로 대체.
  • 화면 내 텍스트/숫자는 영상 생성에 요청하지 않는다 — AI 영상의 텍스트 렌더링은 신뢰 불가. 라벨·숫자·인포그래픽은 후반 합성으로.
  • Whisper word-timestamp는 실제 발화 끝보다 일찍 찍힌다 — 전역 +0.35초 보정.
  • 전역 배율 정렬은 오차가 누적된다 — difflib 문자 단위 로컬 정렬 사용 (일치율 95%+ 확인).
  • TTS/녹음 음성은 문장별 음량 편차가 있다 — dynaudnorm+loudnorm 정규화 필수.
