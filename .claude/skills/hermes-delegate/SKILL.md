# Hermes 위임 우선 규칙 <!-- id: b7f1 -->

Claude Code는 로컬 실행 작업을 직접 수행하기 전에 Hermes 위임 가능 여부를
먼저 판단합니다. 다음 중 하나라도 해당하면 Hermes 위임을 우선합니다.

- 실제 셸/파일시스템이 필요한 작업
- Docker/CLI/로컬 서비스 실행이 필요한 작업
- GPU/ComfyUI/FFmpeg 등 실제 하드웨어가 필요한 작업
- SSH/원격 PC에서 실행해야 하는 작업
- curl/API smoke test 등 실제 네트워크 검증
- 빌드/테스트/배포
- 로그 확인 및 실패 원인 조사
- 동일 작업의 재시도 가능성이 높은 경우
- 장시간 실행이 필요한 작업
- 사용자가 직접 여러 명령을 반복 입력해야 하는 작업

Hermes가 실행 가능한 환경을 가지고 있고 보안상 허용되는 작업이라면, Claude
Code가 직접 실행하거나 사용자가 명령을 복사해 실행하도록 요구하기보다
Hermes에게 위임합니다. Hermes 위임 후에는 결과를 받아 다음 작업을 판단합니다.

**Hermes에게 위임하지 않는 주요 작업**:
- 계정 생성/최초 인증
- 결제 승인
- 비밀값의 직접 입력 또는 전달
- 관리자 권한이 필요한 보안 변경
- 되돌릴 수 없는 파괴적 변경
- 제품/아키텍처의 최종 의사결정

단, 안전하고 되돌릴 수 있는 작업은 Hermes가 자율적으로 실행하고, 실패하면
로그를 확인하여 원인을 진단하고 최대 3회까지 재시도합니다.

**역할 분리**: 클로드 코드(THINK·DESIGN·CODE·DECIDE·ORCHESTRATE) →
헤르메스(EXECUTE·OBSERVE·VERIFY·RETRY) → 클로드 코드(JUDGE·DECIDE·REPORT) →
사장님(APPROVE·제품/비가역 결정). 클로드 코드가 직접 실행할 수 있다는
이유만으로 이 위임을 건너뛰지 않습니다.

**결과 보고 형식**: 위 DONE=VERIFIED 원칙(§f3a9)을 헤르메스 실행에도 그대로
적용하기 위해, 결과는 가능하면 TASK/EXECUTION/OBSERVATION/VERIFICATION/
EVIDENCE/FAILURE-RECOVERY/STATUS 순서로 받습니다. 이미 이 정보가 자연스럽게
다 나오면 형식을 억지로 강제하지 않습니다. 목적은 "완료했다"는 말이 아니라
증거로 STATUS(DONE/VERIFIED 또는 실패)를 판단하는 것입니다.

근거: 2026-09-10 새김 MCP를 상시 서버(구형 PC)에서 Cloud Run으로 옮기며
처음 적용. 상시 서버가 가정용 회선·오래된 하드웨어라 안정성이 부족하다고
판단해 헤르메스가 있는 PC로 배포 실행을 넘긴 사례. 관리자급 키 값은
텔레그램·헤르메스에게 값 자체로 전달하지 않고, Secret Manager 같은
저장소에 참조(이름)로만 넘깁니다.

⚠️ **원격 클라우드 세션은 헤르메스를 호출할 채널이 없습니다.** 2026-09-10
실측: `ListAgents`·`list_environments`로 확인해도 헤르메스로 연결되는
에이전트·환경이 없고, 이 세션엔 텔레그램 등 헤르메스 통신 도구 자체가
없습니다. 이런 세션에서 위 목록에 해당하는 작업(빌드 등)을 만나면, 위임을
시도했다고 서술하지 말고 **막혔다는 사실을 그대로 보고한 뒤** 클로드 코드가
직접 실행하고 동일한 DONE=VERIFIED 증거 기준을 적용하세요. 실행 환경(로컬
데스크톱 세션 등)에 따라 헤르메스 채널이 있을 수 있으니, 매 세션 실제로
확인하고 감으로 판단하지 마세요.

**⚠️ 실제 자동 실행 채널은 mailbox가 아니라 solar-bible `tasks/pending(-long)/`이다
(2026-09-27 확인, cxo-db#242)**. `mailbox.py send 헤르메스 ...`로 우편만 보내면
아무도 자동으로 안 읽는다 - 헤르메스의 크론 폴러(`solar-bible-tasks-poller`/
`-long-poller`)는 solar-bible 저장소의 `tasks/pending/`(짧은 작업, 10분 이내)
또는 `tasks/pending-long/`(긴 작업)에 `.md` 지시서 파일을 만들어 origin/main에
push해야 집어간다. 지시서 제목 첫 줄에 `(내 이름 -> 헤르메스)`를 적으면 완료 시
그 이름 앞으로 우편 알림이 자동으로 온다. 지시서는 산문 설명보다 **한 줄로 실행
가능한 스크립트/명령**을 주는 편이 훨씬 잘 통한다(핏 N19: 산문 지시서 실패,
스크립트 3연속 성공). 결과는 `tasks/done/<이름>.md`(원본 그대로)와
`reports/<이름>-result.md`(의뢰+실제 응답+헤르메스 자신의 실행 피드백)로 나뉜다.

**위임 지시서를 push한 직후: 수동 재확인 대신 감시를 건다(2026-09-27, 전 페르소나 기본 규칙)**
우편함은 받는 쪽이 새 세션을 열 때만 자동으로 보이고, 헤르메스는 Claude 세션이 아니라
`SendMessage`로 이쪽을 깨울 수도 없다 - 그래서 위임한 세션이 계속 떠 있으면 완료 알림이 와도
스스로 알아챌 방법이 없다("생각날 때마다 수동으로 재확인"은 놓치기 쉽다). 위 지시서를
`tasks/pending(-long)/`에 push한 직후, 같은 세션에서 바로 아래를 Monitor 도구의 `command`로
띄운다(직접 실행 후 방치하지 않는다 - `run_in_background`는 완료 시에만 알리므로 이벤트마다
알림받으려면 Monitor를 쓴다). 이 완료 알림은 폴러가 `tasks/pending-long/`을 처리했을 때만
자동으로 온다(`tasks/pending/`짧은 레인은 알림 없음, 결과는 `reports/`에서 직접 확인):

```
python scripts/ops/watch_mailbox_reply.py --persona <내 이름> --keyword 헤르메스,<위임 주제 낱말>
```

새 우편이 도착하면 그 줄이 이벤트로 올라온다. Monitor는 최대 30분 시효라 만료 알림이 오면 그
자리에서 재무장한다. 이 스크립트는 로컬 파일 존재만 확인하는 순수 파이썬이라 토큰을 안 쓴다
(API 호출 0) - 실제로 새 줄이 찍혀 이벤트가 될 때와 30분마다 재무장할 때만 아주 조금 든다.
