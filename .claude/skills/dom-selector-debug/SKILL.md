# DOM 셀렉터 디버깅 절차

`_sns-extension`이 다루는 사이트는 전부 **로그인이 필요해서 Claude가 직접
열어볼 수 없다.** 그래서 실패한 선택자를 고치려면 사장님에게 화면을
캡처해달라고 요청하는 수밖에 없는데, 요청을 잘못하면 왕복이 여러 번
생긴다(2026-09-03 실제로 클립 카드 하나 때문에 3번 왕복함). 아래 순서를
지키면 왕복이 1~2번으로 줄어든다.

## 원칙: 추측으로 코드부터 쓰지 않는다

href 패턴이나 class명을 "이럴 것 같다"고 짐작해서 코드부터 쓰면 거의 항상
틀린다(2026-09-03: href 기반 클립 수집, "재생" 라벨 지연로딩 판단, private
필터 최초 시도 — 셋 다 처음엔 틀렸다). **반드시 실제 마크업을 먼저 받고
나서 코드를 쓴다.**

## 1. 무엇을 캡처해달라고 요청할지

- 리프 요소(예: `<video>`, `<svg>` 하나)만 요청하면 부모-자식 관계를 알 수
  없어 한 번 더 왕복하게 된다. **처음부터 "그 요소를 감싼 카드/타일 전체"의
  outerHTML을 요청한다.**
- 정확한 요청 문구(컴맹 기준, 번호로):
  1. 대상 요소 위에서 **우클릭 → 검사(Inspect)**
  2. Elements 패널에서 **그 요소를 감싼 카드 하나 전체**가 될 때까지
     들여쓰기를 따라 위로 몇 단계 올라가기 (판단 기준: 원하는 텍스트/숫자와
     식별자(링크나 캡션)가 **같이** 들어있는 가장 작은 태그)
  3. 그 태그에서 **우클릭 → Copy → Copy outerHTML**
  4. 대화창에 붙여넣기
- 요소 선택기(화살표 커서 아이콘, Ctrl+Shift+C)로 화면에서 직접 클릭하게
  하는 게 "Elements 패널에서 찾아보세요"보다 훨씬 빠르다.

## 2. 받은 마크업에서 선택자를 뽑을 때

- class에 해시가 섞여 있으면(`css-a44adb-7937d88b--StyledLock3pt e4r3kg6`)
  그 해시는 배포마다 바뀔 수 있다고 가정하고, **의미 있는 토큰 하나만**
  정확히 매칭한다(`[class~="private"]`처럼 `~=`로 토큰 단위 매칭 — `*=`
  부분일치는 다른 클래스를 오탐할 수 있어 피한다).
- 데이터가 "라벨 span + 숫자 span" 형제 구조라면, 요소 텍스트 전체를
  느슨하게 긁는 것보다 **형제 관계(`nextElementSibling`)로 정확히 짚는다**
  — 느슨한 텍스트 매칭은 페이지의 다른 곳에 있는 동음이의 텍스트(예: "재생"이
  지표 라벨이자 재생 버튼 라벨이기도 함)를 잘못 집을 수 있다.
- 진짜 링크(href)가 없는 카드(버튼 기반 SPA)라면 억지로 href 패턴을 찾지
  말고, 캡션(aria-label 등) 해시를 id로 쓰는 대체 전략으로 바로 넘어간다.

## 3. 고친 뒤 검증

- **서버 스크립트(GitHub Actions)**: `workflow_dispatch`로 직접 재실행하고
  `get_job_logs`로 실제 출력을 확인한다 — "커밋했으니 될 것"이라고 넘어가지
  않는다. 실패하면 진단 로그(스니펫)를 보고 다음 가설을 세운다.
- **크롬 확장(`_sns-extension`)**: 사장님이 재방문해서 결과가 그대로면,
  **코드를 다시 의심하기 전에 "확장 폴더 자체가 최신 코드로 갱신됐는지"부터
  확인한다.** `chrome://extensions` 새로고침은 로컬 파일을 다시 읽는
  것뿐, GitHub에서 새로 받아오는 게 아니다(2026-09-03 사고 — README의
  "코드가 바뀌면 새로고침만으로는 안 될 수 있습니다" 절 참고). 재확인
  순서: ① 팝업의 확장 버전 번호가 방금 커밋에서 올린 버전과 같은지 ②
  아니면 zip 재다운로드 → 폴더 교체를 먼저 시키고 나서 재검증.
- 검증 없이 "고쳤습니다"라고 보고하지 않는다 — 이번 세션에서 검증 없이
  넘어갔다가 사장님이 재확인해서야 안 고쳐진 게 드러난 사례가 있었다.

## 4. 변경은 작게, PR도 작게

한 번에 여러 가설을 섞어 커밋하지 않는다. 가설 하나 → 커밋 하나 →
검증 하나. 틀렸으면 그 커밋 위에 다음 가설을 쌓아 올리고, 최종적으로
맞은 상태로 PR을 merge한다 — 검증 안 된 중간 가설이 커밋 히스토리에
남는 건 괜찮다(공개 커밋엔 "무엇을 했는가"만 남으므로).
