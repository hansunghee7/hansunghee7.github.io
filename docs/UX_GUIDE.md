## 1. 공통 원칙 — 양쪽 다 지킬 것

새 페이지나 컴포넌트를 어느 쪽에 만들든 아래는 지킵니다.

### 1.1 타이포그래피 페어링: 제목=세리프, 본문/UI=Pretendard
- **제목류**: 공개 사이트는 `'Noto Serif KR'`(로그 글 커버) 또는 `'Boska','Source
  Serif 4'`(about·book·pillar·home), 스튜디오는 `'Noto Serif KR'` — 표기는
  달라도 "제목은 명조/세리프" 원칙은 동일합니다.
- **본문/UI**: 공개 사이트는 `'Noto Sans KR'`(글 본문) 또는 `'Pretendard
  Variable'`(nav·카드·UI), 스튜디오는 전부 `'Pretendard Variable'` — 마찬가지로
  "본문·UI는 산세리프, Pretendard 우선" 원칙이 같습니다.
- 새 화면을 만들 때도 이 조합(제목=세리프 / 본문=Pretendard)을 유지하세요. 완전히
  다른 서체군(예: 고딕 단독, 손글씨체)을 새로 들이지 않습니다.

### 1.2 점진적 정보 노출 (Progressive disclosure)
핵심 정보는 항상 보이게, 부가 설명·재고성 정보는 숨겨뒀다 필요할 때만 보여줍니다.
구현 방식은 화면마다 다르고, **다르게 두는 것이 맞습니다**:
- 공개 사이트: `<details>`/`<summary>` (필러 페이지 "더보기", book.html 목차,
  모바일 GNB 아코디언) — 검색엔진 크롤러는 닫혀 있어도 읽는다는 점을 코드 주석에
  반복 기록해둠.
- 스튜디오: ⓘ info-dot 버튼(hover/탭 토글) — [STYLE_GUIDE.md](../insight-7b3e9f2c/STYLE_GUIDE.md#ⓘ-설명-버튼-info-dot-패턴) 참고.

메커니즘은 다르지만 **배치 원칙은 공통**입니다: 그 정보가 설명하는 대상 바로
옆/아래에 둔다 — 링크 끝이나 화면 구석으로 밀어두지 않습니다.

**뭘 숨기고 뭘 상시 노출할지의 기준(2026-08-31, 재정의)**: "문장이
길다/짧다"가 아니라 **"한 번 읽으면 그다음부턴 안 봐도 되는가"**로
판단합니다.
- **사실 정보(날짜·출처·집계 방식 등)** → 항상 보이는 짧은 메타 텍스트로
  둡니다(`.meta-text`, 예: "2026-08-30 신설 · CMO 마야 스레드"). 매번
  갱신되거나 스캔하듯 훑어야 하는 정보라 숨길 필요가 없습니다.
- **그 외 설명(사용법·이유·페이지 소개 등)** → 한 번만 읽어도 그 뒤로는
  다시 볼 필요가 없으면 전부 ⓘ/`<details>` 뒤에 숨깁니다. 랜딩·샘플
  페이지(`studio-sample/`)의 "이 페이지가 뭐하는 곳인지" 같은 첫인상
  설명도 예외가 아닙니다 — 처음 온 사람도 ⓘ를 눌러서 볼 수 있고, 재방문자
  에게는 어차피 다시 볼 필요 없는 정보이므로 일관되게 숨기는 쪽이 낫습니다
  (이전엔 "첫인상 설명은 상시 노출" 예외를 뒀었으나, 판단 기준이 두 개로
  나뉘면 매번 어느 쪽인지 다시 따져야 해서 하나로 통일했습니다).

### 1.3 고정 테마 — 사용자 다크모드 대응 없음
두 화면 다 `prefers-color-scheme` 미디어쿼리를 쓰지 않습니다. 대신 **페이지
유형별로 테마를 고정**합니다(공개: 대부분 다크 `#080808`+`#f5f3ee`, book.html만
예외적으로 라이트 크림 톤 / 스튜디오: 전체 라이트 고정). 사용자 시스템 설정에
따라 자동으로 바뀌는 다크모드 토글은 아직 없습니다 — 도입하려면 두 화면 전체에
영향을 주는 별도 논의가 필요합니다.

### 1.4 접근성 기본선
- 장식용 이미지(연관글 썸네일 등)는 `alt=""`, 의미 있는 이미지는 실제 설명 텍스트.
  **빈 값도 아니고, 원본 CDN URL 토큰이나 파일명을 그대로 넣는 것도 안 됩니다**
  — 2026-08-29에 블로그 본문 3개 글에서 이미지 로컬라이즈 과정 중 alt에 깨진 URL
  토큰이 남은 사고를 발견해 수정했습니다. 이미지 처리 스크립트를 만들거나 고칠 때
  alt 필드를 반드시 사람이 읽을 설명으로 채우세요.
- 아이콘 전용 버튼(닫기, 이전/다음, 메뉴 열기, ⓘ 등)에는 `aria-label` 필수.
  **아이콘만 있는 링크(`<a>`, 예: "↗" 바로가기)도 동일** — `title`만 있고
  `aria-label`이 없으면 스크린리더·터치 사용자에게 유일한 설명 통로가
  안정적으로 전달되지 않습니다. 2026-08-30에 `sns-insight.html`의 SNS
  바로가기 링크(`title`만 있던 경우)에서 실제로 발견해 `aria-label`을
  추가했습니다 — `title`은 마우스 사용자를 위해 그대로 남겨둡니다.
- **"바로가기" 링크는 화살표(↗)만이 아니라 타이틀 텍스트까지 클릭 영역에
  포함시킵니다.** "채널명 ↗"처럼 제목과 화살표를 하나의 `<a>`로 묶고,
  화살표만 따로 작은 아이콘 링크(`.shortcut-link`류, 18×18px)로 떼어두지
  않습니다 — 클릭 영역이 손가락 터치 기준으로 너무 작다는 지적을 실제로
  받았습니다(2026-09-01, `content-insight.html`/`sns-insight.html`에서
  수정). `book-insight.html`의 `labelHtml()`이 원래 이 패턴이었으니
  새 카드/헤더를 만들 때 그걸 기준으로 삼으세요.

### 1.5 브랜드 표기
- 로고/타이틀/메타데이터: 영문 **"Simplifier"**. 본문 서술: 한글
  **"심플리파이어"**. 문맥에 맞게 병기합니다(JSON-LD도 `name: "Simplifier"`,
  `alternateName: "심플리파이어"`로 이미 이렇게 되어 있음).
- 대표 개인명: 한글 본문은 "한성희", 영문/저자 표기는 "Han Sunghee"로 통일.
- **로고 이미지는 배경에 맞는 버전을 씁니다** — 다크 배경(`#080808` 등)에는
  `log_assets/images/logo_white.png`, 라이트 배경에는 검정 로고
  (`logo_black.png` — 현재는 라이브 참조가 없어
  `log_assets/images_quarantine_2026-08-29/`에 보관 중, 쓰게 되면 `git mv`로
  복원). 흰 로고를 라이트 배경에 올리면 안 보이고, 반대는 뭉개집니다.
- **문서·브리핑형 페이지에서 로고 배치는 헤더(제목 줄) 우측 끝** —
  제목과 같은 행에 두고, 날짜·메타 텍스트는 그 아래 행으로 분리합니다.
  메타 텍스트와 한 줄에 섞으면 화면 폭에 따라 로고가 애매한 위치로
  밀립니다(2026-08-30 모닝 브리핑 미리보기에서 실제로 발생해 수정한 사례).
  로고에는 `alt="Simplifier"`를 넣습니다. 공개 사이트 GNB의 로고는 좌측
  (홈 링크 관례)이라 이 규칙과 다른 게 맞습니다 — 문서형에만 적용.

### 1.6 노출 범위를 먼저 정하고 시작한다
새 페이지를 만들기 전에 "이 페이지는 고객이 검색해서 찾아와야 하는가, 아니면
관리자만 봐야 하는가"부터 정합니다.
- 공개 성격 → sitemap.xml 포함, JSON-LD/OG 메타 채움, 검색엔진 노출 극대화가 원칙.
- 관리자 전용 성격 → `<meta name="robots" content="noindex, nofollow, noarchive">`
  + `<meta name="referrer" content="no-referrer">`, 공개 nav에 노출 금지, 주소
  자체가 유일한 자물쇠(스튜디오는 지금 이 방식으로 운영 중).
성격이 애매한 채로 만들면 나중에 "이거 검색에 걸려도 되는 거였나?"를 되짚어야
하는 상황이 생깁니다.

### 1.7 UX 라이팅 — 버튼·에러·빈 상태 같은 인터페이스 문구
이 절은 **화면 문구**(버튼 라벨, 에러·검증 메시지, 빈 상태, 확인 문구)에 적용됩니다.
SNS·블로그처럼 콘텐츠로 나가는 목소리는 이 절 소관이 아닙니다 — 그건
`docs/퍼스널_브랜딩_가이드.md`(개인)·`docs/브랜딩_가이드.md`(서비스)를 봅니다. 규칙은
서술이 아니라 지시문으로 둡니다 — 이 문서 자체가 "지시문·우선순위로 쓴다"는 UX
라이팅 원칙을 따라야 한다는 게 2026-09-03 사장님 지적이었습니다.

1. **에러 메시지는 원인과 행동을 한 문장에 같이 말합니다.** 원인만 말하고 뭘 해야
   하는지 안 주면 안 됩니다.
   - ❌ "오류가 발생했습니다" — 뭐가 잘못됐는지, 뭘 하면 되는지 둘 다 없음
   - ✅ `contact_modal.html`의 실제 문구: "이메일 형식을 다시 확인해주세요.",
     "어떤 일로 연락 주셨는지 먼저 골라주세요." — 무엇이 문제인지 + 존댓말
     요청형으로 행동까지 말합니다.
2. **에러는 문제가 있는 요소 바로 옆/위에 둡니다** — 1.2(점진적 정보 노출)의 배치
   원칙과 같습니다. 문구가 폼 맨 아래에만 뜨고 문제 필드는 맨 위에 있으면
   사용자가 못 찾습니다(`contact_modal.html`이 실제로 이 문제를 겪고 고친
   사례 — 문제 필드를 하이라이트하고 스크롤+포커스까지 옮김).
3. **에러는 사용자가 고치기 시작하면 즉시 사라집니다.** 다 고쳤는데도 에러가
   남아있으면 "이것도 아직 틀렸나"는 의심을 만듭니다. `input` 이벤트에서 바로
   지우세요(`contact_modal.html` 기준 구현 참고).
4. **버튼 라벨은 동사 + 구체적 결과.** "확인"·"제출"·"OK"처럼 범용 동사만
   쓰지 않습니다.
   - ❌ "확인", "제출"
   - ✅ "보내기"(`contact_modal.html`) — 무엇을 보내는지 문맥상 분명한 선에서는
     짧아도 됩니다. 문맥이 여러 개로 갈리는 화면(예: 여러 폼이 한 페이지에)이면
     "질문 보내기"처럼 목적어를 붙입니다.
5. **파괴적 동작(삭제 등) 확인 문구는 결과를 구체적으로 말합니다.** "정말
   삭제하시겠습니까?"가 아니라 "이 글을 삭제하면 되돌릴 수 없습니다. 삭제할까요?"
   처럼 되돌릴 수 있는지 여부를 문장에 넣습니다. (아직 이 저장소에 파괴적 동작
   UI가 없어 실제 사례는 없음 — 생기면 이 항목부터 적용하고 사례로 갱신)
6. **톤은 화면 성격을 따라갑니다.** 공개 사이트(방문자 대면)는 정중한 존댓말
   기본(해요체/합니다체 혼용 가능, `contact_modal.html`처럼). 스튜디오(관리자
   전용)는 더 간결·사무적이어도 됩니다 — 매번 안내형 문장을 쓸 필요 없습니다.

### 1.8 핵심 콘텐츠 영역은 상속받은 여백보다 우선한다
콘텐츠 자체가 화면의 목적인 페이지(채팅형 답변, 긴 리스트 등)에서는 제목·nav
같은 "틀" 영역의 여백이 실제 콘텐츠 공간을 잠식하지 않게 합니다. 특히 공용
스타일시트를 상속하는 페이지를 새로 만들 때는 그 공용 규칙의 여백값이 이
페이지의 콘텐츠 밀도에 맞는지 별도로 점검하세요 — "이 페이지만의 스타일"만
살펴보고 상속된 값은 안 보고 넘어가기 쉽습니다.

- 판단 기준: 그 여백이 **가독성을 위해 필요한가**(문단 사이 숨 쉴 공간 등,
  유지) 아니면 **공용 컴포넌트의 기본값이 우연히 따라온 것인가**(이 페이지
  목적엔 불필요, 제거).
- 모바일처럼 세로 공간이 좁은 화면일수록 이 판단이 더 중요합니다 — 같은
  24px 여백도 데스크톱에서는 티가 안 나지만 모바일 뷰포트에서는 콘텐츠
  노출량을 눈에 띄게 줄입니다.

**실제로 있었던 사고**: `insight-7b3e9f2c/ask.html`(Simplifier Dialogue, 대화
내용이 핵심인 채팅형 화면)이 `studio.css`의 공용 `header` 규칙을 그대로
상속했는데, 그 규칙에 `margin-bottom:24px`가 있어 헤더 바로 아래 대화 영역이
모바일에서 불필요하게 좁아졌습니다. 페이지 자체 `<style>`에서는 `padding`만
재정의하고 상속된 `margin`은 손대지 않아서 한동안 못 잡혔습니다(2026-09-03,
PR #213). 공용 컴포넌트를 상속할 때는 padding·margin을 함께 점검하세요 —
하나만 덮어쓰면 나머지가 그대로 남습니다.

## 3. 심플리파이어 스튜디오 — 요약

세부 규칙의 정본은 [insight-7b3e9f2c/STYLE_GUIDE.md](../insight-7b3e9f2c/STYLE_GUIDE.md)입니다. 새 스튜디오 페이지를 만들거나 고칠 땐 **그 문서를 먼저 읽으세요** — 여기는 공개 사이트와 대조하기 위한 요약만 남깁니다.

- 공유 `insight-7b3e9f2c/studio.css`/`studio.js` 한 쌍으로 디자인 토큰·nav·ⓘ
  버튼·새로고침 버튼 동작을 전부 통일(공개 사이트와 가장 크게 다른 지점 — 아래
  4장 참고).
- 라이트 고정 테마, `python scripts/check_studio_style.py`로 구조적 규칙 위반을
  기계적으로 점검.
- **너비 정책(2026-08-30 확정)**: 지배 원칙은 하나 — **그 페이지에서 실제로
  폭을 쓰는 콘텐츠가 뭔지에 맞춘다.** 컨테이너(`--width-content`, 표준형,
  유동 1200px 기준)가 항상 기본값이고, 거기서 갈라지는 모양은 셋뿐입니다 —
  네 번째 숫자를 새로 만들지 않고 이 셋 중 하나로 분류합니다.
  1. **혼합형** — 표·갤러리처럼 넓게 써야 하는 요소와 문단·리스트처럼 읽는
     요소가 한 페이지에 같이 있으면, **컨테이너는 표준형 그대로 두고 러닝
     텍스트(h2/h3/p/ul/ol/blockquote)만** `--width-prose`(읽기형, 720px)로
     좁힙니다. 이미지만 컨테이너 전체 폭을 그대로 씁니다. 블로그 글 본문
     (`.post-mode + .article-body`가 읽기 폭 컬럼을 만들고 `.img-gallery`는
     컨테이너 폭 그대로 쓰는 것)이 이 경우입니다. 본문 텍스트가 다른
     메뉴보다 좁아 보이는 건 버그가 아니라 이 규칙입니다.
  1-doc. **스튜디오 문서형(`.doc` 패턴) — 예외 없이 전부 읽기 폭**
     (2026-08-31 재정의) — 스타일 가이드·브랜드 가이드·숏폼 문서·모닝
     브리핑 샘플처럼 `.doc` 패턴을 쓰는 페이지는 위 "혼합형"과 달리 표·카드
     그리드·미리보기 박스도 컨테이너 전체 폭(breakout)을 안 씁니다 —
     직계 자식 전부(`.doc > *`) `--width-prose`로 좁히고 가운데 정렬합니다.
     `.doc`는 정의상 항상 "문서"라(진짜 대시보드는 `.doc` 패턴을 안 씀)
     표/카드도 "넓게 펼친 데이터"가 아니라 "표 모양을 한 산문"에 가깝기
     때문입니다. 표 셀은 줄바꿈, 카드 그리드는 칼럼 수를 줄여서 읽기 폭
     안에 맞춥니다. 처음엔 "표·카드만 예외적으로 넓게" 시도했다가
     (2026-08-31 오전) 새 박스 유형(TOC·diff 리스트·asset-grid·mail-frame
     등)이 나올 때마다 "이건 넓어도 되나?"를 매번 새로 판단해야 해서
     하루 만에 세 번 화이트리스트를 늘렸고, 사장님 판단으로 "전부 안으로"
     단순화했습니다. 정말 넓어야 하는 데이터는 애초에 `.doc` 패턴이 아니라
     아래 3번(데이터 전용 페이지)으로 갑니다.
  2. **텍스트 전용 페이지** — 페이지 전체가 러닝 텍스트뿐이고 넓게 쓸 다른
     요소가 아예 없으면, 컨테이너를 표준형으로 키워봐야 채울 콘텐츠가 없어
     빈 여백만 남습니다. 이런 페이지는 **컨테이너 자체를 읽기형(720px)**으로
     둡니다 — Simplifier와의 대화(ask.html, 대화형 UI 전체가 텍스트)가
     이 경우입니다.
  3. **데이터 전용 페이지** — 반대로 페이지 전체가 표·스파크라인처럼 넓어야
     좋은 콘텐츠뿐이면 **컨테이너 자체를 데이터형(1600px)**으로 넓힙니다 —
     book-insight.html(두 책을 나란히 비교하는 표·스파크라인 밀집 화면)이
     유일한 사례입니다.
  4. **도구/임베드형** — 페이지가 "읽는 콘텐츠"가 아니라 다른 도구를 화면
     전체에 끼워 넣은 것이면(예: write.html의 Sveltia CMS iframe) 애초에
     폭 정책 적용 대상이 아닙니다 — 컨테이너 폭을 정하는 대신 뷰포트를
     그대로 씁니다.
  1번은 "컨테이너는 그대로, 이미지만 예외"이고 1-doc번은 "`.doc` 안에서는
  이미지 같은 예외도 없이 전부 좁힘", 2·3번은 "컨테이너 자체가 기본값에서
  벗어남", 4번은 "정책 대상 자체가 아님"이라 서로 다른 메커니즘처럼
  보이지만, 결국 같은 질문("이 폭을 실제로 쓰는 콘텐츠가 있는가")에
  대한 답이 다를 뿐입니다.
  구현 규칙(마크다운 렌더 방식, 상대링크 재작성, H1 중복 방지, 너비 토큰 등)은
  STYLE_GUIDE.md의 [".doc 패턴" 절](../insight-7b3e9f2c/STYLE_GUIDE.md#긴-마크다운-문서를-페이지로-렌더링할-때--doc-패턴)이 정본입니다.

### 3.1 대화형 에이전트 답변 스타일 (Simplifier와의 대화, 2026-09-02 확정)

`ask.html`처럼 AI가 답을 생성해 보여주는 화면은 답변 텍스트 자체가 UI입니다.
그래서 답변의 말투·형식도 화면 규칙으로 정합니다. 실제 규칙은 워커의 시스템
프롬프트(`simplifier-agent/worker-ask.js`)에 있고, 여기는 "왜 그렇게 정했는지"의
정본입니다 — 프롬프트를 바꿀 땐 이 절도 같이 바꿉니다.

- **답할 수 없으면 한 문장으로 거절한다** — 정확한 문구는
  **"심플리파이어가 답할 수 없는 내용입니다."** 근거 자료가 없을 때 다른
  표현("자료에서 찾지 못했다", "잘 모르겠다" 등)을 섞지 않고, 이 문구 뒤에
  사과나 대안 제시를 길게 붙이지 않습니다. 거절이 여러 말투로 나오면 사용자가
  "이건 못 찾은 건가, 답변이 부실한 건가"를 매번 판단해야 합니다.
- **출처는 본문 안에서 문맥으로만 언급하고, 끝에 목록으로 붙이지 않는다** —
  `("뛰어난 PO는 어떤 자질이 다를까?" 글)`처럼 문장 속에서 근거를 밝히는 건
  허용, 답변 마지막에 `(blog - …, book - …)` 같은 출처 나열은 금지. 출처는
  답변 아래 **칩(chip)** 으로 화면이 따로 보여주기 때문에 본문에 또 쓰면
  중복입니다. 이전엔 프롬프트가 나열을 시키고 프런트가 정규식으로 잘라내는
  임시방편이 있었는데(취약해서 표현이 조금만 달라져도 중복이 남음), 프롬프트
  쪽에서 아예 안 쓰게 바꿔 없앴습니다.
- **출처 칩이 붙는 조건** — 근거로 실제로 쓰인 조각의 글/책만 칩으로 답니다
  (유사도 문턱을 넘은 것만). 거절 답변에도 칩이 붙어 있으면 문턱이 너무
  낮다는 신호로 봅니다.
- **사실 질문과 방법론 적용 요청을 구분한다** — "이런 글 쓴 적 있어?" 같은 사실
  확인은 자료에 있는 것만, "질문법대로 코칭해줘" 같은 적용 요청은 자료의
  방법론을 실제로 수행. 이 구분이 없으면 코칭 요청에도 "자료에 없다"고 거절해
  버립니다.
- **답변 아래 후속 질문 칩 3개** — 답변이 끝나면 "다음에 물어볼 만한 질문"을
  칩으로 답니다. 조건은 하나, **이번 답변의 근거 자료로 실제로 답할 수 있는
  질문만** — 눌렀는데 "답할 수 없는 내용입니다"가 나오면 제안이 아니라 함정입니다.
  누르면 입력창에 채우고 바로 보내되, Voyage 쿨다운 중이면 채워두고 카운트다운이
  끝날 때 보냅니다(그 사이 사용자가 입력창을 고쳤으면 자동 전송 안 함). 첫 화면의
  제안 칩과 같은 모양(`.suggestion-chip`)을 한 단계 작게 씁니다. 거절 답변에는
  붙지 않습니다.

- **정보 노출 메커니즘**: 공개=`<details>`(SEO 친화적, 크롤러가 닫힌 콘텐츠도
  읽음), 스튜디오=ⓘ 버튼(비공개 도구라 SEO 고려 불필요, 클릭 인터랙션에 집중).
- **노출 정책**: 공개=검색엔진에 최대한 노출, 스튜디오=검색엔진에서 완전히 숨김.

**아직 정리 안 된 차이 (의도했다기보다 그때그때 만들다 보니 이렇게 됨)**:
- 스튜디오는 공유 CSS 파일(`studio.css`) 하나로 통합돼 있는데, 공개 사이트는
  레이아웃마다(`default`/`pillar`/`book`/`home-body`) 인라인 `<style>`이 따로
  있고 공유 `:root` 토큰 파일이 없습니다. 색상 하나를 바꾸려면 여러 파일을
  각각 찾아 고쳐야 하는 구조입니다.

## 5. 정리 후보

지금 당장 바꾸자는 제안이 아니라, 나중에 필요해지면 참고할 수 있도록 남겨두는
기록입니다.

- **공개 사이트 공유 디자인 토큰 파일화**: `_includes/design-tokens.html`
  같은 걸 만들어 다크 팔레트(`#080808`/`#f5f3ee`)와 book.html의 크림 팔레트를
  변수로 뽑아 각 레이아웃이 include 해서 쓰게 하면, 스튜디오처럼 한 곳만 고쳐도
  전체에 반영됩니다. 다만 Jekyll의 {% raw %}`{% include %}`{% endraw %}로 CSS 변수를 주입하는 방식과
  캐싱/빌드 영향을 먼저 검토해야 합니다 — 지금 이 문서를 쓰는 시점에서 결정하지
  않고 후보로만 남깁니다.
- **공개 사이트에도 ⓘ 패턴이 필요한 지점이 있는지 점검**: 예를 들어 book.html의
  긴 설명이나 pillar 페이지의 통계 수치처럼, `<details>`로 펼치기엔 과하고 짧은
  보조 설명 한 줄이면 충분한 자리가 있다면 ⓘ 버튼이 더 적합할 수 있습니다 —
  현재는 필요성이 확인된 사례가 없어 미룸.
