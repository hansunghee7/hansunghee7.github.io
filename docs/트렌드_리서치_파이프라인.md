> 매번 Gemini 딥리서치를 수동 실행해 반입하는 방식이었다(2026-09-15 최초 시도).
> 반복 빈도가 그 규약의 승격 신호("핸드오프가 주 3회 이상 반복되고 수동 전달에서
> 실수가 날 때")를 넘어설 것으로 보여, 검색·검증 단계를 에이전트가 직접 수행하는
> 쪽으로 전환한다. 사장님이 직접 손대는 건 3·4·7단계뿐이다.

## 7단계

| 단계 | 하는 일 | 담당 | 사용 도구·문서 |
|---|---|---|---|
| 1 | 1차 출처 기반 폭넓은 검색 | 헤르메스 | 아직 세팅 필요 — 아래 "지금 막힌 것" 참고 |
| 2 | 검색 결과 검증·정리 | 제미나이 API (또는 LiteLLM) | `docs/지시서/litellm_config.gemini-pool.yaml`(gemini-pool, 3키+자동 재시도, 2026-09-16 검증완료) |
| 3 | 조사 자료로 주제 후보 압축, 사장님께 제안 | 마야 | `assets/data/analytics.json`(조회·리드), `assets/data/search-console.json`(실제 검색 수요) 교차 |
| 4 | 주제 최종 확정 | **사장님** | — |
| 5 | 글 초안 작성 | 마야 | `docs/퍼스널_브랜딩_가이드.md`(무엇을·화법), `docs/WRITING_GUIDE.md`(문장 규칙) |
| 6 | 이미지 선정 | 마야 | `docs/질문하기_파이프라인.md` 2-1절 기준 재사용 — Unsplash `search_photos`로 검색해 `regular` URL을 `image:`에 그대로 삽입(다운로드 안 함, 컨테이너 egress 차단 실측 근거). 후보 없으면 `logo_white.png` 폴백 |
| 7 | 발행 컨펌 | **사장님** | — |

3단계가 이전 파일럿(오늘)에서 실제로 한 일이다 — 트렌드 후보를 내부 데이터와
교차해 우선순위를 매기고, 브랜딩 가이드의 1차/2차/3차 타깃 정의에 맞는지 걸러서
제안한다. "커뮤니티 화제성"과 "실제 검색 수요"가 다를 수 있다는 게 오늘 실측으로
확인됐으므로(§검색 콘솔 실측 참고), 3단계는 반드시 이 둘을 같이 본다 — 화제성만
보고 주제를 고르지 않는다.

## 지금 막힌 것 (2026-09-17)

- **1단계(헤르메스)**: 이 파이프라인을 처음 정리한 세션(마야, 로컬)엔 헤르메스로
  연결되는 채널이 없다(`ListAgents`로 확인, 로컬탐 세션만 보임). 로컬탐 세션엔
  있을 가능성이 있으나 확인 안 됨. **사장님 확인 필요**: 마야 세션에 헤르메스
  연결을 새로 설정할지, 아니면 1단계를 탐에게 위임하는 구조로 갈지.
- 이 문제가 해결되기 전까지는 1단계를 사람이 대신 실행(예: 사장님이 직접
  검색하거나, 기존 `multi-llm-handoff` 방식으로 임시 대체)해야 한다.

## multi-llm-handoff 규약과의 관계

`.claude/skills/multi-llm-handoff/SKILL.md`의 "지금 하지 않는 것" 절에 있던
"LLM 간 직접 연동(gemini-mcp 등) 미도입"은 **트렌드 스캔 용도에 한해** 이 문서로
대체된다. 다른 종류의 일회성 외부 리서치(예: 특정 기술 스펙 조사, 시장 조사)는
여전히 기존 규약(사장님이 딥리서치 도구로 직접 실행)을 따른다 — 트렌드 스캔만
반복 빈도가 승격 신호를 넘겼기 때문이다.

## 뒤집을 신호

- 1~2단계(헤르메스+제미나이 API)가 실제로 돌려봤을 때 사람이 직접 하는 것보다
  결과 품질이 떨어지면, 3단계 이전까지는 다시 수동 딥리서치로 되돌린다.
- 3단계에서 마야가 제안한 주제가 반복적으로 반려되면(2회 이상), 3단계 로직
  (내부 데이터 교차 기준)을 재검토한다.
