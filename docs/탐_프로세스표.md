| 2 | 처리 | 아래 3~5절 중 맞는 프로세스로 |
| 3 | 증거 확인 | 행의 "완료 증거" 칸에 적은 것을 실제로 본다. 못 봤으면 상태를 `진행`으로 둔다 |
| 4 | 회신 | 요청자에게 우편 한 줄(무엇을 했고 증거가 어디 있는지). 사장님 결정이 필요하면 마야 형식(CLAUDE.md 7번) |
| 5 | 닫기 | 대장 행을 "닫힌 항목"으로 옮기고 날짜·근거 한 줄 |

## 3. 헤르메스 위임 · 같은 PC 세션 간 전달

> 채널 선택(hx.sh, tasks/pending, 우편은 헤르메스에 안 닿음)과 직접 실행 예외의 정본은 `hermes-delegate` 스킬의 "채널 고르기" 절이다. 아래 표는 탐 고유의 실측과 절차만 둔다.
>
> 사장님 목표(2026-09-19): 사장님 리소스·리드타임 최소화. 복사·붙여넣기 전달이 생기면 그것이 사고다. 역할노트-탐.md 1절의 원칙(권한 뼈대)을 여기서 구체화한다.

| 순서 | 활동 | 상세 |
|---|---|---|
| 0 | 위임 판단 | GPU·장시간·재시도 가능성·원격 PC 중 하나라도 해당하면 위임, 단순 스크립트 순차 실행이면 탐이 직접(0절). 위임 금지 목록은 `hermes-delegate` 스킬 |
| 1 | 채널 확인 | 같은 PC(신PC) 세션이면 로컬 명령이 곧 헤르메스 PC다. `scripts/hx.sh`는 SSH 별칭 `shinpc`를 쓰므로 **Git Bash에서 별칭이 안 풀리면 실패한다**(2026-09-24 실측: `Could not resolve hostname shinpc`). 탐 외 세션(마야 등)은 `hx_lite.sh`(put 없음) |
| 2 | 지시 | 한 줄 완결 명령(`hx.sh ask`(표준입력=업무지시)/`read`/`ls <경로>`/`cron`, 또는 `hermes -p <프로필> chat -q "..." --oneshot`). 결과 보고 형식은 TASK~STATUS. 폴러 지연은 `pending-detector` 크론이 줄임(백로그 28) |
| 3 | 확인 | 산출물(파일·exit code·상태판)로 판정. 로그만 보고 완료라 하지 않는다 |
| 4 | 실패 | 원인을 스크립트·지시서에 고친 뒤 재지시(최대 3회). 3회째도 실패면 대장 행에 원인과 함께 `사장님` 또는 `보류` |
| 5 | 같은 PC 살아있는 세션 전달 | 우편이 아니라 세션 메시지로 직접(사장님 지시 2026-09-20: 살아 있는 스레드가 바로 보고 반응해야 함). `ListAgents`로 상대를 찾고 `SendMessage`로 보낸다. **보낸 뒤 같은 내용을 우편함에도 한 줄 요약으로 남긴다**(사장님이 보는 "에이전트 요청" 그룹은 우편함만 비춰서, 안 남기면 답장이 안 보인다. 2026-09-20 사장님 지적). 신PC에서는 우편 뒤 `hermes cron run 96bf15033f87`(배달원)로 바로 배달. 실측: 쉬는 세션(마야)에 보낸 뒤 몇 분 안에 실질 답이 왔다. 한계: 다른 PC·클라우드 세션 도달 여부는 미확인(문서상 다른 PC는 Remote Control과 서버 경유) |
| 6 | 우편함·`tasks/pending` | hx가 안 될 때(클라우드 세션, 신PC 꺼짐)나 10분 넘는 야간 배치에만 쓴다 |

**사장님이 손으로 전달한 일이 생기면** 같은 세션에서 [전달 사고 대장](전달_사고_대장.md)에 원인과 재발방지를 적는다. **지시서가 "처리 완료"로 표시돼도 결과 보고 원문이 없으면 완료로 보지 않는다.**
