# 오케스트레이터 일하는 방식 (전사 공용)

정본 공정: 탐 21번(평소 역할), 탐비상모드, 클라우드세션작업지시, 마야 18번. 이 문서는 그 공통분모와 페르소나별 적용을 한 장으로 모은 것이다.

## 한 줄 원칙
- 직접 하는 일은 지시서 작성, 위임, 결과 판정, 병합 한 줄, 사장님 대화뿐이다. 편집·조사·통독·push는 맡긴다.

## 왜
- 2026-10-07 탐 실측: 컨텍스트 25%에서 45%로 오르는 동안 손일 구간의 증가가 가장 컸고, 오케스트레이션 구간은 완만했다.
- 같은 날 주간 한도 증가는 1%p 안팎, 클라우드 크레딧은 US$164에서 161로 줄며 일감 5건을 처리했고, 같은 시간에 병합한 PR이 6건이다.
- 사장님 관찰은 "퍼포먼스가 2~3배"다. 이것은 정성 평가이고 같은 일을 손으로 했을 때와의 비교 실측은 없다.

## 맡길 곳 다섯 갈래
- 헤르메스: 수집·측정·실행·반복. solar-bible tasks/pending(-long)에 한 줄 명령 지시서를 올린다.
- 클라우드 세션: 저장소 안에서 끝나는 코드·문서·시험 PR. `claude -p "일감" --cloud <세션 주소>`로 보내고, 브랜치는 claude/cloud-..., 병합은 맡기지 않는다.
- GCP Vertex: 초안·문서·검토. ask_vertex.py(회사 크레딧 우선).
- 덱스·비티: 사실 확인과 위험 검토, 그리고 실무 구현.
- 소넷 서브에이전트: 파일 편집, 결과 파일 읽기, PR diff 검토, 한 줄 수정까지.

## 결과는 요약으로만 받는다
- 결과 파일을 오케스트레이터가 열지 않는다. 서브에이전트가 읽고 판정(채택, 조건부, 기각)과 근거 5줄만 돌려준다.
- PR은 서브에이전트가 diff를 검토하고, 오케스트레이터는 CI 확인과 병합만 한다.

## 감시 걸기
- 위임한 일마다 결과 파일이나 PR 생성을 폴링하는 감시를 같은 턴에 건다. 로그 위치를 적어 두면 세션이 닫혀도 새 세션이 읽는다.
- 클라우드 일감은 claude/cloud-* 브랜치와 PR 생성을 신호로 본다.
- 시각이 아니라 사건을 기다릴 때는 감시가 필수다(commit-gate 규칙).

## 컨텍스트 마감선
- 컨텍스트 30%에서 마감을 제안한다(비상모드는 25%). 한 세션에서 호출이 약 40회를 넘어도 제안한다.
- 인수인계에는 진행 중인 일, 결과 파일 위치, 감시 로그 위치를 적는다.

## 직접 해야 하는 예외
- 비밀값·자격증명을 다루는 일.
- 사장님 화면 앞의 브라우저 조작처럼 위임할 수 없는 일.
- 금고 코드의 허용 문장 판정.

## 페르소나별 적용 메모
- 핏: 이미 관제탑 방식이다(역할노트 8절). 서브에이전트를 임대해 실행시키고 10줄 안팎 보고서만 읽고 판정한다.
- 마야: 공정 18번으로 이미 오케스트레이터다. 조사·작성·채점은 위임하고 지시서와 판정만 한다.
- 지투: 제품·UX PO이므로 조사와 대량 읽기는 서브에이전트에 맡기고, 판단과 가이드 수정은 직접 한다.
- 노트: 개발자이므로 코드는 직접 쓰되 탐색, 검토, 시험은 위임한다.
- 헤르메스·덱스·비티: 맡는 쪽이다. 지시서에 적힌 끝 조건과 보고 형식을 지키면 된다.

## 측정 한 줄
- 세션마다 주간 한도 증가분, 병합 건수, 소진 크레딧(클라우드 US$, GCP 원)을 작업 기록(worklog.py)에 남긴다. 쌓이면 "2~3배"를 정성에서 수치로 바꿀 수 있다.
