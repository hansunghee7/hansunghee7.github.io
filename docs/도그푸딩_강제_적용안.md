# 에이전트 도그푸딩 강제 적용안 (초안, 사장님 확정 대기)

> 작성: 탐, 2026-09-20. 정의는 사장님 말씀(2026-09-20)을 그대로 따른다: **고객과 똑같은 환경에서 우리가 고객과 똑같이 써 보면서, 고객이 문제를 파악하기 전에 우리가 먼저 파악해 문제없고 더 개선된 서비스를 제공하는 것.** 이 안은 새김(saegim)을 첫 대상으로 하되 다른 서비스에도 같은 틀을 쓴다. 확정 전까지는 제안이며 정책이 아니다. 고객 정보는 공개 저장소라 쓰지 않는다.

## 0. 목표와 지표
1. **고객보다 먼저 발견**: 지표는 "고객이 먼저 발견한 문제 0건". 우리가 먼저 발견한 건수도 함께 센다.
2. **경쟁 서비스보다 훨씬 좋게**(사장님 지시 2026-09-20): 문제를 고치는 데서 끝내지 않고 개선점을 찾는다. 지표는 4절의 고정 과제 비교표에서 우위인 항목 수.

## 1. 현재 상태 (사실, 2026-09-20 확인)
- 고객 경로 시험 3종(가입 시험, 도그푸딩 스모크, 복구 시험)은 **수동 전용**이고 마지막 실행이 9/13~9/14다. 오늘 요청 제한과 GET 405 배포 뒤에는 돌지 않았다.
- 오늘의 끊김(약 18초마다 요청이 잘려 재접속)은 **핏의 보고와 우리 로그로** 알았다. 고객이 먼저 겪었는지는 미확인이다.
- **외부 고객사가 이미 1곳** 있다. 오늘 변경이 그 고객의 연결에 준 영향은 미확인이다.
- 사용 기록(조회와 인용)은 tenant별로 쌓이고 `scripts/check_usage_signal.py`로 볼 수 있다. 에이전트 계정이 고객 가입 경로로 발급됐는지는 미확인이다.
- 오늘 도그푸딩이 실제로 찾아낸 것: 요청 제한 15초에 의한 잘림 반복, UX 가이드 1.3절 토큰 빈칸(PR #852로 수정, 재시드 확인).

## 2. 강제 수단 (기계가 강제하고 기억에 맡기지 않는다)
| 층 | 강제 방식 | 담당 | 참고 |
|---|---|---|---|
| L1 같은 환경 | 에이전트 계정은 **고객과 같은 가입 → 메일 → 설치 명령 → 연결** 절차로만 발급한다(수동 발급 금지). 먼저 지금 계정이 어떻게 만들어졌는지 감사한다 | 탐 | 고객 여정 전 구간이 매번 시험된다 |
| L2 배포 게이트 | 배포 뒤 고객 경로 시험(스모크, 세션 유지 시험)이 **자동 실행**되고, 실패하면 배포를 성공으로 치지 않고 알린다. 가입 시험은 메일이 나가므로 하루 1회 | 탐 | 시험 3종은 이미 있고 수동만 자동으로 바꾸면 된다 |
| L3 상시 합성 감시 | **가짜 고객이 주기적으로 써 보는 로봇**(합성 모니터링). 실제 MCP 클라이언트로 접속해 조회하고, 몇 분 쉰 뒤 다시 조회해 끊김을 자동 검출한다. 이상이면 에이전트 채널로 알린다 | 헤르메스 크론 또는 스케줄 워크플로 | 오늘 끊김이 이 방식이면 핏보다 먼저 잡혔다 |
| L4 일상 사용 | 화면 파일을 고치는데 이 세션에 새김 조회가 없으면 한 줄 경고, 고친 뒤 인용이 없으면 한 줄 경고, 아티팩트 발행 전 조회가 없으면 경고(전부 경로와 기록으로 판정, 의미 해석 없음). 주 1회 성적표(조회, 인용, 누락, 선발견 건수) | 탐(훅), 헤르메스(성적표) | 훅은 이 저장소 세션에서만 동작한다. 다른 저장소는 따로 넣는다 |
| L5 발견 → 개선 | 발견은 비공개 저장소 인박스 이슈로 던진다(기존 규칙). 매주 1건은 고친다 | 탐 | 새 문서를 만들지 않는다 |

### 2-1. 사장님께 가는 보고는 무조건 새김을 거친다 (사장님 지시 2026-09-20)
- 기계가 감지할 수 있는 3곳(**아티팩트 발행, 파일 전달, 사장님 앞 우편**)은 이 세션에 새김 조회 기록이 없으면 훅이 막는다(`.claude/hooks/saegim-gate.py`). 시험 10개와 실제 세션 기록 3건(조회 있는 세션은 통과, 없는 서브에이전트 2건은 차단)으로 확인했다. 이 항목은 사장님 지시로 처음부터 차단형이다.
- 채팅 답변은 기계가 보고물인지 알 수 없어 막지 못한다. 규칙 문장(CLAUDE.md 진입점 표)과 주간 감사(무작위 표본)로 다룬다.
- 새김이 끊긴 날 보고가 막히지 않는 통과 장치: 이 세션의 가장 최근 새김 호출이 오류로 끝났을 때, `.claude/saegim-outage` 파일이 있을 때(접속 불가를 사장님께 밝히고 UX_GUIDE.md를 직접 읽은 뒤 만든다), 환경변수 `SAEGIM_GATE=off`. 통과 장치가 쓰인 횟수도 성적표에 센다.
- 한계: 이 저장소의 세션에서만 동작한다. 다른 저장소(shorts-lab 등)와 다른 PC, 클라우드 세션에는 같은 훅을 따로 넣어야 한다. 서브에이전트가 사장님께 직접 보내는 경우는 거의 없다고 보고 다루지 않았다(미확인).

## 3. 강도 단계와 넘어갈 신호
| 단계 | 내용 | 다음으로 넘어갈 신호 |
|---|---|---|
| 0. 이번 주 | 오늘 변경이 외부 고객에게 준 영향 확인(고객보다 먼저 아는 첫 사례) | 확인 끝 |
| 1. 이번 주 | L2 자동 시험, L3 합성 감시 | 두 주 연속 가짜 고객이 이상을 잡고 오탐이 적음 |
| 2. 다음 주 | L4 경고 훅과 주간 성적표, L1 계정 감사 | 경고가 3주 연속 무시되면 해당 항목만 차단형으로 승격 |
| 3. 이후 | 4절 경쟁 비교 정례화 | 월 1회 비교표 갱신 |

## 4. 문제점 외에 개선점을 찾는 방법 (경쟁 서비스보다 좋아지기 위해)
1. **마찰 기록**: 사용 중 문제는 아니지만 불편, 느림, 헷갈림을 한 줄로 남긴다. 고객은 "고장"보다 "번거로움"에서 떠난다.
2. **같은 과제로 경쟁 서비스 비교**: 고정 과제 5~6개(예: 화면 작업 전 가이드 찾기, 색·간격 위반 검사, 인용 기록, 새 세션 연결 설치)를 우리 서비스와 경쟁 서비스에서 같은 조건으로 실행해 **정확도, 걸린 시간, 설치 마찰, 오류**를 표로 비교한다. 에이전트 행동 시험(Golden Test)과 같은 방식이다. 경쟁 후보는 아직 확정하지 않았다: 헤르메스 딥리서치로 수집, 제미나이가 출처를 검증, 클로드가 원문 표본을 확인해 판정한다(검증 단계 미실행이면 그렇게 표기).
3. **고객 신호**: 고객의 문의, 미사용 기간, 이탈 조짐을 월 1회 본다(고객 세부는 비공개 저장소).
4. **개선 후보 채점**: 영향과 비용으로 점수를 매겨 월 1회 상위 3개를 사장님께 올리고 선택은 사장님이 한다.

## 5. 엔진 배분 ([작업 엔진 라우팅](작업_엔진_라우팅.md) 준수)
- 수집, 측정, 주기 실행은 헤르메스와 스크립트. 시험 실행은 소넷. 통과·반려·우위 판정은 클로드(소넷 이상)이고 무료·로컬 엔진에는 판정을 맡기지 않는다.

## 6. 지금 하지 말 것
- 대형 모니터링 도구 도입, 자동 롤백. 스케줄 워크플로와 헤르메스 크론이면 충분하다.
- 처음부터 차단형 훅. 오탐이 나면 일이 멈춘다.
- 에이전트 간 점수 순위. 성적표는 사용량 경쟁이 아니라 "선발견"이 목적이다.

2. 경쟁 비교의 후보를 조사로 먼저 확정할지(비교는 그 뒤).

## 8. 새김 구글 클라우드 사용량과 비용의 일일 자동 측정 (사장님 지시 2026-09-20)
목적: MCP를 쓰는 만큼 구글 클라우드에서 얼마가 나가는지 매일 자동으로 숫자로 본다. 이 프로젝트의 Cloud Run 서비스는 새김 전용이라 프로젝트 전체가 곧 MCP 비용이다. 새김의 총비용에는 구글 클라우드 외에 Supabase, 메일 발송 등이 더 있고 이번 측정은 구글 클라우드만 다룬다.

공식 문서 조사(2026-09-20, 하이쿠 수집, 원문 표본 확인은 일부):
| 무엇을 | 방법 | 사실 표기 |
|---|---|---|
| 사용량(요청 수, 청구 대상 인스턴스 시간, CPU·메모리 할당 시간) | Cloud Monitoring API를 하루 1회 조회. 읽기 권한 역할은 `monitoring.viewer` 또는 `monitoring.metricReader` | 지표 이름과 역할 확인 |
| **실제 금액**(SKU별, 크레딧 반영) | **BigQuery 결제 내보내기**를 켜고 BigQuery에서 하루 1회 SQL 조회 | Cloud Billing API는 지출액을 돌려주지 않는다(카탈로그 가격과 예산 정보만). 내보내기 자체는 무료. **단일 리전 데이터세트는 켠 날부터만 쌓이고 소급되지 않는다** |
| 예산 도달 알림 | 예산 Pub/Sub 메시지에 현재 지출액 필드(`costAmount`)가 있다 | 얼마나 자주 오는지는 미확인 |

미검증(확인 못 함): ① `gcloud`에 시계열을 읽는 명령이 있는지(사장님이 받으신 설명의 예시 명령은 확인 못 함, Monitoring API 직접 호출은 확인됨) ② 내보내기 표의 `cost` 열이 크레딧 반영 전 값이라 실부담은 크레딧 항목을 합쳐야 한다는 점(제 지식이고 이번 조사에서는 확인 못 함) ③ 서울이 Tier 2라는 공식 표기(별도 조사에서는 확인, 이번 조사에서는 못 찾음).

자동화 설계:
1. **사장님(콘솔, 한 번)**: 결제의 BigQuery 내보내기를 켠다. **오늘 켜야 이력이 오늘부터 쌓인다.** 크레딧이 2026-12-10에 소멸하므로 그 전후 비교가 가장 중요하다.
2. **탐**: 새김 저장소에 스케줄 워크플로 하나(하루 1회)와 스크립트를 만든다. 사용량은 Monitoring, 금액은 BigQuery에서 읽어 **하루 한 줄 요약**(요청 수, 청구 시간, 금액, 요청 1,000건당 금액)을 기록하고 이상이면 알린다. 기존 배포용 Workload Identity 인증을 재사용한다.
3. **사장님(콘솔, 한 번)**: 그 서비스 계정에 읽기 권한(`monitoring.viewer`, BigQuery 조회 2종)을 준다. 보안 설정이라 에이전트는 하지 않는다. 배포 계정이 이미 읽기 권한을 갖고 있으면 생략된다(시험 실행에서 거부 메시지로 확인).
4. 임시 방법: 지금처럼 결제 화면 캡처(수동). 자동화가 들어가면 폐기.
