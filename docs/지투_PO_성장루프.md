## 루프 한 바퀴의 공통 모양

- 하이~ 지투로 시작하면 훅이 **기한 지난 항목만** 한 번에 보여 준다(없으면 조용하다).
- 보인 항목은 그 세션에서 처리하거나 보류 이유를 기록장에 적는다. 처리하지 않고 넘어가면 다음 하이~에도 다시 나온다.
- 기록장에 적는 것이 바퀴를 닫는 행위다. 말로만 한 것은 닫힌 것이 아니다.

## 루프 4: 검사 공백 (사고 → 검사)

한 줄: 사고가 나면 "어떤 검사가 없었나"를 찾아 **그 검사를 실제로 추가**한다. 반성문을 쓰는 것이 아니다.

- 트리거: 병합했다 되돌림, 고쳤다가 다시 깨짐, 사장님 지적으로 고침(홈 간격 번짐, 카드 폭 불일치 같은 것). `git revert`·`git reset --hard`·`gh pr revert`를 하면 훅이 상기한다.
- 기록: `jitu_po.py gap add --what "무슨 일" --missing "없던 검사" --added "추가한 검사(훅·테스트·프로세스표 단계)"`. 추가한 검사를 아직 못 정했으면 `--added` 없이 적으면 **열린 건**이 되고 `due`에 계속 나온다.
- 닫는 조건: 훅, 시험, 프로세스표 단계, 가이드 확인 목록 중 **무엇이 바뀌었는지 가리킬 수 있을 때**만 `gap close`.
- 훅이 이미 하는 것: 병합 안전 관문. `gh pr checks ... | ...` 처럼 파이프를 붙인 채 같은 명령에서 `gh pr merge`를 하면 막는다(10/6 simplifier-saegim#558 사고가 첫 사례).
- 하지 않을 것: 사고마다 새 훅을 만들지 않는다. 먼저 기존 훅·시험·프로세스표에 한 줄 추가로 막을 수 있는지 본다(문서 다이어트 원칙).

## 루프 2: 외부 고객 지표 (주 1회 측정)

한 줄: 외부 고객이 Carvit을 **실제로 쓰고 있는지**를 매주 같은 방식으로 잰다.

- 지표(외부 호출자만, 내부 점검 계정 `jitu-check`·`dogfood`·심플리파이어 소속 제외):
  - 활성 호출자: 최근 7일에 호출한 외부 호출자 수.
  - 활성화: 호출자가 `lookup`만이 아니라 `cite`까지 도달했는가.
  - 유지: 첫 호출 주 다음 주에도 호출했는가.
  - 찾지 못한 검색률: 찾지 못한 검색 수 ÷ 조회 수, 그리고 그 검색어 목록(내용 공백 신호).
  - 피드백 수: `feedback` 호출 건수.
- 측정: `usage_company(scope=<고객 회사>)`를 읽고 `jitu_po.py kpi add --active N --views N --cites N --misses N --feedback N --note "..."`.
- 주기와 훅: 7일이 지나면 하이~ 때 "지표 측정 기한 지남"이 나온다. 예약 세션은 쓰지 않는다(10/6 사장님 결정, 과도함).
- 한계(2026-10-06 기준선): 사용 기록에 호출자×날짜 분리가 없어 "최근 7일 활성"을 정확히 나눌 수 없다. 누적 값으로 적고 노트에게 개선을 요청했다(고객 신호 F-3).
- 하지 않을 것: 고객이 1곳(5인)인 지금은 통계 의미가 약하다. North Star·코호트 분석·활성화 목표치를 정하지 않는다. 신호는 외부 고객 3곳 이상이다.

## 루프 3: 고객 신호 (수집 → 분류 → 백로그 → 회신)

한 줄: 고객이 말하지 않아도 사용 기록에서 불편 신호를 찾고, 고객이 말한 것은 **회신까지** 닫는다.

- 수집 원천: ① `feedback` 도구 호출(`usage`·`usage_company`의 recent_feedback), ② 찾지 못한 검색(recent_misses), ③ 사용 기록 이상(호출이 끊김), ④ 면담 메모. 지표 측정 때 함께 훑는다.
- 기록: `jitu_po.py feedback add --source 찾지못한검색 --who <별칭> --text "..."` → 하루 안에 `feedback triage <번호> --kind 버그|UX|요청|내용공백|칭찬|잡음 --state triaged|backlog|dropped --action "조치"`.
- 백로그로: `--state backlog`로 올릴 때 새김 UX 백로그(simplifier-saegim/docs/새김_UX_백로그.md) 행 번호를 `--action`에 적는다.
- 회신: 고객에게 가는 메시지는 사장님 컨펌 문안만 보낸다(지투 고객 발송 규칙). 회신하면 `--reply "문안 요지"`, `--state replied`. 7일 넘게 회신 없이 backlog에 머물면 `due`에 나온다.
- 고객 이름·메일·비밀값은 기록장에 넣지 않는다(호출자 별칭만).
- 하지 않을 것: 고객 피드백의 자동 수정·자동 회신. 제미나이 조사도 "사람 승인 거침이 일반적"이라고 했고, 우리 규칙상 고객 발송은 컨펌이다. 신호는 주 5건 이상 들어오는 때(그때 분류 틀을 다시 본다).

## 루프 1: 예측과 결과의 짝

한 줄: 변경을 정할 때 **"무엇이 얼마나 바뀔지"를 먼저 적고**, 점검일에 실제 값과 비교한다.

- 트리거: `gh pr merge`가 병합되면 훅이 상기한다. 사소한 문구·정리는 생략해도 된다. 사용자 행동·지표·품질에 영향을 줄 변경에만 쓴다.
- 기록: `jitu_po.py predict add --change "..." --expect "관측 가능한 한 줄" --metric "어디서 잴지" --check-on YYYY-MM-DD`. 관측할 수 없는 예측("좋아질 것")은 적지 않는다.
- 점검: 점검일이 오면 하이~ 때 "예측 점검 기한 지남"이 나온다. `predict check <번호> --actual "실제" --verdict 적중|빗나감|판정불가 --lesson "배운 것"`.
- 닫는 조건: 적중률은 `predict list` 맨 아래에 나온다. 빗나간 것은 **무엇을 잘못 가정했는지** `--lesson`에 적는다. 이것이 우선순위 판단을 고치는 재료다.
- 하지 않을 것: RICE·WSJF 같은 정식 점수 체계는 고객이 1~10곳인 단계에 맞지 않다(제미나이 조사도 같은 결론). 지금 점수(효율·긴급·효과)에 예측 한 줄을 더하는 정도로 둔다.

## 루프 5: 노트에게 요청하기 전에 취합하고, 개발 중 멈춤·변경은 확실한 이득일 때만

사장님 지시(2026-10-06): 말을 들으면 바로 노트에게 넘기는 반응 속도는 좋지만, 해당 영역의 **개선 요구사항을 완벽하게 취합**하고 지투가 "다 모았다"는 확신이 들 때 전달한다. 노트가 개발 중일 때는 **지금 멈추고 바꾸는 편이 확실히 이득**이라는 판단이 들 때만 멈춤 또는 스펙 변경을 요청한다.

- 취합: 사장님·고객의 요구가 들어오면 `jitu_po.py req add --area 영역 --text "..."`로 영역별로 모은다. 영역은 같은 화면·같은 제품 줄기로 묶는다(예: 온보딩).
- 확신: 빠진 것을 점검한 뒤 `req ready 영역 --note "..."`로 기록한다. 점검 항목은 ① 선행 작업 ② 서로 충돌하는 요구 ③ 고객·DB 영향 ④ 어떻게 확인할지다. 새 항목이 들어오면 확신이 취소되고 다시 점검한다.
- 전달: 노트에게 새 일을 시키는 메시지에는 `[영역: 이름]` 표지를 넣는다. 훅(`jitu-loop.py pre-send`)이 그 영역의 확신 기록이 없으면 막는다. 보낸 뒤 `req sent 영역 --ref ...`로 남긴다.
- 개발 중 멈춤·변경: "멈춰/중단/보류/스펙 변경/롤백 ... 주세요" 요청에는 `[멈춤·변경 이득: 무엇을 얼마나 아끼거나 막는지 한 줄]` 표지가 있어야 한다. 근거가 확실하지 않으면 보내지 않고 취합을 더 한다.
- 일을 시키지 않는 메시지(검토 결과, 병합·배포 알림, 정정 보고)는 막지 않는다.
- 기한: 모으기 시작 후 하루가 지나도 확신이 없으면 하이~ 때 "요구사항 취합 중"으로 보여 준다. 서두르지 않고 빠짐없이가 기준이다.
- 하지 않을 것: 취합을 이유로 급한 고객 장애·보안 문제를 미루지 않는다(그 경우는 이득 근거를 적고 바로 알린다).

## 루프 6: 누가 할지 먼저 정한다(담당 판정)

사장님 지시(2026-10-06): 문구 수정을 습관적으로 노트에게 넘기지 않는다. 사장님이 "지투가 직접"이라고 했는데도 지시 전에 보낸 요청이 남아 노트와 지투가 같은 일을 중복 수행했다.

- 원인: ① 세션카드의 "구현은 노트에게"가 문구·메일 본문까지 포함하는 것처럼 읽혔고, 지투가 직접 한 선례(백로그 P12 지투 직접 구현, 가이드·FAQ·카피)가 규칙으로 적혀 있지 않았다. ② 새 규칙(영역별 취합)은 "무엇을 전할지"만 거르고 "누가 할지"는 거르지 않았다. ③ 하나를 발견하면 곧바로 같은 메시지로 넘기는 반응 속도 습관이 판정 단계를 건너뛰었다.
- 담당 범위: 지투가 직접 하는 것은 사용자 문구·문안·용어·표기, 메일 본문, FAQ·사이트 문구, 가이드 문장, 백로그, 프로세스표다. 노트가 하는 것은 서버 동작, DB, 인증, 배포, 시험 실행기, 성능이다.
- 세 가지 먼저 묻기: ① 사장님이 지투가 직접 하라고 했는가 ② 지투가 이미 직접 한 선례가 있는가 ③ 노트가 이미 같은 일을 하고 있지 않은가. 하나라도 "예"면 노트에게 넘기지 않는다.
- 훅: 노트에게 문구·문안·표기·용어·메일 본문을 고쳐 달라는 메시지는 `[지투 직접 불가: 이유]` 표지가 없으면 막힌다.
- 겹침이 생기면: 노트에게는 "그 항목을 빼 달라"는 철회만 알리고(이득 근거 표지), 노트가 이미 한 변경분의 위치를 물어 참고한다.
