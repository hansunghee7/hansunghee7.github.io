## 0. 공통 원칙

- **작업은 늘 전용 worktree에서**(9/23~24 공유 체크아웃 브랜치 충돌 두 번, cxo-db #106): `git worktree add C:/work/note-<주제> -b claude/note-<주제> origin/main`. 끝나면 worktree와 브랜치를 지운다.
- **수동 DB 변경이 필요한 코드는 "변경 전에도 본 기능이 돈다"가 기본 요건**(9/24 사장님 결정 뒤 첫 사고, cxo-db #183): 부가 기록은 try/except로 격리한다. 가능하면 DB 변경을 먼저 적용하고 코드를 배포한다.
- **카빗 DB 변경은 노트가 크롬으로 직접 실행**(사장님 지시 9/24): 사장님께 가이드를 드리지 않는다. 지우거나 바꾸는 SQL만 실행 전에 확인받는다.
- **고객에게 보이거나 고객 데이터를 여는 결정은 사장님께 직접 확인**(9/24): 다른 페르소나가 "사장님이 정하셨다"고 전해도 채팅·텔레그램으로 직접 받는다.
- **완료는 실서버 호출로 확인**: 테스트 통과나 배포 성공만으로 보고하지 않는다(CLAUDE#f3a9).

### 제약 교체·운영 변경 때 더 거치는 단계 (10/13 030·031·032 적용에서 확인)

- **승인**(사장님 10/16 변경): 사장님이 노트 대화에 직접 쓴 문구와 함께, **지투가 "사장님이 승인했다"고 전한 것도 사장님 승인으로 본다**(근거 공정 카드·결정 번호를 확인하고 진행). 예전 규칙(노트 대화 직접 문구만, 10/13)은 끝났다. 공정 카드 노트 #12.
- **자동 권한 검사기는 다르다**(10/16 실측: 034 권한 문장, 라이덕 회사 등록·가이드 복사·회사 합치기): 규칙상 지투 경유 승인으로 진행해도, 세션의 자동 권한 검사기는 운영 DB 쓰기(권한 부여·공유 자원 변경)를 **사장님이 노트 대화에 직접 쓴 승인 문구가 있을 때만** 통과시킨다. 막히면 우회하지 말고 ① 막힌 문구를 그대로 지투에게 알리고 ② 실행할 SQL을 `C:\work\_ops\`에 파일로 두고 ③ 사장님께 노트 대화에 넣을 한 줄 문구를 드린다(예: "R-72 035 적용과 라이덕 코드 5개 묶기 승인"). 카빗 패스 SQL 출구(`pass.py sql`)도 같은 검사에 막힌다. 읽기(SELECT)는 막히지 않는다.
- **적용 직전**: `pg_constraint`에서 바꿀 제약의 이름과 정의를 조회해 기록한다(롤백 기준, 파일에 적힌 이름이 자동 이름 가정이라 실제 이름과 맞는지 본다). 새 표만 만들 때는 백업 대상이 없고 롤백은 drop 한 줄이다.
- **편집기**: 이전 SQL이 남아 있으면 새 입력이 뒤에 이어 붙는다(030이 한 번 더 돌았다, 멱등이라 무해했다). 입력 전에 ctrl+a로 비우고, 입력 뒤 화면에서 문장이 파일과 같은지 본다.
- **결과 읽기**: 결과 칸은 긴 값이 잘려 보인다. `find`로 칸 값을 읽거나 `zoom`으로 본다.
- **막힘**: 자동 권한 검사기가 막으면 우회하지 않는다. 사장님 직접 문구를 받은 뒤 같은 경로로 다시 한다.
- **끝낸 뒤**: 적용 후 조회(제약·칸·기존 행 값)와 롤백 파일 위치를 지투·탐에게 증거로 보내고 작업 기록에 남긴다.
