# 시크릿 처리·안전 검사 대응 기본 프로세스 설계 (초안 2026-10-04, 탐)

> 사장님 지시(2026-10-04): "탐은 맨날 과거 관습대로 접근한다. 오늘 작업을 마치면 시크릿키 처리와 안전검사 대응을 기본 프로세스 설계로 정리하라." 이 문서는 오늘(N136·N143) 실제로 막힌 경험에서 뽑은 초안이고, N143 OAuth 도그푸딩이 끝나면 실측으로 보강한다.

## 0. 결론 한 줄

문이 두 개인데 서로를 모르는 것이 문제다. **Pass 승인(사장님 폰)과 클로드 코드 안전 검사는 각자 판단하고, 한쪽의 승인이 다른 쪽에 전달되지 않는다.** 막힌 뒤에 보고하고 멈추는 대신, **일을 시작할 때 문을 미리 열어 두는 설계**로 바꾼다.

## 1. 과거 관습 (고칠 것)

오늘 반복된 탐의 습관을 스스로 적는다.

- 막힌 뒤에 알아낸다: 일을 하다가 안전 검사에 걸리고 나서 "사장님, 허용해 주세요"로 멈췄다(오늘 2회, 어제 N136 첫 발급 1회).
- 승인을 한 번 더 요청한다: 이미 받은 폰 승인이 안전 검사에는 안 보이는데, 같은 요청을 말로 다시 부탁하는 형태로 끝났다.
- 검사를 장애물로 본다: "어떻게 통과하나"를 먼저 묻고, "이 단계를 없애는 설계가 무엇인가"는 두 번째로 물었다(에이전틱 원칙 id:ag01의 "제약은 설계 재료"를 말로만 따랐다).
- 사람이 하는 일을 에이전트가 대신하려 한다: 화면에서 사람이 한 번 누르면 끝나는 일을 에이전트가 화면을 열어 처리하려다 막혔다.

## 2. 두 개의 문과 각각이 지키는 것

- 문 1, 카빗 패스 승인(사장님 폰): 비밀값 사용·키 목적지·운영 DB 변경을 건마다 승인. 지키는 것은 **값과 돈과 데이터**.
- 문 2, 클로드 코드 안전 검사(분류기): 계정·상시 규칙 변경, 비밀 저장소 쓰기, 외부 발신 같은 **에이전트 행동의 종류**. 설명 없이 거부하는 때도 있다.
- 겹치지 않는 것: 문 1의 승인은 문 2를 열지 않는다. 문 2를 열려면 사장님이 권한 모드를 바꾸거나 허용 규칙을 넣어야 하는데, 에이전트가 자기 권한 설정을 바꾸는 것은 규칙상 금지다.

## 3. 시크릿 처리 기본 규칙

- 에이전트는 값을 보지도 쓰지도 않는다. 값이 대화·로그·인자·파일에 나오면 사고다(재발급 기준은 CLAUDE.md의 자격증명 예외 조항).
- 값이 들어오는 길은 하나: 사장님이 화면에서 복사 → Pass 확장이 담음. 에이전트가 읽는 것은 키 이름과 등급뿐이다.
- 값이 나가는 길은 Pass 출구뿐: `envput`(환경 파일), `ghsecret`(깃허브), `sql`(운영 DB, 건마다 폰 승인). 목적이 한정된 키(bound)는 그 출구 말고는 못 쓴다.
- 쓰기 전에 `pass.py list`로 이미 있는지 확인한다(사장님께 메모장 안내 전에).
- 새 키 종류를 받을 때 정할 것 세 가지: 등급(일반·중요), 목적 한정 여부, 만료·재발급 날짜(날짜는 대장에 적는다).
- 서비스가 OAuth를 주면 개인 토큰 대신 OAuth를 쓴다(N143). client secret은 사람이 화면에서 한 번 복사하고 Pass가 담으며, 코드 교환은 우리 서버 중계가 한다.

## 4. 안전 검사 대응 기본 프로세스 (새 방식)

### 4-1. 시작 전 점검(프리플라이트)

일을 시작하기 전에 이 일이 어떤 분류에 걸릴지 먼저 적는다. 걸릴 분류의 예: 계정·상시 규칙 변경(외부 서비스 설정 화면, 앱 등록), 비밀 저장소 쓰기, 외부 발신, 데이터 삭제. 걸릴 것이 있으면 일을 시작하지 않고 4-2로 간다.

### 4-2. 허용을 한 번에, 좁게, 미리

- 걸릴 분류마다 따로 묻지 않고 **카드 한 장**에 묶어서 폰으로 보낸다(제목=이번 일, 본문=열 문 목록·범위·만료).
- **허용의 범위 원칙(사장님 확정 2026-10-04)**: 폰 허용은 에이전트가 해당 과제를 진행하는 데 필요한 사람의 승인, 딱 그 범위까지다. 규칙 문장에 과제 이름과 정확한 대상(도메인+경로, 폴더, 명령 종류)을 넣고, 과제가 끝나면 함께 끝낸다(만료는 상한일 뿐 과제 종료가 먼저). 더 넓은 허용·재사용·"혹시 몰라서" 넉넉한 범위는 두지 않는다. 사장님이 폰 외의 다른 요청은 받지 않게 하는 것이 목표다.
- 승인하면 금고가 허용 규칙을 설정에 넣는다(에이전트는 설정 파일을 직접 고치지 않는다). 규칙에는 만료(7일)와 범위(폴더, 또는 도메인·경로)가 반드시 붙는다.
- 지금 있는 규칙 종류는 "폴더 안 파일 작업"뿐이다. **브라우저 화면 이동(도메인·경로 한정) 규칙이 없는 것이 오늘 막힌 구멍**이다(개선 과제 4-5).

### 4-3. 거부됐을 때

- 같은 일을 다른 도구·쪼갠 명령으로 다시 시도하지 않는다(거부는 결과에 걸린 것이지 명령 모양에 걸린 것이 아니다).
- 거부 사유가 설명되어 있으면 그 사유가 없어지도록 4-2로 간다. 설명이 없으면(오늘 2번째처럼) 같은 화면을 다시 열지 않고 멈춘다.
- 멈추기 전에 끝낼 수 있는 나머지 일은 끝낸다. 보고에는 막힌 곳, 이미 받은 승인 번호, 풀리는 조건을 한 줄씩 쓴다.

### 4-4. 사람이 해야 하는 일은 사람이 하는 순간을 설계한다

계정·상시 규칙은 에이전트 금지다. 이때 "에이전트가 어떻게 대신 하나"가 아니라 **사람이 한 번만 누르면 끝나게 만든다**: 화면을 여는 것·입력할 값은 에이전트가 준비하고, 마지막 "만들기" 버튼과 값 복사는 사람이 한다. Pass 확장이 복사 값을 담는다(오늘 N143 앱 등록이 이 형태).

### 4-5. 제품 개선 과제로 올릴 것

- 허용 규칙 종류에 "브라우저 화면 이동(도메인·경로 한정)" 추가.
- 폰 승인 카드가 "금고 승인"과 "안전 검사 허용"을 한 장으로 묶어 처리(두 문을 한 번에).
- 승인 대장에 "이 승인이 어느 문을 열었나" 칸 추가(지금은 문 1만 기록).
- 설명 없는 거부(분류 이유 없음)를 만났을 때 어떤 분류인지 알아내는 방법(예: 같은 행동을 읽기 전용 화면으로 먼저 시험).

## 7. 시험 기록 (2026-10-04, 사장님 승인 "추천순, 사장님을 찾지 않고 텔레그램 승인까지")

- 1번 N143 OAuth 앱 등록: 프리플라이트 승인(폰 카드 #ac5eaf)을 받았지만 안전 검사가 같은 화면 열기를 두 번 거부했다. 거부 뒤 재시도·우회 없이 멈춤. 실측 결론: **폰 승인은 안전 검사를 열지 못한다**(4-5 개선 과제의 근거가 확정). 사장님은 이후 "찾지 말라"고 하셨으므로 권한 모드 변경 요청은 하지 않고 대기.
- 2번 N141 ②: 폴더 안 파일 작업과 `pass.py sql`은 기존 허용 경로로 멈춤 0회로 끝까지 갔다(코드·시험 6항목·push). 실제 DDL 카드는 폰 승인 5분 초과로 미실행. 멈춤 0회, 사람 개입 0회, 승인 대기 1건.
- 3번 B51: 10/3에 교체가 이미 끝나 시험 대상이 아님. 대체 후보는 N81(주간 로컬 LLM 감시, 상시 규칙 분류).
- 배운 점: 프리플라이트 카드를 "안전 검사용"이 아니라 "금고용"으로만 보내면 검사에는 소용이 없다. 4-5의 "두 문을 한 카드로 묶기"가 먼저 필요하다.

## 8. 개선 ③ 승인 대기 연장 구현 (2026-10-04 오후)

- 오늘 실제 DDL 카드가 5분 안에 눌리지 않아 요청이 사라진 경험에서 나왔다. `pass.py sql --wait <분>`(기본 5, 최대 30)으로 대기를 늘리고, 카드 바닥글과 취소 문구에 실제 분이 나온다. 길게 걸 때는 run_in_background로 돌려 에이전트가 다른 일을 이어 간다. saegim-pass dev 24ecb3a, 시험 vault_wait 5항목과 관련 5종 통과.
- 한계: 도우미(host)는 크롬이 띄운 프로세스라 크롬·확장을 다시 불러야 새 코드가 적용된다(금고는 유휴 종료 뒤 자동으로 새 코드). 그때까지 `--wait`는 무시되고 기본 5분이다. 승인 줄이 한 번에 하나라 길게 걸수록 다른 카드가 뒤로 밀린다(상한 30분의 이유).
- 다음: ① 허용 규칙 확장(브라우저 도구·도메인+경로 범위)을 위 범위 원칙으로 설계, ② 작업 허용서 카드(`pass.py plan`).
