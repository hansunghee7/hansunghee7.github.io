# 비공개 전환 절차서 (저장소 비공개 + GitHub Pro + 구PC 실행기)

작성: 탐 점검 세션, 2026-10-24. 읽기 전용 점검 결과이며 이 문서 작성 때 실행기 등록·변수 설정·공개 범위 변경·결제는 하지 않았다. 근거 공정 카드: 탐-관문 #28·#31~#36, 탐 #113·#114·#133.

## 결론 한 줄

**지금 그대로 전환하면 위험하다.** 비공개로 돌려도 깃허브 내장 "pages build and deployment"가 호스트 실행기에 고정이라 이 저장소만으로 Pro 포함 3,000분을 넘길 가능성이 크고, 지출 한도 0달러면 넘는 순간 사이트 배포가 멈춘다. 이 한 가지(위험 1)를 먼저 풀고, 별도 실행기(위험 2·3)를 갖춘 뒤 전환한다.

## 관문과 주기 실행 (점검 2)

확인된 사실(구PC의 job_started.sh 원문과 관문 로그 실측):
- 관문은 가용 메모리 3GB 이상이고 한국 시각 22:50·23:03·01:53·02:19·10:11부터 각 60분이 아닐 때만 통과시킨다.
- 안 맞으면 1분 간격으로 10번 기다리고(카드의 "30분"은 옛 설명, 실제 10분) "10분 대기 뒤 포기"를 남기며 **exit 1로 job을 실패**시킨다. 로그에 실제 포기 기록이 있다(10/23).
- 이 관문은 실행기 프로세스 전체에 걸려 있어, 새 저장소 job도 같은 실행기를 쓰면 똑같이 적용된다.
- 실행기가 online이라 runner_watch(Carvit 쪽)는 우회를 켜지 않는다(탐 #133). 이 저장소에는 자동 우회 자체가 아직 없다.

추정(실측 안 함): 포기로 실패한 예약 실행은 깃허브가 자동 재시도하지 않으므로 그 회차 데이터는 건너뛴다. PR의 build-check가 걸리면 auto-merge가 막히고 다시 실행해야 한다.

## 호환성 (점검 3)

22개 파일 모두 `runs-on`은 변수 한 줄이고(변수 없으면 ubuntu-latest), 쓰는 외부 액션은 `actions/checkout@v4`, `actions/setup-python@v5`, `ruby/setup-ruby@v1`뿐이다. 컨테이너·서비스·매트릭스 OS·윈도우·맥 의존은 없다. 위험 파일:

- **fetch-book-insight, fetch-naver-content, fetch-sns-public, verify-live-page**: `playwright install --with-deps chromium`이 시스템 패키지를 깔려고 sudo를 쓴다. 구PC는 비밀번호 없는 sudo가 안 되므로(실측: "interactive authentication is required") 이 단계가 실패한다. 한 번 손으로 깔아 두거나 `--with-deps`를 빼야 한다.
- **build-check**: `ruby/setup-ruby`와 `bundler-cache`가 우분투 26.04용 미리 빌드된 루비를 못 찾을 수 있다(추정: 지원 목록 밖 버전). 이 job은 PR마다 도는 병합 관문이라 가장 먼저 시험한다.
- **setup-python을 쓰는 19개**: 우분투 26.04 파이썬이 도구 캐시에 없으면 내려받기 실패 가능(추정). 시스템 파이썬(3.x)이 요구 버전을 만족하는지 먼저 확인.
- **scheduled-publish, site-health-check, research-newsletter, verify-live-page**: 수동 실행 입력(inputs)이 있으나 실행기와 무관(통과).
- 환경변수·시크릿은 저장소 시크릿이 그대로 주입되므로 실행기 쪽 설정은 필요 없다.

## 분 계산 (점검 4)

표본: API 목록이 1,000건에서 끊겨 **실제로는 10/20 04:19~10/23 16:45(약 3.5일)만** 잡혔다. 한계: 분은 실행 시작~갱신 시각 차이라 대기 시간이 섞이고, 깃허브는 job마다 올림 과금한다. 7일 전체로 늘리면 두 배 안팎이다.

| 구분 | 표본 3.5일 | 월 환산(×8.6) |
|---|---|---|
| pages build and deployment (303회, 호스트 고정) | 650분(올림 시 810분) | 약 5,600분(올림 시 약 7,000분) |
| 나머지 워크플로(자체 실행기로 이동 가능) | 약 807분 | 약 6,900분(이동 후 0분) |

- 전환 후에도 호스트에 남는 것은 Pages 빌드뿐인데, 이것만으로 **월 5,600~7,000분으로 포함 3,000분의 2배 안팎**이다. 초과분 약 2,600~4,000분이면 분당 0.006달러 기준 약 16~24달러(추정, 요금표 미확인).
- 지출 한도를 0달러로 두면 포함분이 끝나는 날부터 Pages 빌드가 실패해 사이트 반영이 멈춘다(추정, 가장 큰 위험).
- Pages 빌드 303회/3.5일은 봇이 main에 자주 커밋하기 때문(수집 결과 커밋 등).

4. 위험 1 해소 방식 결정(아래).

## 순서 (전환 단계, 부모 세션이 실행)

1. **위험 1 해소부터.** (가) Pages 배포를 "GitHub Actions" 소스로 바꿔 build-check의 Jekyll 빌드를 자체 실행기로 돌리는 배포 워크플로를 추가(내장 Pages 빌드 0분), 또는 (나) 봇 커밋 빈도를 줄여 Pages 빌드를 월 1,000회 미만으로. 성공 판정: 일주일 환산 호스트 분이 월 2,000분 미만. 이게 안 되면 중단.
2. 구PC에 이 저장소 전용 실행기를 **별도 폴더·별도 이름표(예: home-ci)**로 하나 더 등록하고 관문은 메모리 700MB 하한만 있는 느슨한 버전을 단다(핏 리셋창은 GPU 작업용이라 사이트 job에 불필요). 등록(config.sh)은 원격 코드 실행 통로라 사장님 직접 승인이 먼저(탐 #114). 성공 판정: 깃허브 설정 화면에서 online·Idle. 중단: 등록 토큰 오류 시 재발급만 하고 멈춤.
3. 비공개 전환 전 마지막 점검: 위 호환성 4곳을 실행기에서 `workflow_dispatch`로 1회씩 시험(변수는 아직 안 켬). 판정: 4개 모두 초록.
4. 저장소 공개 범위를 비공개로 변경(사장님 승인 뒤). 성공 판정: 로그아웃 상태로 저장소 주소·PR 주소가 404, simplifier.co.kr은 계속 열림(Pages는 비공개여도 사이트는 공개 유지).
5. 변수 켜기: `gh variable set HOME_CI_RUNNER --body '["self-hosted","home-ci"]' --repo hansunghee7/hansunghee7.github.io`. 성공 판정: site-health-check 수동 실행 1회가 자체 실행기에서 초록(job의 runner_name 확인).
6. 24시간 관측: 거절창(22:50, 01:53, 10:11) 때 실패가 0인지, 실행기 online 유지, 호스트 분 누적 확인. 중단 조건: 실패가 2회 연속이거나 실행기 offline 10분 이상 → 아래 되돌리기.

## 위험 (5개)

1. **Pages 내장 빌드의 분 초과 → 사이트 반영 정지.** 완화: 순서 1(가) 또는 (나), 지출 한도는 0달러로 유지하되 초과 임박 알림(예상 80% 이상) 설정.
2. **관문 거절로 예약 발행·사이트 점검 실패.** 완화: 별도 실행기에 느슨한 관문, 기존 saegim-test 실행기는 건드리지 않음.
3. **우분투 26.04 도구 호환(sudo·파이썬·루비).** 완화: 순서 3의 사전 시험, playwright 의존 패키지 한 번 수동 설치.
4. **실행기 한 대가 죽으면 이 저장소 전체 CI 정지.** 이 저장소에는 자동 우회(runner_watch)가 없다. 완화: 되돌리기 한 줄을 알고 있고, 우회 감시를 이 저장소에도 추가하는 것을 과제로 올림.
5. **구PC 부하·비밀 노출 범위.** 실행기 job은 같은 사용자 권한으로 돈다(키가 있는 폴더와 같은 PC). 비공개이고 1인 협업이라 현재는 허용 범위. 완화: 다시 공개로 돌리기 전에 변수를 먼저 지운다(공개 PR 코드가 자체 실행기에서 도는 것을 막는 핵심).

## 되돌리기

- **1분 안에 호스트 실행기로**: `gh variable delete HOME_CI_RUNNER --repo hansunghee7/hansunghee7.github.io` 한 줄. 변수가 없으면 모든 워크플로가 ubuntu-latest로 돌아간다(1단계 PR 2672로 확인된 동작). 이후 호스트 분이 다시 쌓이므로 지출 한도에 걸리지 않게 확인.
- **다시 공개로**: 설정 > 일반 > 위험 구역에서 공개 전환(사장님 직접). 먼저 변수를 지울 것. 위험: 비공개 기간 PR·커밋 메시지가 다시 공개되고, 한 번 공개된 내용은 복구 불가이며, 자체 실행기가 남아 있으면 외부 PR 코드가 구PC에서 돈다. 전환 시 스타·포크 관계는 되돌아오지 않을 수 있다.
- 되돌린 뒤: 실행기 이름표 home-ci는 offline으로 두고 삭제는 별도 판단.
