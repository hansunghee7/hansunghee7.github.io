# 외부 딥리서치 의뢰서: 에이전트와 사람의 대기 시간 줄이기 (2026-09-20)

> 사장님이 외부 딥리서치 도구(제미나이 등)에 직접 붙여 넣는 의뢰서다. 이 문서에는 회사 고객, 가격, 매출, 전략 같은 비공개 정보가 없다(멀티 LLM 규약 2번). 실측 수치는 우리 시스템의 기술 값이다.
> 결과는 [반입용 요약]과 함께 받아 저장소에 파일로 저장한 뒤 탐이 검토한다(규약 5원칙). 숫자와 고유명사는 검증 전에는 "미검증"으로 취급한다.

---

## 의뢰 본문 (여기부터 붙여 넣기)

### 목적
AI 에이전트 여러 개와 사람 1명이 일하는 아주 작은 조직에서, **에이전트끼리·에이전트와 사람 사이의 메시지 전달 지연과 그에 따른 대기 시간**을 줄이는 현실적인 방법을 조사해 주세요. 이론이 아니라 지금 당장 적용할 수 있는 방법을, 비용과 보안 제약 안에서 비교해 주세요.

### 우리 환경 (사실)
- 사람 1명(대표), 에이전트: Claude Code 세션 여러 개(Windows 데스크톱 앱, 로컬 PC), 별도 PC에서 도는 오픈소스 에이전트 프레임워크 Hermes Agent v0.21.3(Nous Research), 외부 LLM(제미나이 등)은 검증용.
- PC는 Windows 11 두 대와 Linux 한 대, Tailscale로 연결. 신PC(Hermes 실행)는 SSH 직결 가능(키 로그인, 왕복 약 11~12초로 실측).
- 메시지 저장은 GitHub 저장소의 마크다운 파일("우편함", 파일 1개가 메시지 1개). 사장님 알림은 텔레그램 봇.
- 예산은 사실상 0원에 가깝게, 월 몇 만원 이하. 운영 인력은 대표 1명이라 **운영 부담이 낮아야 한다.**
- **보안 원칙:** 공유기 포트 개방과 신PC의 공개 인바운드 진입로는 만들지 않는다. 외부 접속은 Tailscale만 쓴다. 공개 저장소 대상 자체 호스팅 러너는 쓰지 않는다.
- 제약: Claude Code 데스크톱 앱의 열린 세션에는 외부에서 직접 메시지를 넣을 수 있는 공식 방법이 확인되지 않았다(Channels는 CLI 플래그 `--channels`만 문서에 있고 데스크톱 앱 지원은 문서에 없음, 확인함).

### 현재 실측한 대기 시간 (기준선)
| 구간 | 현재 값 | 원인 |
|---|---|---|
| Claude 세션이 Hermes에 SSH로 직접 지시 | 약 11~12초 | 양호 |
| GitHub에 지시서 파일 푸시 뒤 Hermes 폴러가 집어 가기 | 24분 관측 | 폴러가 3분 주기로 설정돼 있으나 실제 실행 간격은 약 4분이고, **폴러가 긴 작업을 실행하는 동안 다른 지시서가 대기**함 |
| Hermes 크론 최소 주기 | `every 1m`으로 등록했으나 실제 약 2분 간격 | 원인 미확인(스케줄러 틱 추정) |
| 우편함 파일 → 텔레그램 알림 | 배달원 크론 주기 10분, 실제 약 11분 간격 | 폴링 |
| 텔레그램에서 사람이 답하기 | **불가** | 봇이 받은 답장을 에이전트에게 넘기는 경로가 없음(Hermes 게이트웨이가 봇 업데이트를 이미 소비하고 있을 가능성) |
| 긴 딥리서치(수십 분) 완료를 사람에게 알림 | 우편함+배달원 폴링에 의존, 회신 없이 30분 이상 대기한 사례 | 완료 신호가 폴링을 두 번 거침 |
| 폴러 방식 | 매번 LLM 에이전트를 호출(AI 호출 하루 약 480회, 무료 모델 일일 한도와 부딪힘) | AI 호출 기반 폴링 |

### 조사해 주세요 (각 항목마다 공식 문서·1차 자료 URL, 접속 일시, 15단어 이내 원문 인용)
1. **실행 중인 Claude Code 세션에 외부 이벤트를 넣는 방법의 2026년 현재 상태.** Channels, 세션 간 메시징(SendMessage 계열), 훅(SessionStart, UserPromptSubmit 등), MCP 알림/리소스 구독, Claude Agent SDK의 스트리밍 입력. Windows 데스크톱 앱에서 되는 것과 CLI에서만 되는 것을 구분하고, 최소 버전·플랜·플래그와 알려진 한계를 적어 주세요.
2. **소규모(에이전트 5개 이하)를 위한 저지연 메시지 전달 패턴 비교.** 후보: (a) git 저장소 폴링을 값싼 스크립트로 바꾸기, (b) 로컬 파일 감시나 OS 이벤트 트리거, (c) SQLite나 파일 기반 작업 큐, (d) NATS·Redis 같은 브로커(구PC Linux 위), (e) Tailscale 안쪽 HTTP 수신기, (f) ntfy·Pushover 등 알림 서비스. 각각 지연, 월 비용, 운영 부담, 보안 위험, 우리 제약(공개 인바운드 금지) 적합도를 표로.
3. **텔레그램 양방향 컨펌.** 사람이 봇 메시지에 답하거나 인라인 버튼을 눌러 승인하면 그 결과가 특정 에이전트에게 전달되는 구조. 이미 다른 프로세스(Hermes 게이트웨이)가 같은 봇의 업데이트를 소비 중일 때의 충돌(getUpdates 중복 소비, 409 오류) 회피 방법, 웹훅 대 롱폴링, 허용 사용자 검증, 메시지 4,096자 제한과 긴 글 분할, 링크·이미지 미리보기 동작.
4. **Hermes Agent(Nous Research) 공식 문서에서 이벤트 기반 실행이 가능한지.** 웹훅, 게이트웨이, 백그라운드 작업, 병렬 서브에이전트, 크론의 최소 주기와 즉시 실행(`cron run`이 "다음 스케줄러 틱"에 실행된다는 뜻), 여러 작업 동시 처리 가능 여부. 문서에 없으면 "문서에 없음"이라고.
5. **에이전트 작업에서 사람의 대기와 컨펌 부담을 줄이는 운영 패턴.** 승인 요청 묶음 처리, 기본값과 타임아웃 후 자동 진행, 자율 단계 설계, 알림 채널 분리(할 일 있는 알림만 사람에게, 나머지는 모니터링 채널). 근거 있는 사례나 공식 가이드 중심.
6. **대기 시간 측정법.** 최소 비용으로 지연을 지속 측정하는 방법(발송 시각, 읽음 시각, 처리 시작·종료 시각 기록 설계).

### 결과 형식
- 맨 앞에 `[반입용 요약]` 한 문단(결론 우선, 5문장 이내).
- 비교표, 그리고 **추천 3안을 "지금 / 다음 / 보류"**로 나누고 각각 실행 난이도, 예상 지연 개선, 비용, 위험, **다음 단계로 넘어갈 신호**를 적어 주세요. 우리는 1인 회사 규모라서 대기업식 정답을 그대로 옮기는 것보다 규모에 맞게 줄인 안이 필요합니다. "지금 하지 말아야 할 것"도 적어 주세요.
- 산문은 순수 마크다운, 표는 마크다운 표(데이터가 많으면 CSV), 코드는 원본 그대로. HTML과 장식 포맷은 쓰지 마세요.
- 특정 회사나 플랫폼의 자체 통계(사용자 수, 정확한 개수·비율 등)는 출처 URL이나 발표 문서명을 못 대면 절대 인용하지 말고, "다수", "상당수" 같은 정성 표현을 쓰세요.
- 확인하지 못한 것은 추측하지 말고 "미확인"이라고 쓰세요. 기억에 의존한 버전 번호나 기능 이름은 쓰지 마세요.
