## 0. 방향을 한 번 잘못 잡았다가 되돌린 기록 (정직하게 남김)

- 처음(오전): "AItoEarn은 Pay As You Go 크레딧제라 유료"라고 판단해서 메타 공식 Graph API로 방향을 틀었다. 메타 개발자센터에서 앱을 만들고 페이스북·스레드 권한까지 진행했다(2~3시간 소요).
- 핏이 실측 결과를 공유하면서(우편, 2026-09-24) AItoEarn을 이미 API로 조회해봤고, 페이스북·인스타·틱톡이 다 되며 게시 API가 "월 1,000회까지 무료"라는 걸 확인했다. 공식 문서로 재확인함: [Publishing flow](https://docs.aitoearn.ai/en/use/publish-flow), 초과분만 건당 CNY 0.10.
- 즉 애초 판단이 근거 부족이었다. 우리 규모(주 몇 건)에서는 AItoEarn이 사실상 무료다. **메타 개발자센터 작업은 버리지 않되(나중에 AItoEarn이 막히면 대안) 우선순위에서 내리고, AItoEarn을 그대로 쓰는 걸로 되돌린다(2026-09-24 사장님 승인).**

## 1. 최종 아키텍처

```
assets/data/sns_publish_queue.json (마야가 게시할 항목을 채워 둠, status: "pending")
  → GitHub Actions 워크플로(.github/workflows/publish-sns.yml, 하루 2회)
  → scripts/publish_sns_queue.py 가 AItoEarn 발행 흐름 API(POST /api/v2/channels/publish-flows) 호출
    (실제 게시 시각은 각 항목의 publishAt, AItoEarn 서버가 그 시각에 게시한다)
  → 결과(flowId 또는 에러)를 큐 파일에 다시 커밋
  → 다음 날 _sns-extension 수집 결과(팔로워·조회수)와 대조해 완료 확인(탐이 준 재사용 자산 a)
```

**왜 GitHub Actions인가**: 정해진 시각에 맞춰야 하는 반복 작업(예약 게시)은 사람이 매번 지켜보며 누르는 것보다, 그 시각에 도는 서버가 대신 하는 편이 안전하고 확실하다. 이 저장소의 `fetch-analytics.yml`(GA4)·`fetch-sns-public.yml`과 완전히 같은 구조라 새 기술이 아니라 기존 패턴의 재사용이다. 실행은 사장님이 채팅에서 승인한 항목(`approved_by`)에만 한정한다(2026-09-24, 탐의 검토 반영: 처음 이 문서를 "Claude Code 세션이 못 하니 다른 경로로 실행한다"는 식으로 썼다가 우회 설계로 판정받아 고쳤다).

시크릿 이름: `AITOEARN_API_KEY` (GitHub 저장소 Settings → Secrets and variables → Actions에 사장님이 직접 붙여넣기, 1회).

2026-09-24 사장님 재지시: "사장이 직접 업로드를 안 하는 방법을 조사든 실험이든 찾아서 해결". 복붙 반자동은 답이 아니다. 조사(서브에이전트 2건, 출처는 아래) 결과로 채널별 경로를 정했다. 모두 **실측 전**이다.

- **사장님 결정(2026-09-24)**: 브런치·로켓펀치·리멤버 모두 확장 방식으로 진행. 근거(사장님 말씀 요지): 매크로 금지는 대량 반복 어뷰징을 막는 조항이고, 우리 빈도는 사람 수준이라 위험이 낮다. **빈도 상한**: 예약 발행 기능이 있는 곳(브런치)은 확장이 주 1회 들어가 한 주치를 예약, 없는 곳(로켓펀치·리멤버)은 주 3회 직접 게시. 이 상한을 넘기는 설계는 다시 사장님 확인.
- **구현 방식 결정(사장님, 2026-09-24)**: 기존 웹스토어 SNS 확장(`_sns-extension/`)에 게시 기능을 붙인다. 이유: 새 채널이 늘 가능성이 매우 낮고, 사장님이 3년간 수집 확장을 운영해 보니 사이트 화면 변경으로 고칠 일이 1년에 1~2회였다. 그래서 심사를 받는 부담(1년에 1~2회)이 주 3회×7채널 게시를 자동화하는 효과보다 훨씬 작다. 운영 규칙: 확장에 넣기 전에 Claude in Chrome으로 사장님 크롬에서 채널별 게시를 끝까지 실측하고, 다 된 것만 모아 심사 1회. 심사 중 멈춘 채널은 마야가 크롬으로 대신 게시. 웹스토어 제출은 사장님 개발자 계정이라 매번 사장님께 확인.
- 메타 브라우저 자동화는 [계정 무결성 정책](https://transparency.meta.com/policies/community-standards/account-integrity/) 위반이라 페이스북 개인 프로필에는 확장 방식을 쓰지 않는다.
- 네이버클립(핏 쪽): 공식 업로드 API 없음(핏 확인).

### 로켓펀치 (2026-09-24 실측 성공)
- 글쓰기 창: `https://www.rocketpunch.com/` 피드의 "오늘의 생각…" 옆 `게시하기` 버튼(상단 `+ 게시하기`를 JS로 누르면 창이 안 열렸다).
- 편집기: tiptap(ProseMirror) `div.tiptap.ProseMirror[contenteditable=true]`. 값 대입이 아니라 `ClipboardEvent('paste')`에 `text/plain`을 실어 보내면 들어간다. 문단 사이를 `

`으로 이으면 문단+빈 문단 하나로 들어가 사장님이 올리던 모양과 같아진다(`
` 하나면 문단이 붙어 보인다).
- 제한: **2,000자**(화면 카운터 `n/2000자`). 넘으면 줄인 안을 사장님 컨펌 후 쓴다.
- 형식: 첫 줄 제목, 빈 줄, 본문, 끝에 `from <원문 URL>`(사장님 기존 게시물과 같은 모양).
- 이미지: **로켓펀치·리멤버 모두 대표 이미지를 넣어도 된다(선택 사항, 필수 아님)**(사장님 2026-09-24). 첫 게시(631)는 이미지 없이 올렸다. 확장에서는 `simplifier.co.kr`의 표지 이미지를 받아 `File`로 만들어 `미디어` 버튼의 파일 입력에 `DataTransfer`로 넣는 방식을 실측해 두되, 이미지 없이 올려도 된다.
- 게시: `글쓰기` 버튼 → 하단 알림 "게시물이 등록되었습니다." → `https://www.rocketpunch.com/@simplfier/post` 맨 위에 "방금"으로 뜨면 완료.
