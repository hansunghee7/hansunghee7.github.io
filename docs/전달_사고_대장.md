# 전달 사고 대장

> 사장님이 손으로 전달·복붙하거나 기다려야 했던 일을 **발생할 때마다** 한 건씩 적는다.
> 목표(2026-09-19 사장님): 사장님 리소스와 업무 리드타임 최소화. 사고마다 원인과 재발방지 대책을 세운다.
> 원칙: 원인은 **직접 확인한 것**과 **추정**을 나누어 적는다. 재발방지는 문서만이 아니라 도구나 검사로 남긴다.
> 공개 저장소이므로 호스트명, IP, 키를 적지 않는다.

## 기록 칸
발생 / 무엇을 손으로 전달했나 / 원인(확인, 추정) / 재발방지(적용 여부) / 검증

## 2026-09-20 #1 탐이 헤르메스에게 낼 지시를 사장님이 손으로 전달

- **발생**: 탐(로컬)이 헤르메스에게 결과 원문 보고를 요청. 우편함으로 보냈으나 급해서 사장님이 지시문을 복사해 헤르메스에게 직접 전달.
- **원인(확인)**
  1. 2026-09-15 설계 문서(`solar-bible/docs/hermes-channel-design.md`)에 "로컬 세션은 SSH 직결"이 이미 있었다. 그런데 이 노트북에는 신PC 접속 별칭이 없었고, 탐의 역할 노트(`역할노트-탐.md`)도 없어서 세션이 그 경로를 떠올릴 근거가 없었다.
  2. 우편함은 헤르메스 폴링(3분)을 기다려야 하고, 결과 보고를 강제하지 않는다. 지시서가 "처리 완료"로 옮겨졌는데도 결과 보고가 저장소에 없는 사례가 같은 날 확인됐다.
- **원인(추정)**: 탐이 발주 방법을 고를 때 "우편함이 표준"이라는 최근 도입 규칙을 SSH보다 먼저 적용했다. 확인은 못 했다.
- **재발방지**
  - [적용] `scripts/hx.sh`: 탐이 신PC에 지시·읽기를 하는 한 줄 통로. 허용 동작만 통과(업무지시 ask, 읽기 read/ls, 크론 조회 cron). 비밀 파일과 허용 밖 경로는 거부.
  - [적용] 이 노트북의 SSH 별칭 `shinpc`(저장소 밖, 호스트 정보를 공개하지 않기 위해).
  - [적용] `역할노트-탐.md`에 "발주는 hx 우선, 우편·복붙은 hx가 안 될 때만" 명시.
  - [적용] `hx.sh put`: 스크립트 배포 통로(헤르메스 scripts 폴더 .py만, 백업과 문법 검사 조건). 사장님 허용 2026-09-20.
  - [대기] `.claude/settings.json`에 `Bash(bash scripts/hx.sh:*)` 허용 규칙(자동 승인 검사가 자기 권한 수정을 막아 사장님 추가가 필요).
  - [미적용] 헤르메스가 결과 보고 파일 없이 지시서를 done으로 옮기지 못하게 하는 검사(헤르메스 쪽 작업).
- **검증**: 2026-09-20 hx로 크론 조회, 파일 읽기, 업무지시 왕복 11초 확인. 비밀 파일과 `..` 경로 거부 시험 통과.

## 2026-09-20 #2 배달원 알림이 사장님 폰에 스팸으로 도착

- **발생**: 신솔라 텔레그램에 에이전트 간 우편, "사장님 앞 우편 10건 쌓임" 반복, "긴급 우편 테스트"가 밤새 도착. 사장님 판정: 스팸, 왜 봐야 하는지 모름.
- **원인(확인, 스크립트 코드)**
  1. 요약을 하루 한 번만 보내려는 함수가 정의만 있고 호출되지 않았다. 사장님 앞 우편은 처리 표시도 없어서, 21:00 이후 크론이 돌 때마다(10분) 같은 요약이 나갔다.
  2. 에이전트 간 우편도 `긴급: 예`이면 신솔라로 나가는 규칙이었다.
  3. 문구에 무엇에 대한 것인지, 왜 봐야 하는지, 사장님이 할 일이 없었다.
- **원인(추정)**: 00:44~01:06에 반복된 "긴급 우편 테스트"는 헤르메스 검증이 시험 모드에서 실제 텔레그램을 보낸 것. 근거는 그 우편의 키가 상태 파일에 없다는 사실. 확인은 못 했다.
- **재발방지**
  - [적용] 정책 개정판 배포(2026-09-20 07:36): 신솔라는 사장님 앞 + `요청:` 줄이 있는 우편만, 문구는 `상황 / 무엇에 대한 것 / 👉 할 일`. 요약 알림 삭제.
  - [적용] 에이전트 우편은 별도 에이전트 채널로 분리(채널 미설정 시 아무 데도 안 보냄).
  - [적용] 시험 모드(`--dry-run`, `--mailbox-dir`, `--state-file`)는 `--really-send` 없이는 실제 발송 불가. 시험이 폰에 나가는 경로를 구조로 막음.
  - [적용] 개정 첫 실행은 기존 우편 전부를 조용히 처리(폭주 방지), 발송 직후 상태 저장(중복 방지), 하루 상한(신솔라 10, 에이전트 60).
  - [적용] 에이전트 채널 생성(사장님)과 id 설정(`courier_config.py`, `.env`는 건드리지 않음).
- **검증**: 로컬 시험 11건 통과(`scripts/hermes_courier/test_courier.py`: 첫 실행 폭주 없음, 요청 유무별 분기, 중복 없음, 상한, dry-run 무기록). 신PC 실제 크론 첫 실행 정상(기존 우편 56건 처리 표시, 종료 ok). 실제 발송 경로: 헤르메스가 `.env` 수정은 자격증명 보호로 못 해서(백업만 성공) 그룹 id를 `scripts/courier_config.py`(신PC에만 둠)로 읽게 바꿈. 시험 우편(08:16) 뒤 08:27 크론 출력에 "에이전트 채널 1건 발송" 기록. 사장님 폰(에이전트 요청 그룹) 도착 확인은 사장님 몫.
