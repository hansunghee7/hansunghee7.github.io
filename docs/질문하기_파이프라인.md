## 0. 한 장 요약

```
[검색어·기존글·리서치] → 질문 후보(자동, 주 1회) ─사장님 픽─┐
[방문자 질문 + 이메일] ──── 폼 ──────────────────────────┴→ 접수함(대기)
  → 초안(자동: 클로드 + 문체 교본) → 교정지(PR) ─사장님이 경험 채우고 확정─→ 발행(기존 파이프라인)
  → 질문자 회신 ─사장님(지금)─→ 관련글·리서치 보강(자동) → 뉴스레터 주간 묶음 ─사장님 확정─→ [성과]
```

다섯 개의 자리:

| 자리 | 무엇 | 비유 |
|---|---|---|
| Supabase `questions` 테이블 | 질문·이메일·상태 | **접수함** — 이메일이 있는 유일한 곳 (공개 저장소엔 절대 안 옴) |
| 홈페이지 저장소 | 초안·발행 글·문체 교본 | **인쇄소** — 지금도 글이 발행되는 곳 |
| GitHub PR | 초안 검토·확정 | **교정지** — 사장님이 빨간펜 들고 보는 종이 |
| GitHub Actions | 초안 쓰기·후보 제안·발행 | **야간 작업자** — 2시간마다 접수함을 본다 |
| `docs/WRITING_GUIDE.md` | 필자 문체 규칙 | **문체 교본** — 클로드가 매번 읽고 쓰는 기준 |

## 1. 원칙 다섯 가지

1. **이메일은 접수함에만.** 저장소·PR·채팅·로그 어디에도 이메일을 쓰지 않는다. 이 저장소는 공개다.
2. **사장님 이름으로 나가는 글의 경험과 사실은 사람이 넣는다.** 클로드는 자리표시자 `[에피소드 필요: …]`, `[사실 확인 필요: …]`를 남기고, 사장님이 채운다. 지어낸 경험은 한 번 나가면 회수가 안 된다.
3. **관문은 PR 하나.** 초안은 `published: false`로 PR에 올라오고, 사장님이 고친 뒤 `published: true`로 바꿔 병합하면 기존 발행 파이프라인이 라이브로 올린다. 승인 화면을 새로 만들지 않는다.
4. **기계는 상태 단어로만 움직인다.** 접수함의 `status` 한 칸이 신호등이다: `후보 → 대기 → 처리중 → 초안 → 발행 / 반려`. (쇼츠와 같은 어휘.)
5. **한 계단씩.** 한 계단이 한 주 잘 돌면 다음 계단.

"누가" 칸의 굵은 글씨가 사람이 꼭 필요한 자리. "예외만"은 문제가 생긴 것만 사장님께 올라온다는 뜻.

|---|---|---|---|---|---|---|
| 0 | 성과 기록 | 발행 글 → 조회·검색 유입·후속 질문 수 | 자동 | 이미 있는 콘텐츠 인사이트 데이터(`assets/data/`) 재사용. 새로 모으지 않음 | — | — |

| 3 | 질문 접수 | 방문자 질문+이메일 → 접수함 | 방문자 | 공개 글 하단 폼. anon 키로 Supabase에 "삽입만" | (신규) → 대기 | 폼이 "잠시 후 다시" 안내 |

**사람이 손대는 시간, 편당**: 픽 1분 + 뼈대 승인 2~3분 + 경험·사실 채우기 10~15분 + 확정 1분 + 회신 2분 = **약 17~22분**. (지금 글 한 편은 두세 시간.)

> **왜 체크포인트가 하나만 늘었나 (2026-09-03, 마야 파일럿 반영)**: 마야가 직접
> 한 편을 수동으로 써보니(파일럿) 왕복 1회 가정이 실제론 부족했다 — 완성본이
> 나온 뒤에야 "문제 원인과 해법이 안 이어진다"는 걸 사장님이 잡은 사례가 나옴.
> 필요한 확인은 셋(뼈대·실사례·로직)이었지만, **로직 확인은 이미 7단계(PR에서
> 사장님이 원고 전체를 읽는 순간)와 같은 일**이라 새 단계가 아니다. 그래서 실제로
> 추가한 건 본문 작성 **전** 확인 하나(5-2)뿐 — 왕복 3회가 아니라 1회 증가.

## 3. 상태 열 정의 (접수함 `status`)

`후보 → 대기 → 처리중 → 초안 → 발행` / 어디서든 `반려`

- 사장님이 바꾸는 것: **픽**(후보→대기, 이슈 체크박스), **발행**(PR 병합). 두 번.
- 기계가 바꾸는 것: 나머지 전부. 기계는 자기 앞 단어일 때만 움직이고, 자기 단어를 켜고 멈춘다. 잡을 때는 "지금도 '대기'인가"를 확인하고 잡는다(겹쳐 돌아도 두 번 안 씀).

## 4. 사람이 남는 자리와 이유

| 자리 | 왜 사람인가 | 자동화하면 안 되는 이유 |
|---|---|---|
| 픽 | 채널의 취향 | 검색어가 많다고 다 쓸 글은 아니다 |
| 경험·사실 채우기 | 필자의 경험은 필자만 안다 | 지어낸 에피소드는 회수 불가. 이 자리가 이 글의 "진짜" |
| 발행 확정 | 밖으로 나가기 직전 | 나간 뒤엔 본 사람을 되돌릴 수 없다 |
| 회신 (지금) | 아직 건수가 적다 | 50건 넘으면 기계로 (신호 §10) |
| 뉴스레터 확정 | 구독자 우편함은 회수 불가 | 발행 확정과 같은 이유 |

나중에 사람을 뺄 수 있는 자리: 회신(발송 API), 뉴스레터 묶음 자동 발송(연속 5회 수정 없이 확정되면).
절대 빼지 않을 자리: 경험 채우기, 발행 확정.
더할 사람 자리: 없음. 다섯 번째 사람 자리는 "편당 20분"을 깬다.

## 5. 만드는 순서 (계단)

| 계단 | 만드는 것 | 사장님이 할 일 | 기준: 다음 계단으로 |
|---|---|---|---|
| 1 | 접수함 + 폼(미리보기) — `supabase/questions.sql`, `_includes/question_form.html`, `preview/question-form.html` | SQL 실행, 접수함 주소·anon 키 등록, 미리보기에서 테스트 질문 1건 | 내 테스트 질문이 Supabase 표에 보임 |
| 2 | 초안 자동 + 교정지 — `scripts/draft_from_questions.py`, `draft-from-questions.yml` | 클로드 API 키 등록, 문체 교본 위치 결정(§9), 워크플로 수동 실행 1회 | 테스트 질문이 PR로 나타나고, 병합하니 글이 라이브에 뜸 |
| 3 | 폼 공개 + 회신 절차 | `enabled: true` (노출-승인 PR), 첫 외부 질문에 회신 | 외부 질문 1건이 끝까지 감 |
| 4 | 질문 후보 제안(1·2번) + 관련글·리서치 보강(11·12번) | 매주 이슈에서 체크 | 픽 → 초안까지 손 없이 한 편 |
| 5 | 뉴스레터 주간 묶음(13번) | 초안 PR 확정 | 한 주 묶음이 PR로 나옴 |
| 6 | 회신 자동화 + 발행 시 접수함 상태 자동 갱신 | 발송 수단 결정(§9) | 회신 손 0 |

## 6. 사장님이 할 일 — 처음 한 번 (컴맹용)

한 번만 하면 된다. 순서대로, 모르면 그 줄에서 멈추고 물어보면 된다. **키는 채팅에 붙이지 않는다** — 아래 화면에만.

1. **접수함 만들기** — Supabase 대시보드(simplifier-agent 프로젝트) 로그인 → 왼쪽 **SQL Editor** → 새 쿼리 → 이 저장소의 `supabase/questions.sql` 내용 전체 붙여넣기 → **Run**. "Success" 뜨면 끝.
2. **폼과 접수함 연결** — Supabase 대시보드 → **Settings → API** → `Project URL`과 `anon public` 키 두 개를 복사 → GitHub에서 `_data/question_form.yml` 파일 열어 `supabase_url`, `supabase_anon_key`에 붙여넣고 커밋 (anon 키는 원래 공개되는 키라 괜찮다. `service_role`은 절대 넣지 않는다). `enabled`는 아직 `false`로 둔다.
3. **미리보기에서 테스트** — `https://simplifier.co.kr/preview/question-form.html` 열어 질문 하나 보내기 → Supabase **Table Editor → questions**에 한 줄 생겼는지 확인. (여기까지가 계단 1.)
4. **클로드 API 키** — console.anthropic.com → API Keys → 새 키 → 복사 → GitHub 저장소 **Settings → Secrets and variables → Actions → New repository secret** → 이름 `ANTHROPIC_API_KEY`, 값 붙여넣기. (Supabase 시크릿 둘은 이미 등록돼 있다.)
5. **문체 교본 위치 결정** — §9의 첫 항목. 공개 `docs/`로 가면 탐이 커밋한다.
6. **첫 실행** — GitHub **Actions** 탭 → "Draft from questions" → **Run workflow**. 몇 분 뒤 **Pull requests**에 "초안: …"이 생기면 성공. (계단 2.)

## 7. 사장님이 할 일 — 매일/매주 (컴맹용)

- **PR 알림이 오면**: 폰 GitHub 앱에서 "초안: …" PR 열기 → **Files** 탭에서 파일 열어 연필(편집) → `[에피소드 필요]` 자리에 경험 쓰기, 숫자 확인, 대표 이미지 경로 바꾸기 → `published: false`를 `true`로 → Commit → **Merge**. 라이브 반영은 자동.
- **회신**: 접수함(Supabase Table Editor)에서 그 질문의 이메일 보고 Gmail로 링크 1통.
- **매주 (계단 4부터)**: "질문 후보" 이슈에서 마음에 드는 것 체크. 그게 픽.
- 이 외의 것은 하지 않는다. 초안을 채팅에 붙이거나, 파일을 옮기거나 하지 않는다. 그런 일이 생기면 파이프라인이 덜 된 것이니 탐에게 말한다.

| 결정 | 선택지 | 탐 추천 |

| 문체 교본 위치 | 공개 `docs/WRITING_GUIDE.md` (자동화가 바로 읽음, 문체 규칙이 공개됨) vs 비공개 `simplifier-cxo-db` (Actions에 PAT 하나 추가) | 속도가 목표면 **공개**. 문체 규칙은 이미 발행된 글에 다 드러나 있는 것이라 새로 새는 정보가 적다 |
| 초안 모델 | `claude-opus-5`(기본) vs Sonnet 5(약 1/3 비용) | 편당 $0.3이면 품질 우선, **오퍼스** |
| 지어낸 에피소드 | 허용 / 자리표시자 | **자리표시자** (원칙 2) |
| 회신 수단 | Gmail 수동 / 발송 API | S1은 **수동**, 50건 신호 |
| 뉴스레터 발송 수단 | 미정 | 계단 5 전엔 정하지 않는다 |
| 폼 문구·디자인 | 미리보기 초안 | 시안(UX)에게 검토 요청 가능 |

## 10. 하지 않을 것과 다음 단계 신호

**지금 하지 않는다**: 승인 전용 화면, 사람 확인 없는 자동 발행, 이메일을 저장소·시트로 복사, 뉴스레터 플랫폼 선계약, 저장소 밖 워커 코드 수정, 로그인 있는 웹서비스.

**신호가 오면 다시 판단한다**:
- 주 3건 이상 질문 접수 → 2시간 주기를 즉시(웹훅)로
- 연속 5회 PR을 수정 없이 병합 → 자동 발행 실험(경험 자리가 비어 있지 않을 때만)
- 이메일 50건 → 회신 발송 API
- 에피소드 자리가 매번 비어 있음 → 비공개 "경험 은행" 설계(사장님 경험담을 미리 쌓아두고 클로드가 고르게)
- 외부 사용자가 접수함을 관리해야 함 → 이때 로그인·권한
- 다이얼로그(제미나이 무료 티어) 처리 용량이 실제로 걸림 → 그때 "대기 티켓 +
  SNS 캠페인" 성장 채널화 검토(2026-09-03 마야 아이디어, 시안·탐 스코프). 계단
  1(접수함)도 아직 안 켜진 지금은 두 계단 앞선 얘기라 보류.
