# 설계: 자체 실행기 컨테이너 방식(C안) — 비공개 전환의 분 문제를 푸는 공정자산 (초안)

작성: 탐, 2026-10-24. 상태: 설계 초안, 해커톤 이후 착수. 근거 공정 카드: 탐-관문 #28·#31~#47, 시험 실패 기록 run 40037028311.

## 결론 한 줄

저장소를 비공개로 돌리면 호스트 실행기는 월 3,000분 포함인데 우리는 월 약 16,700분을 쓴다. 스케줄을 줄이는 B안은 약 19%만 줄이므로 부족하고, 작업을 **컨테이너 안에서 자체 실행기로** 돌리는 C안이 필요하다. 이 문서는 C안을 반복 가능한 절차(공정자산)로 만드는 설계다.

## 사실 (2026-10-24 실측)

- 최근 7일 1,937건, 올림 분 합 3,905분(월 환산 약 16,700분). 구성: 페이지 내장 빌드 1,639분, 빌드 점검 1,162분, 예약 발행 462분, 책 인사이트 수집 193분, 사이트 점검 114분, 나머지 소량. 한계: 분은 실행 시작~갱신 시각 차이라 대기가 섞인다.
- 7일 main 커밋 597건 중 274건이 `[skip ci]` 봇 스냅샷이다. 배포 워크플로(pages-deploy.yml)를 push 방식으로 바꾼 뒤 이 커밋은 배포를 일으키지 않는다(실측: 스위치 뒤 커밋 4건 중 3건 건너뜀). 이 효과로 페이지 빌드가 약 46% 줄어 총 분이 약 19% 줄 것으로 본다(추정, 월 약 13,500분).
- 구PC 제약: CPU가 구형(AVX2 없음)이라 `actions/setup-python`이 받는 미리 빌드된 파이썬이 "CPU ISA level is lower than required"로 실패한다. 루비는 설치되어 있지 않고 `ruby/setup-ruby`는 도구 캐시 폴더 쓰기 권한이 없어 실패한다. 관리자 암호(sudo)는 에이전트가 쓸 수 없다. 도커는 쓸 수 있고 `python:3.11` 이미지가 이미 있다.

## 설계

1. **컨테이너 단위:** 워크플로의 job에 `container: image`를 단다. 파이썬 job은 `python:3.11-slim`, 사이트 빌드 job은 `ruby:3.3`(둘 다 일반 x86-64 빌드라 CPU 제약이 없다). 도구 설치를 호스트가 아니라 이미지가 맡으므로 sudo가 필요 없다.
2. **이미지 고정:** 태그가 아니라 버전(가능하면 digest)으로 고정하고, 이미지 갱신은 별도 PR로만 한다. Docker Hub 내려받기 한도를 피하려고 한 번 받은 이미지는 구PC에 두고 `pull_policy`로 재사용한다.
3. **캐시:** 루비 gem과 파이썬 패키지는 컨테이너 밖 볼륨(실행기 폴더의 `_cache`)에 둔다. 매번 설치하지 않게 한다.
4. **실행기 분리:** 이 저장소 전용 실행기(이름표 home-ci)는 별도 폴더·별도 이름표, 작업 시작 관문은 메모리 700MB 하한만 둔다. 기존 카빗용 실행기는 건드리지 않는다.
5. **전환 스위치:** 워크플로의 `runs-on`은 변수(`HOME_CI_RUNNER`)로 고르고, `container:`도 같은 변수가 켜질 때만 적용되게 한다. 변수를 지우면 1분 안에 호스트 실행기로 돌아간다.

## 순서와 판정 (단계마다 증거, 실패하면 멈춤)

1. 사이트 빌드 job만 컨테이너로 시험(임시 브랜치 push 방식, 변수는 끈 채). 판정: 빌드 성공, 산출물 HTML 개수가 호스트 빌드와 같음.
2. 빌드 점검(병합 관문)을 컨테이너로. 판정: PR 5건 연속 성공.
3. 파이썬 수집 워크플로를 하나씩. 판정: 각각 1회 수동 실행 성공 후 다음.
4. 변수 켜기와 비공개 전환은 마지막이며 사장님의 "전환하세요" 한 마디가 있어야 한다.
5. 관측: 24시간 동안 호스트 분 증가 0, 실패 0, 실행기 online 유지.

## 위험

- 컨테이너 안에서 만든 파일의 소유자 때문에 작업 폴더 정리가 실패할 수 있다(실행기 사용자와 컨테이너 사용자를 맞추거나 작업 후 정리 단계를 둔다).
- 구PC는 상시 한 대라 죽으면 이 저장소 전체 CI가 멈춘다. 자동 우회(호스트 실행기로 되돌리기) 감시를 이 저장소에도 만든다.
- 구PC의 메모리와 디스크는 다른 작업(영상 제작 등)과 나눠 쓴다. 메모리 하한 700MB와 디스크 여유 점검을 관문에 둔다.

## 대안과 선택 기준

- **C1. 구PC 컨테이너(이 문서의 본안):** 비용 0, 구PC 의존이 남는다.
- **C2. 클라우드 가상머신 실행기:** 신형 CPU와 관리자 권한이 있어 도구 설치 제약이 없다. 비용은 Azure 크레딧($5,000, 2027-07-11 만료)으로 충당할 수 있으나 상시 가동 비용과 관리 부담이 생긴다(요금은 이번에 조회하지 않았다).
- **C3. 오라클 무료 서버:** Always Free 서버는 유휴 7일이면 회수될 수 있어 주기 실행에는 맞지 않는다.
- 선택 신호: 구PC 컨테이너 시험(1~2단계)이 안정적이면 C1, 구PC 부하나 장애가 반복되면 C2로 간다.

## 사장님이 정할 것 (해커톤 이후)

- C1로 먼저 시험할지, C2(클라우드 가상머신)를 바로 시험할지.
