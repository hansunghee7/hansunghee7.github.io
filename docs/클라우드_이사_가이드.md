## 1. `simplifier-agent` 코드를 private 저장소로 (가장 효과 큼)

**왜**: 지금 이 프로젝트는 PC에만 있어서, 클라우드 세션에서는 코드를 읽지도
고치지도 못합니다. GitHub에 올려두면 RAG 로직 개선·프롬프트 튜닝·`ingest.py`
수정 등 **작업의 대부분을 클라우드에서** 할 수 있게 됩니다.

**핵심 원칙**: 코드만 올리고 **책 PDF는 절대 올리지 않습니다.** PDF는 계속
PC에만 두고, 실제 임베딩을 돌리는 그 순간에만 PC를 씁니다.

### 순서

1. GitHub에서 저장소를 새로 만듭니다 (사장님이 직접 — 자동화 도구는 저장소
   생성 권한이 없습니다):
   - https://github.com/new
   - Repository name: `simplifier-agent`
   - **Private 선택** (반드시. Public으로 만들면 안 됩니다)
   - "Add a README file" 등 초기화 옵션은 **전부 끄기**
   - Create repository

2. PC에서 클로드 코드를 열고 `simplifier-agent` 폴더에서 이렇게 요청하세요:

   > "이 폴더를 git 저장소로 만들고, 책 PDF(book_sources/)는 .gitignore로
   > 제외한 다음 `hansunghee7/simplifier-agent` private 저장소에 올려줘.
   > 올리기 전에 `git status`로 PDF나 API 키가 포함되지 않았는지 꼭 확인해줘."

3. **올리기 전 반드시 눈으로 확인할 것** (사장님이 직접):
   - `git status`에 `.pdf` 파일이 하나도 없는지
   - `.env`, `service_account.json`, API 키가 든 파일이 없는지
   - 하나라도 보이면 그대로 진행하지 말고 `.gitignore`부터 고칠 것

4. 올린 뒤 클라우드 세션에서 그 저장소를 열어 정상적으로 보이는지 확인.

### 이후 작업 방식

- 코드 수정·리팩터링·문서화 → **클라우드**
- 책 PDF를 새로 넣고 `ingest.py` 실행 → **PC** (1~2년에 한 번)

## 2. 책 PDF는 왜 지금 옮기지 않는가

Supabase Storage 같은 곳에 PDF를 올려두면 임베딩까지 클라우드에서 돌릴 수
있습니다. 기술적으로 가능하고, `SUPABASE_SERVICE_KEY`가 이미 GitHub Secrets에
있어서 준비도 반쯤 돼 있습니다.

**그런데 지금은 하지 않는 게 맞습니다.** 이 작업이 필요한 빈도가 신간을 낼
때, 즉 1~2년에 한 번이기 때문입니다. 그 한 번을 위해 버킷 설정·CI 다운로드·
시크릿 관리·실패 디버깅 체계를 만드는 건 들이는 비용이 얻는 편의보다 큽니다.

**나중에 아래 신호가 오면 그때 옮기세요:**
- 자료 추가가 분기에 한 번 이상으로 잦아짐
- PC 말고 다른 기기에서도 임베딩을 돌려야 하는 상황이 생김
- 임베딩 소스가 PDF 2개 → 수십 개로 늘어남

## 3. GA4·서치콘솔·클래리티 백업 트리거를 cron-job.org로 통일

**현재 상황**: `.github/workflows/fetch-analytics.yml`은 이중 안전장치를
씁니다 — GitHub cron(하루 3회) + **PC 작업 스케줄러**가
`Documents\SimplifierSNSBot\trigger-github-workflows.ps1`로 직접 호출.
반면 `fetch-search-console.yml`·`fetch-clarity.yml`은 백업이 저녁
재시도(19시대) cron뿐이라, 새벽 예약이 건너뛰면 그날 아침 브리핑은
낡은 값을 그대로 보여줍니다 — 2026-08-30·31 이틀 연속 실제로 이랬습니다.

이중 안전장치 자체는 옳은 설계입니다. GitHub의 예약 실행은 "최선 노력"
방식이라 부하가 높으면 지연이 아니라 **아예 건너뛰기도** 하거든요(이
저장소에서 실제로 여러 번 안 돈 적 있음). GA4의 기존 백업도 **PC가 켜져
있어야만** 작동한다는 한계가 있었습니다.

**해결**: 이미 `fetch-book-insight.yml`이 쓰고 있는 방식을 GA4·서치콘솔·
클래리티 세 워크플로 모두에 적용합니다 — **cron-job.org**(무료 외부
스케줄러)에서 GitHub API의 `workflow_dispatch`를 호출. PC와 무관하게
돌고, 세 워크플로 모두 이미 `workflow_dispatch: {}`가 열려 있어서
코드 변경 없이 cron-job.org 쪽 설정만으로 끝납니다.

### 순서

1. https://cron-job.org 로그인 (도서 순위용으로 이미 쓰고 계시니 계정 있음).
   Actions write 권한은 워크플로 단위가 아니라 **저장소 단위**라, 그때 만든
   PAT를 그대로 재사용하면 됩니다(새로 안 만들어도 됨).
2. 새 cron job을 **3개** 생성 (URL의 워크플로 파일명만 다르고 나머지는 동일):

   | 워크플로 | URL의 `.../workflows/` 뒤 | 실행 시각(KST) |
   |---|---|---|
   | GA4 | `fetch-analytics.yml/dispatches` | 05:45 |
   | 서치콘솔 | `fetch-search-console.yml/dispatches` | 05:45 |
   | 클래리티 | `fetch-clarity.yml/dispatches` | 05:45 |

   공통 설정:
   - Method: **POST**
   - Headers:
     - `Authorization: Bearer <GitHub PAT>` (fine-grained, 이 저장소의
       Actions write 권한만)
     - `Accept: application/vnd.github+json`
   - Body: `{"ref":"main"}`
   - 05:45로 같은 시각을 쓰는 이유: 세 스크립트 모두 그날 값을 통째로
     다시 써서(upsert/overwrite) 여러 번 돌아도 안전하므로, 새벽 cron
     순번(04:47~05:31)이 다 지나고 06:00 브리핑 전에 한 번에 메우는
     쪽이 cron job을 따로 관리하는 것보다 단순합니다.
3. 각각 한 번 수동 실행해서 GitHub Actions 탭에 `workflow_dispatch` 실행이
   뜨는지 확인
4. 확인되면 **GA4용 PC 작업 스케줄러 기존 작업을 비활성화**하고, 이 파일과
   `fetch-analytics.yml` 주석에서 로컬 스케줄러 언급을 지울 것

> ⚠️ PAT는 대화로 주고받지 말고 사장님이 cron-job.org 화면에 직접 붙여넣으세요.

## 4. 옮길 수 없는 것 — 크롬 확장 (영구 로컬)

링크드인·페이스북·인스타그램·스레드·리멤버 5개 채널의 팔로워 수는
**로그인한 브라우저 세션에서만** 보입니다. 서버에서 접근할 방법이
원리적으로 없습니다:

- 공식 API: 링크드인은 팔로워 수를 파트너 전용으로 막았고 신규 파트너
  접수도 닫혀 있습니다(2026-08-30 확인). 나머지도 앱 심사·검증이 필요한데
  얻는 게 숫자 하나라 비용이 안 맞습니다.
- 서버 스크래핑: 로그인 벽 + 자바스크립트로 그리는 화면이라 HTML만 받아서는
  숫자가 없고, 자동 요청은 봇으로 감지될 위험이 있습니다.
- 크롬 확장은 **모바일에서 동작하지 않습니다**(안드로이드·iOS 모두 미지원).
  즉 이 5개는 PC를 켠 날에만 수집됩니다.

**그래서 한 일**: 옮길 수 있는 3개(브런치·네이버블로그·로켓펀치)를
2026-08-30에 서버 수집으로 이관했습니다(`scripts/fetch_sns_public.py`).
확장이 여는 탭도 8개 → 5개로 줄었고, 최소화된 별도 창에서 열려 작업을
방해하지 않습니다.

**판단 원칙**: 로컬에 남을 수밖에 없는 것과 옮길 수 있는 것을 구분해서,
옮길 수 있는 것만 옮긴다. 전부 옮기려 애쓰면 무리한 우회(로그인 자동화 등)로
가게 되고 그건 계정 정지 위험을 부릅니다.
