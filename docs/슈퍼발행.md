# 슈퍼발행: 콘텐츠 등록·관리 정본

사장님이 "컨텐츠 등록 및 관리 방식에 이름을 하나 지어 정본으로 만들고 마야도 쓰게 하라"고 하셔서(2026-10-22) 핏이 이름을 지었다. 영상(숏폼·롱폼)과 SNS 글을 여러 플랫폼에 예약하고, 올라갔는지 확인하고, 일정을 바꾸는 방식 전체를 가리킨다. 근거는 같은 날 한 슈퍼구루 조사(제미나이 Reddit·GitHub 공감순 질의 2건, 덱스 의견 DX30, 비티 의견 BT33)와 우리 실측이다. 이름 사전은 [슈퍼_용어집.md](슈퍼_용어집.md).

## 다섯 원칙

- **날짜의 정본은 주제 시트 한 곳이다.** 시트가 플랫폼별 예약 날짜를 따로 적는다(시차 게시 허용). 유튜브·AItoEarn·DB는 시트를 따라가는 쪽이고, 어긋나면 시트가 맞다. 플랫폼 앱(유튜브 스튜디오, 인스타 앱 등)에서 따로 고치지 않는다.
- **"예약됨"과 "게시 확인됨"을 나눈다.** 예약 서비스의 상태 1(게시)은 "그쪽 기록상 올렸다"일 뿐 영상이 실제로 있다는 뜻이 아니다. 존재는 따로 확인한다.
- **일정 변경은 단일 명령으로만 한다.** `resched_all.py`가 시트, 유튜브, AItoEarn 순서로 맞춘다. 새 예약을 먼저 만들고 옛 예약을 취소하며, 삭제는 하지 않고, 이미 공개·게시된 것은 건드리지 않는다.
- **점검은 하루 1회, 알림은 문제가 있을 때만, 한 채널로만 보낸다.** `post_verify.py`가 감시 대장(`fn:post-verify`)에서 돈다.
- **정각·슬롯은 사장님이 정한 대로 둔다.** 롱폼 슬롯과 17:00은 핏-발행#43·#50이 정본이다. 정각 회피 같은 실험은 사장님이 정할 때만 한다.

## 상태를 부르는 말

- **예약됨**: AItoEarn 상태 0, 유튜브는 비공개+예약 시각.
- **게시 확인됨(VERIFIED)**: 상태 1이고 플랫폼에서 영상이 실제로 확인됐다(틱톡은 영상 페이지의 내장 응답 statusCode 0).
- **어긋남(DESYNC)**: 게시 기록은 있는데 영상이 없다(틱톡 statusCode 10204 "item doesn't exist").
- **지연(OVERDUE)과 멈춤(STUCK)**: 예약 시각이 30분 넘게 지났는데 AItoEarn 상태가 0·6으로 남았거나, 유튜브가 비공개로 남았다.
- **취소**: AItoEarn 상태 9는 취소다. 같은 글의 다른 예약이 있으면 재예약된 흔적이다. [실측: 2026-10-22 lf09 틱톡 예약을 취소한 직후 상태가 9로 바뀜, 취소 도구 출력과 상태 조회]

## 도구와 검증 상태(DONE=VERIFIED 기준, 증거 있는 것만 정본)

- **`tools/publish/post_verify.py`** (shorts-lab): 틱톡 영상별 존재 확인과 유튜브 예약 지남 점검. [실측: 2026-10-22 첫 실행 틱톡 16건 모두 VERIFIED, 문제 0건, 리포트 pilot-shorts2/게시확인_리포트.md]
- **`tools/publish/resched_all.py`**: 일정 변경 단일 명령. 사용 `python resched_all.py <편ID> "YYYY-MM-DD HH:MM" [--apply] [--only=...]`, `--apply` 없으면 계획만 보여 준다. [실측: lf09 틱톡으로 실제 실행해 새 예약 생성과 옛 예약 취소까지 통과, ep42로 계획 출력 확인]
- **기존 도구**: `yt_api.py`(upload, reschedule, list), `aitoearn_publish.py`(schedule, status, cancel), `topic_sheet_write.py`(시트 칸 쓰기), `playlist_fill.py`(롱폼 예약 직후 재생목록 채우기).
- **정본이 아닌 것**: `sched_align_check.py`는 일정 DB(최대 1시간 늦고 삭제된 영상이 남음)를 읽어 헛경보를 냈다. [실측: 2026-10-22 lf10s3·lf10s4가 유튜브 실시간 목록에 없는데 어긋남으로 나옴] 시트와 유튜브·AItoEarn 실시간 기준으로 다시 써야 해서 아직 쓰지 않는다.

## 새 편을 등록할 때 순서

1. 시트에서 그 편의 발행 날짜와 슬롯을 확인한다(발행 슬롯 감사).
2. 유튜브는 `yt_api.py upload`, 나머지 플랫폼은 `aitoearn_publish.py schedule`로 예약한다.
3. 롱폼은 바로 `playlist_fill.py`로 재생목록을 채운다.
4. 시트의 플랫폼별 예약 칸이 채워졌는지 읽어 확인한다.
5. 다음 날 `post_verify.py` 리포트(`pilot-shorts2/게시확인_리포트.md`)에서 문제가 없는지 본다.
6. 날짜가 바뀌면 직접 고치지 말고 `resched_all.py`를 쓴다.

## 마야가 쓰는 법

- 마야의 SNS 발행도 같은 이름과 원칙을 쓴다. 단일 원장은 [SNS_등록대장.md](SNS_등록대장.md)이고, 예약됨과 게시 확인됨을 나누고, 변경은 한 곳에서 한다.
- 도구 중 `post_verify.py`는 틱톡 영상용이라 마야 채널에는 그대로 쓸 수 없다. 원칙 1·2·4(원장 하나, 게시 확인, 하루 1회 점검과 한 채널 알림)부터 적용하고, 필요한 확인 수단은 마야가 핏에게 요청한다.
- 용어(예약됨, 게시 확인됨, 어긋남, 지연)를 같이 써서 보고가 서로 같은 말이 되게 한다.
