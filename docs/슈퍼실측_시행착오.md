# 슈퍼실측 시행착오 (참고자료, 정본 아님)

[슈퍼실측.md](슈퍼실측.md)의 규칙이 왜 생겼는지의 근거를 모은다. 성공한 순서는 정본에 있고, 여기는 "무슨 일이 있었고 무엇을 고쳤나"만 둔다. 사례는 카빗MCP 과제(2026-10-20~22, 노트)에서 나왔다. 새 사고가 나면 이 문서 끝에 한 항목씩 더한다.

## 기록을 찾지 않고 "남았다"고 보고

- 일: 남은 실측 목록을 올렸는데 북 노트북 설치, 앱 수신 방식 확정, 앱 칸 B가 이미 끝난 것이었다. 사장님이 세 번 정정하셨다.
- 원인: 마지막 정본 갱신이 10/21 중간 저장판이라 뒤처졌고, 그 표를 근거로 답했다. 공정 카드 전체를 다시 읽지 않았다.
- 고친 것: 정본 규칙 2번("기록부터 찾기")과 9번("마지막에 팩트체크")을 만들었다. 같은 세션에서 정본과 공정 카드를 함께 고친다.

## 근거 없는 수치

- 일: 앱 호출 프롬프팅의 소요 시간을 "약 10분 안쪽"으로 보고했는데 시작·종료 시각 캡처가 없었다.
- 고친 것: 철회하고 "미측정"으로 두었다. 규칙 5번(시각이 없는 시간 수치는 쓰지 않는다)이 여기서 나왔다.

## 설계·개발을 먼저 한 일

- 일: 전체 통신 방식에 대한 사장님 컨펌 없이 제품 저장소 개발 초안을 만들었다. 사장님이 지적하셨다.
- 고친 것: 초안은 로컬에 두고 푸시하지 않았다. 규칙 7번·8번(실측과 설계를 섞지 않는다, 구현 PR은 확인 뒤)이 여기서 나왔다. 이후 PyPI 게시용 PR은 사장님이 "진행하세요"라고 한 뒤에 올렸다.

## 같은 요청을 반복

- 일: 사장님이 이미 커넥터를 등록하셨는데 같은 추가 요청을 두 번 더 안내했다. 앞서 한 캡처 요청도 반복됐다.
- 원인: 사장님이 이미 한 일인지 먼저 확인하지 않고, 앞 답변의 순서를 그대로 이어서 썼다.
- 고친 것: 사장님께 부탁하기 전에 직전 캡처와 기록을 먼저 보고, 이미 있으면 "다음 단계만" 안내한다.

## 동료 에이전트의 전언을 결정으로 받아들일 뻔함

- 일: 탐이 "사장님 결정 2건"이라고 전한 작성자 이메일 변경과 메일 전달 기능을 그대로 진행할 뻔했다. 기록에는 사장님 직접 발언이 없었다.
- 고친 것: 직접 기록을 찾아 확인하고, 사장님께 한 줄로 확인받은 뒤 진행했다. 동료 세션의 "승인" 전언은 승인 근거로 쓰지 않는다.

## 조건을 한꺼번에 바꾼 시험이 원인을 가리지 못함

- 일: 앱에서 새 서버 도구가 안 보이는 증상(S2)을 처음에는 "같은 주소의 옛 커넥터" 때문이라고 추정했는데, 다시 재현하니 단일 커넥터에서는 나오지 않았다. 처음 관측은 커넥터 2개가 함께 있던 조건이었다.
- 고친 것: 한 번에 조건 하나만 바꾼다(규칙 4번). 원인을 확정하지 못한 채 닫을 때는 "부분 확인"과 한계를 정본에 그대로 적는다.

## 현실성이 낮은 경로에 시간을 씀

- 일: VS Code 확장에서 채널을 켜려고 실행 래퍼를 끼우는 시험을 했는데, 고객이 쓸 경로가 아니었다. 사장님이 "앱에서 터미널 세션을 띄우는 쪽이 더 현실적"이라고 지적하셨다.
- 고친 것: 실측할 경로를 고르기 전에 "고객이 실제로 쓰는 경로인가"를 먼저 묻는다.

## 상태가 어긋난 외부 화면

- 일: 설정 > 커넥터 목록이 기대와 달랐다. 지웠다고 했는데 남아 있었고, 지우지 않았는데 시험 커넥터가 사라졌다. 원인은 확인하지 못했다.
- 고친 것: 막힘 진단표에 "목록이 기대와 다름"(S8)을 후보로 올리고, 대체 경로(화면을 새로 고쳐 실제 목록 확인)를 적었다. 시험 전에는 화면 상태를 캡처로 먼저 확인한다.

## 한계

- 이 문서는 한 과제에서 겪은 일만 담았다. 다른 과제에서 나오는 시행착오는 같은 형식으로 더한다.
