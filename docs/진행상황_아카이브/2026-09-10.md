상태: 🟡주시

한 것: Claude Cloud → MCP Adapter 외부 연결 PoC의 인증 방식을 4단계로 나눠 조사·설계(Phase 5A~6A, 전부 리서치/설계 의견이고 실행은 없음). Phase 5A: Claude Custom Connector의 Remote MCP 요구사항(Streamable HTTP, OAuth vs static header) 1차 조사. Phase 5D: 사장님 계정 실제 Custom Connector UI에 static Bearer/OAuth Client ID·Secret 입력란이 **없다**는 실측을 받아 반영. Phase 6: 그 실측 기준으로 "Cloudflare Worker + `workers-oauth-provider`"(OAuth 2.1+DCR, Claude.ai 실사용 검증 사례 있음)를 1순위 아키텍처로 제안, Cloudflare Access는 정적 헤더/브라우저 세션 요구라 비호환으로 기각. Phase 6A: MCP 2025-11-25 스펙의 새 기본값 CIMD(Client ID Metadata Document, SEP-991, 사전 등록 없이 URL 자체가 client_id)까지 반영해 A(Adapter 자체 OAuth 구현)/B(Cloudflare Worker)/C(WorkOS·Stytch 같은 관리형 MCP-OAuth) 재비교, A는 "1인 회사가 감당하기엔 직접 짠 인가서버의 상시 보안 유지 부담이 큼"으로 배제, B/C는 Windows 쪽 기존 도메인 보유 여부에 따라 최종 선택하기로 보류.

막힌 것 / 비정상 상태: Windows 로컬 실측(Phase 5B `server.py` 인증코드 확인, Phase 6A `cloudflared` 설치·설정파일·기존 도메인·Adapter/Hermes 포트 상태)은 이번 세션에서도 전부 BLOCKED, `ListAgents`로 2회 재확인했지만 연결 가능한 Windows 로컬 세션 없음. 이전 세션(§37 이하)과 동일한 원인(원격 클라우드 세션엔 채널 자체가 없음, CLAUDE.md#b7f1)이라 새로운 조사는 안 하고 매번 확인만 반복. claude.com/support.claude.com/docs.anthropic.com/developers.cloudflare.com 등 주요 1차 문서 도메인이 이 세션 프록시에서 egress 차단돼 있어, 조사 근거가 platform.claude.com(API 문서)·github.com 이슈·WebSearch 스니펫(2차 출처) 위주였다는 점도 다음 세션이 알아야 함, UI 세부사항은 문서보다 사장님 실측이 더 정확했음(Phase 5D→6에서 실제로 뒤집힘).
