# 카빗MCP 합본 개발 스펙 (초안, 사장님 검토 전)

작성: 노트, 2026-10-22. 방식: [슈퍼실측.md](슈퍼실측.md) 7~8단계(실측과 설계를 합쳐 한 장으로). 근거 정본: [카빗MCP_과제_정본.md](카빗MCP_과제_정본.md).

**이 문서의 상태:** 실측은 끝났다(카빗DM 기술검증 백로그 완료, 공정 카드 노트-카빗MCP과제 #115). 아직 지투와 협의하지 않았고 구현도 시작하지 않았다. 사장님이 검토해 순서를 정한 뒤에 지투 협의로 넘어간다.

## 1. 목표와 대상

- 목표(사장님 10/20): 가입 직후 받은 프롬프트를 클로드 코드에 입력하면 통신하는 에이전트가 생긴다.
- 대상: 클로드 코드로 서비스를 만드는 스타트업 창업자와 팀.
- 흐름: 1단계 사용자가 카빗 MCP를 직접 설치(번들), 2단계 에이전트 호출 프롬프팅(페르소나 호출, 필수 문서 세팅, Help 안내).

## 2. 실측으로 확정된 사실 (스펙의 전제)

- 터미널: 설치·새 세션 호출·채널 수신이 실측으로 확인됐다.
- 앱: 설정 > 커넥터 추가, 설치 문장으로 설치(북 노트북), 새 세션 호출 프롬프팅이 확인됐다. 앱 세션 자체는 채널을 못 붙인다. 앱 터미널 탭에서 채널 세션을 따로 띄우면 즉시 깨어난다.
- 같은 세션에서는 새로 설치한 서버 도구가 로드되지 않는다. 새 세션이 필요하다.
- 같은 세션에서 계정 커넥터를 추가하면 기존 카빗 도구가 끊긴 사례가 있다(1회).
- 설치 직후 에이전트가 스스로 `agents`의 `me`를 확인하게 하면 5/5, 안 하면 2/5.
- 설치 배포 순서는 사장님이 정했다: uvx 한 줄(PyPI `carvit-autoreceive` 0.1.1, 게시 완료) → 플러그인 → zip 폴백. 섞어서 설치하지 않는다.
- 수신 방식은 사장님이 정했다: 세션이 열려 수신 확인이 되면 출근으로 보고 DM, 아니면 우편함 저장.
- 막힘 진단표 8행(정본 B4 절)이 있다. S2는 부분 확인, S4 재현 절차와 S8 원인은 미확정이다.

## 3. 요구사항 목록 (번호, 내용, 근거, 담당 후보)

설치 단계
- R1. 설치 전에 같은 주소의 계정 커넥터가 있는지 점검하거나 안내한다. 같은 세션에서 커넥터를 추가했다면 새 세션을 열게 한다. 근거: 시사점 1, S2 재현. 담당 후보: 안내 문구(지투), 서버 지침(노트).
- R2. 설치한 에이전트가 자기 신원을 `agents`의 `me`로 스스로 확인한다. 근거: 시사점 2(5/5 대 2/5). 담당: 서버 지침(노트).
- R3. 안내 문구를 "재시작 후 이어서"가 아니라 "새 세션을 연다"로 바꾼다. 근거: 시사점 3, 사장님 10/20 결정. 담당: 안내 문구(지투).
- R4. 환경 선택(앱·터미널·그 밖)에 따라 다른 설치 문장을 보여 준다. 근거: 클릭형 시안(10/22), 앱과 터미널 경로가 다름. 담당: 화면(지투).
- R5. 설치 문장 복사: 설치 코드는 가리고(••••) 보기 토글, 복사는 항상 전체, 복사 뒤 "복사됨"과 다음 행동 한 줄("새 세션을 열고 붙여넣으세요"). 근거: 시안, 가이드 UX_GUIDE_CARVIT. 담당: 화면(지투).
- R6. 막혔을 때 대체 경로: 진단표 8행을 사용자에게 보이는 증상 기준으로 안내한다(Help 챗봇은 보류이므로 우선 정적 안내). 근거: B4. 담당: 안내 문구(지투), 내용(노트).
- R7. 알림기 배포는 PyPI uvx 정본, 플러그인은 얇은 껍데기, zip은 폴백. 근거: 3종 실측과 사장님 결정(노트#104). 담당: 서버·패키지(노트).

호출 단계
- R8. 호출 프롬프트 복사 화면과, 첫 세션에서 사람이 입력하는 질문(MCP 승인, 폴더 신뢰, 최초 1회 "Pending approval")의 안내. 근거: 호출 프롬프팅 앱 실세션 1/1. 담당: 화면(지투).
- R9. 에이전트끼리 대화가 오갈 때 Help가 "여기서 확인하세요"라며 관전방(Agents 탭) 링크를 안내한다. 근거: 설계 항목(PR 2524). 담당: Help 안내 문구(지투).

통신 단계
- R10. 출근 판정: 세션이 열려 수신 확인(에이전트의 확인 또는 시스템 안의 설정)이 되면 DM으로, 아니면 우편함에 저장한다. 근거: 사장님 10/21 확정. 담당: 서버(노트), 구현 설계는 아래 4절.
- R11. 앱 상시 수신은 R10으로 갈음하고, 터미널 채널 사용은 안내로만 한다(앱 터미널 탭 채널 세션이 깨어남). 담당: 안내 문구(지투).
- R12. 설정 > 커넥터 목록이 기대와 다를 때 화면을 새로 고쳐 실제 목록을 확인하라는 안내(S8). 근거: 관측 2건. 담당: 안내 문구(지투).

## 4. 지투에게 물을 구현 설계 질문 (실측 뒤 협의할 것)

카빗DM 181로 보낸 세 가지(회신은 보류 상태)다.
1. 출근 신호: 무엇을 신호로 볼 것인가(`last_seen_at`, 읽힘 표시, 알림기 확인 중 무엇을 쓰나).
2. 판정 시간 설정: 몇 분 안이면 출근인가, 고객이 바꿀 수 있나.
3. 보낸 쪽 표시: 보내는 사람에게 상대가 출근인지 우편함으로 갔는지 어떻게 보여 주나.

정본의 다른 재료로 `act_as` 신원 전환과 세션 매핑이 있다. 질문 협의 때 함께 다룬다.

## 5. MCP 서브메뉴 구조 변경안

지투가 이미 올린 안이고 사장님이 홀드해 둔 상태다. 노트는 원문을 이 초안에 옮기지 않았다. 협의 때 지투의 원문을 이 스펙의 R4~R9와 맞춘다(화면 구조가 겹치는 부분만 조정).

## 6. 구현 순서 제안

1. 문구와 서버 지침으로 끝나는 것부터: R2, R3, R1(문구 부분), R11. 위험이 작고 바로 효과를 잴 수 있다.
2. 패키지 배포: R7(이미 PyPI 게시 완료, 플러그인 껍데기와 zip 폴백 정리).
3. 화면: R4, R5, R8, R9 (지투 시안, 노트 서버 연동).
4. 출근 판정 구현: R10 (서버 계산 가능 여부 확인이 선행).
5. 진단표 안내: R6, R12.

원칙: 각 단계는 구현 전에 사장님 확인을 받고, 구현 뒤 실제 환경에서 한 번 더 돌려 본다.

## 7. 사장님이 정하실 것

- 3절의 우선순위와 6절의 순서를 이대로 갈지.
- 5절의 서브메뉴 변경안을 이 스펙에 합칠지(합친다면 협의 때 지투 원문을 보고 조정).
- 4절의 질문 3가지를 지금 지투에게 보낼지(사장님 허용 뒤에만 보낸다).

## 8. 한계

- R4~R9는 화면 요구라 클릭형 시안(제품 밖)만 있고 실제 사용자 시험은 아직 없다.
- S2, S4, S8은 원인이 확정되지 않았다. R1과 R12의 안내는 관측 기준이다.
- 서브메뉴 변경안의 내용은 이 초안에 없다.
