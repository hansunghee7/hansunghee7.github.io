# 에이전틱 원칙: 사람은 필수 순간에만 개입한다 (2026-10-03 사장님 지시)

카빗 패스와 카빗 UX는 "에이전트가 다 하고 사람은 꼭 필요한 순간만"인 제품이다. 우리 운영도 같은 방식으로 한다. 정본 요약은 CLAUDE.md id:ag01, 이 문서는 근거와 점검 질문이다.

## 사람 개입이 허용되는 4종
- **외부 서비스 자격증명**: 최초 로그인·계정 비밀번호처럼 에이전트가 대신 입력하지 않는 것. **카빗 패스 PIN 입력은 여기에 넣지 않는다.** PIN은 없앨 개입이다(사장님 지시 2026-10-03). 일반 키는 일반 칸으로 PIN 없이, 중요 키는 승인으로 서랍을 여는 설계(대장 N116 2단계)가 목표다. PIN을 부탁해야 하는 상황은 그 설계의 개선 과제로 올리고 같은 답변에 `[PIN 개선 과제: N116]`를 단다(훅이 이 표시가 없으면 막는다).
- **비가역·돈 승인**: 되돌릴 수 없는 일, 중요 키(돈·관리자) 사용. 승인은 가능하면 휴대폰 한 번(텔레그램 승인).
- **제품·방향 결정**: 무엇을 만들지, 어디까지 줄지 같은 되돌리기 어려운 선택.
- **규칙상 에이전트 금지**: 계정 생성, 외부 발신, 결제 등 시스템 규칙이 막는 것.

## 핵심 한 점: 에이전트 자기 권한 설정의 변경 (사장님 정리 2026-10-04)

안전 검사의 허용 규칙처럼 **에이전트가 자기 권한 설정을 바꾸는 일은 규칙상 금지이고, 이것이 사람이 개입하는 가장 명확한 지점**이다. 사람은 이것만 클로드 코드 채팅창, 텔레그램 승인, 카빗 패스 전용 앱 승인 중 하나로 풀고, 나머지는 에이전트가 자동으로 수행한다.
- 같은 절차를 지나는 것: 허용 범위 추가, 허용 범위 취소(`revoke`)도 포함(줄이는 방향이어도 권한 범위 변경). 구현: 카빗 패스 금고(대장 N137) `perm_request`·`revoke`는 텔레그램 승인이 있어야 실행된다.
- 에이전트가 하는 것: 필요한 범위를 구체적으로 적어 요청(무엇을·어디까지·언제까지), 승인 결과를 기다림, 승인 대장(`pass.py approvals`)에 기록이 남음.
- 에이전트가 하지 않는 것: 설정 파일 편집, 허용 규칙을 사장님께 "넣어 달라"고 말로 요청해 흐름을 멈추는 것(승인 버튼 요청을 보내고 기다린다).
- 승인을 말(채팅)로만 하면 기록이 흩어지므로 공식 버튼(텔레그램 허용, 전용 앱 허용)과 승인 대장으로 옮기는 중이다(N137).

이 4종이 아니면 사장님께 "해 주세요"를 말하지 않는다. 그 대신 아래 질문을 순서대로 푼다.

## 사장님께 부탁하기 전 점검 질문
1. 스크립트·도구로 할 수 있나? (설치기, 점검기, 훅, 헤르메스, 브라우저 도구)
2. 지금 막힌 이유가 기술인가, 규칙인가? 기술이면 다른 경로를 만든다. 규칙이면 4종 중 어느 것인지 적는다.
3. 사장님이 이미 정했나? (`python scripts/ops/ledger_lint.py --find 키워드`, 대장, 지난 대화 검색)
4. 사람이 해야 하는 순간을 없애거나 줄이는 설계가 있나? (예: PIN 대신 승인 한 번, 알림 대신 자동 재시도)

## 4종이 아닌데 사장님을 부른 사례 (2026-10-03, 이후 점검 질문의 근거)
- **확장 새로고침**: 확장에 5분 자동 갱신(`checkUpdate`)이 이미 있었는데 새로고침을 부탁했다.
- **저장 확인**: 지투가 `pass.py list`로 직접 확인할 수 있는데 사장님 화면 확인을 요청했다.
- **이미 정한 백업 대책(B50)**: 10/2 결정이 대장에 있었는데 "선택 대기"로 다시 물었다.
- **일반 칸 채우기**: "PIN을 한 번 입력해 주세요"를 특별 요청으로 말했고, 같은 사고로 PIN 요청을 훅이 막도록 바꿨다. 실제로는 서랍을 여는 평소 행동에 동기화가 붙으면 되고, 요청이 있을 때만 알리면 된다.

## 제약은 결론이 아니라 설계 재료다 (사장님 지시 2026-10-04)
막힘을 만나면 질문의 모양을 바꾼다. "이건 사람이 해야 한다"(구태)가 아니라 "어떤 제품·기능이 이 단계를 없애나"(에이전틱)이다.
- 예 1: BotFather 토큰 교체는 에이전트가 못 한다 → 교체가 정말 필요한가? 아니었다(목표는 안전 보관) → 평문 토큰을 보호 저장소로 옮기고 Pass에 저장(완료).
- 예 2: 서랍 PIN → 일반 키는 일반 칸(PIN 없이, 완료), 중요 키는 승인 개봉 + 승인 중계 서비스(설계 중, 대장 N116).
- 예 3: 확장 새로고침 → 이미 있던 자동 갱신을 쓰면 된다.
- 점검 질문 한 줄: "사람을 부르는 대신, 이 단계를 없애는 기능을 오늘 만들 수 있는가?" 만들 수 있으면 만들고, 못 만들면 개선 과제로 올린다.

## 막힌 데서 끝나면 안 된다 (사장님 지시 2026-10-03)
"막혀서 못 했다, 사장님 결정 바란다"로 끝내는 것은 에이전틱이 아니다. 막히면 아래 순서로 해결 경로를 찾아 실제로 만든다.
1. **지금 있는 도구**: 스크립트, 훅, 헤르메스, 시험 환경, 다른 경로(예: 막힌 편집은 거부 이유를 기록하는 훅부터).
2. **카빗 패스**: 키 요청·승인·저장이 막힌 것(예: 서랍 PIN → 일반 칸, 중요 키 승인 개봉). **카빗 MCP**: 가이드 조회·인용·도구가 막힌 것.
3. **개선 과제 + 임시 우회**: 패스·MCP에 기능이 없으면 한계를 개선 과제로 올리고(패스 = 탐 N116, MCP·UX = 지투, 개발 = 노트) 그 사이에 쓸 우회로를 정한다.
4. **신규 서비스**: 기존 제품으로 풀 수 없고 반복되는 막힘이면 새 서비스를 설계한다. 기준은 "지금 1인 기준으로 충분한가"가 아니라 "팔리는 상품(심플리파이어 2.0)의 공정자산이 되는가".
사장님께는 막힘 자체가 아니라 3·4의 **제품·방향 결정**만 올린다. 관문: 답변에 막혔다는 말과 함께 멈춘다는 표현이 있으면 `[해결 경로: 패스|MCP|신규 서비스|우회|개선 과제]` 표시가 없을 때 Stop 훅이 막는다.

## 제약은 제품 개선으로 연결한다 (도그푸딩 루프, 사장님 지시 2026-10-03)
에이전트가 카빗 패스·카빗 MCP·카빗 UX를 쓰다가 사람 개입이 필요해졌다면, 그 지점이 곧 제품의 한계다. 부탁하고 끝내지 말고 개선 과제로 올린다.
- **어디로**: 카빗 패스 = 탐 대장 N116 칸. 카빗 MCP·UX 가이드 = 지투(제품 책임)에게 우편(R&R: MCP 피드백 채널은 지투). 개발 = 노트.
- **무엇을 적나**: ① 어디서 사람이 필요했나 ② 기술 때문인가 규칙 때문인가 ③ 없애는 설계 한 줄 ④ 다시 생기면 줄었는지 확인할 방법.
- **자동 기록**: `[사람 개입 필요: 사유]` 표시를 단 답변은 훅이 `C:/work/_ops/human_touch_log.jsonl`에 남긴다. 탐은 매주 이 기록에서 없앨 수 있는 개입을 골라 개선 과제로 만든다(프로세스표 0절).
- **옛 규칙 정리**: 에이전틱 원칙과 어긋나는 문구는 지우거나 `docs/CLAUDE_md_근거_이력.md`로 옮긴다. 2026-10-03에 튜터 원칙 3(컴맹 절차를 기본으로)을 좁히고, 다중 LLM 핸드오프 스킬의 "사장님이 직접 딥리서치 실행"을 폐기했다.

## 왜 자꾸 이렇게 되는가 (탐의 분석)
- 보고 형식 ④가 "끝에 사장님이 정하실 것 한 가지"를 매번 요구해 결정을 억지로 만들게 했다. 이제 "없음"이 정답일 수 있다(약속은 실행 증거 표지와 함께, CLAUDE#4e7b).
- "사장님이 직접 손을 대는 절차는 컴맹 기준으로"(CLAUDE.md 튜터 원칙 3)는 사장님께 시키는 방법만 가르치고, 시키지 않는 것이 먼저라는 말이 없었다.
- 원칙이 기억 파일 한 줄뿐이라 답변을 쓰는 순간에 작동하는 관문이 없었다(CLAUDE#4e7b).
