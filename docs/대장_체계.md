# 대장 체계 (크레딧 대장 + 데이터 수집 파이프 대장)

운영 DB(simplifier-ops-data)에 둔 두 대장의 사용법이다. 이 문서는 가리키기만 하고 **내용의 정본은 DB**다. 문서와 DB가 다르면 DB가 맞다. 표 정의는 `tools/db/credit_schema.sql`, `tools/db/pipeline_schema.sql`이고, 운영 DB 실행은 별도 승인 절차를 거친다(표가 없으면 도구가 "표 미생성: <sql 파일> 실행 필요"라고 알려 준다).

## 크레딧 대장: 돈과 한도가 얼마나 남았나

- 역할: 오픈라우터, GCP, 무료 크레딧, 구독, 호출 한도 같은 **유료·무료 잔액 전부**를 계정 단위로 적는다. 계정마다 종류(유료선불, 무료크레딧, 무료티어, 구독, 한도형, 플랫폼), 잔액과 단위, 만료일, 충전·리셋 규칙, 잔액 확인 방법과 명령, 계정 이메일, 워크스페이스 여부를 가진다.
- 사건 표(credit_events)에 충전, 차감, 리셋, 만료, 조정, 확인을 쌓는다. 잔액을 확인한 일도 사건이라 "언제 마지막으로 봤나"가 남는다.
- 뷰 두 개가 눈에 띄게 해 준다. 만료까지 남은 일수, 알림 기준 아래인지, 마지막 확인이 며칠 지났는지가 한 장에 나오고, **30일 안 만료, 잔액 부족, 확인이 72시간 넘게 낡은 것**만 따로 모아 본다.
- 키·결제번호는 어느 칸에도 넣지 않는다. 결제는 `billing_ref`에 참조 이름만, 자원은 `resource_id`에 식별자만 쓴다.

## 데이터 수집 파이프 대장: 데이터가 어디서 어떻게 들어오나

- 구조는 3단이다. **데이터 대장**(pipeline_ledgers, 수집 결과가 쌓이는 곳) 1개에 **수집 파이프**(data_pipelines, API·스크래핑·파일·구독·웹훅·이메일) 여러 개가 붙고, 파이프마다 **실행 기록**(pipeline_runs)이 쌓인다.
- 파이프마다 수집원, 담당, 일정, 엔진, 저장 위치, 인증 참조 이름(auth_ref), 신선도 기준 시간, 감시 id(watch_job_id), 수동 실행 방법, 한계, 약관 위험을 적는다.
- 신선도 기준은 파이프 값이 우선이고 없으면 소속 대장 값을 쓴다. 마지막 성공이 기준 시간을 넘기면 **stale**로 보인다. 계획·폐기 상태는 stale로 치지 않고, 한 번도 성공하지 못한 작동 건은 stale이다.
- 각 데이터 대장(예: SNS 수집, 지표 스냅샷)은 이 표의 같은 절차로 관리된다. 대장마다 갱신 방법을 따로 적지 않고 파이프 한 줄을 등록한다.

## 기존 대장과의 연결

- `resources`(자원 대장): 크레딧 계정의 `resource_id`가 가리키는 곳이다. 어떤 자원이 어느 크레딧 계정에서 과금되는지 이 열로 이어진다.
- `research_*`(리서치 체계): 리서치 실행의 `cost_krw`는 크레딧 차감 사건과 맞춰 본다. 제미나이 검색 키의 월 한도처럼 한도형 계정은 크레딧 대장에도 한 줄 둔다. 리서치 모듈이 수집 성격이면 수집 파이프에도 등록한다.
- `platform_quota`(플랫폼 한도): 매일 리셋되는 무료 한도는 크레딧 대장에서는 종류 `한도형`/`무료티어`, 단위 `calls`/`credits`/`minutes`로 적고, 세부 일일 수치는 platform_quota가 정본이다.
- 감시 대장(`scripts/ops/jobs.toml`, 상태판 `C:\work\_ops\STATUS.md`): 파이프의 `watch_job_id`가 감시 작업 id를 가리킨다. 감시는 "돌았나"를, 파이프 대장은 "무엇을 어디에 넣고 신선한가"를 맡는다.

## 새 수집 파이프라인 등록 표준 절차

1. 등록: `pipeline_db.py register <slug> --name ... --kind ... --source ... --owner ... --schedule ... --engine ... --destination ... --watch-job <id> --ledger <대장 slug>`. 상태는 `계획`으로 들어간다.
2. 감시 대장 등록: `scripts/ops/jobs.toml`에 같은 id로 올린다.
3. 지금 1회 실행하고 증거를 남긴다: 실행 뒤 `pipeline_db.py add-run <slug> --ok yes --rows <건수> --note "..."`. 실패하면 `--ok no`로 남기고 원인을 고친다.
4. 첫 자동 실행 확인: 예약된 시각에 스스로 돈 결과를 `status`로 보고, 두 번째 add-run(또는 감시 결과)이 찍혔는지 확인한다.
5. 대장 상태 갱신: `pipeline_db.py set-status <slug> 작동 --note "첫 자동 실행 확인"`. 3과 4의 증거 없이는 `작동`으로 올리지 않는다(DONE = VERIFIED).

## 명령 사용법 (PowerShell 기준)

- 크레딧: `python scripts/ops/credit_db.py status`(한 장), `expiring`(곧 만료·부족·낡은 것), `howto <slug>`(확인 방법·명령·이메일), `events <slug>`(사건 내역).
- 크레딧 기록: `add-event <slug> --kind 차감 --amount -3 --balance-after 97 --who 탐 --note "..."`은 사건을 넣으면서 계정 잔액과 확인 시각도 같이 고친다. 잔액만 확인했으면 `set-balance <slug> <값> --note "..."`, 상태는 `set-status <slug> <정상|주의|소진|만료|미확인> --note "..."`.
- 수집: `python scripts/ops/pipeline_db.py status`(대장별로 묶은 한 장), `stale`, `howto <slug>`, `ledgers`(대장 건강), `add-run`, `set-status`, `register`.
- 일괄 반영: `credit_db.py seed C:/work/_ops/credit_db`(seed_accounts.json, seed_events.json), `pipeline_db.py seed C:/work/_ops/pipeline_db`(seed_ledgers.json 먼저, seed_pipelines.json 나중). 같은 slug는 덮어쓴다.
- 안전: 모든 쓰기는 길이 제한과 비밀값 모양(키 접두어, 주소 속 키 인자) 거부 관문을 지난다. 접속은 `scripts/ops/opsdb.py`를 쓴다(키는 카빗 패스 금고가 넣어 준 것을 읽기만 한다).
