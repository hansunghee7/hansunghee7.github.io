## 0. 공통

- 새김(simplifier-saegim) 작업은 전용 worktree에서 하고, 자기 브랜치로 PR → CI 전부 통과 → 병합한다.
- 막혔다고 말하기 전에 해당 기록을 열람한다: 이 표, [AI_ROUTING_POLICY.md](AI_ROUTING_POLICY.md), [제미나이_키_정책.md](제미나이_키_정책.md), 노트·탐 프로세스표. 기록에 없으면 그 사실을 적고 이 표에 한 줄 추가한다.
- **오래 걸리는 작업은 시작하자마자 완료 확인 장치를 건다**(사장님 2026-10-05: 안 걸면 사장님이 확인하기 전까지 멈춰 있다). 구PC·SSH·nohup으로 띄운 작업은 이 세션의 백그라운드 작업이 아니라서 끝나도 알림이 오지 않는다. 띄운 직후 `Monitor`로 진행 파일을 읽는 반복 확인을 건다(예: 1분마다 완료 개수를 SSH로 읽어 늘 때마다 알리고, 목표 개수·정지 문구·프로세스 종료 때 끝낸다). 종료 조건에는 성공뿐 아니라 실패·정지·프로세스 사라짐도 넣는다. 걸지 않은 채 "돌고 있다"고 보고하지 않는다. 알림이 오면 이어서 할 일(자르기, 번호표 전송 등)을 바로 한다.
- **공용 main 폴더가 origin/main보다 뒤처져 있으면 그 폴더의 스크립트는 옛 버전이다**(2026-10-05: 옛 `ask_vertex.py`가 풀린 상한 전의 "한도 20회" 문구로 멈춤, 키 429가 아니었다). 스크립트는 `git fetch` 뒤 최신 origin/main 워크트리에서 돌린다. 시작할 때 `git status -sb`의 `behind N`을 본다.
- **예약 세션을 새로 만들면 첫 실행의 도구 승인은 사람이 한 번 해야 하고, 그동안 세션이 대기한다**(2026-10-05 `jitu-backlog-run`: 20:14 시작 뒤 Bash 두 번 호출하고 30분 넘게 활동 없음). 만든 직후 `run_scheduled_task`로 바로 한 번 돌려 승인 창이 뜨는지 보고, 사장님께는 세션 링크(`[제목](#세션id)`)를 준다. 앱의 "루틴" 목록에는 이 방식의 작업이 보이지 않았다(루틴 화면에서 만든 것만 보임). 첫 실행 결과가 나오기 전에는 완료로 치지 않는다(대장 N58).

## 1. 제미나이 API를 부르는 일 (조사·판단 보조·비전 시험)

기록된 규칙(AI_ROUTING_POLICY 모델 고르기·키 대여 행, 제미나이_키_정책):

- **분류·판정 보조·반복 호출·비전 시험은 `gemini-flash-lite-latest`**를 쓴다(무료 분당 15회·하루 500회). 호출 사이 5초를 띄운다.
- **일반 모델(`gemini-flash-latest` 이상)은 분당 5회·하루 20회뿐**이라 반복 호출에 쓰지 않는다. 조사·긴 생성을 한 번에 상세하게 묻는 데만 쓴다.
- 429가 나오면 순서대로: ① 가벼운 모델로 바꾸거나 한도가 풀릴 때까지 기다린다(분당 한도는 몇 초) ② 다른 담당(탐·핏·마야)에게 우편함으로 키 대여를 요청한다(승낙 없이 남의 키를 쓰지 않는다) ③ 검색이 필요한 조사는 `vertex_research.py --route auto`(무료 키 먼저, 막히면 Vertex) ④ 그래도 안 되면 멈추고 대장에 막힌 단계와 풀리는 조건을 적는다.
- 재시도 루프로 시간을 태우지 않는다: 호출마다 시간 제한(25초)을 걸고, 두세 번 실패하면 기록하고 다음으로 넘어간다.

2026-10-04 Logos PoC 사례(대조 결과): 처음 PoC가 일반 모델로 시작해 429(분당 5회)와 503에 걸렸다. 막힌 것이 아니라 위 "일반 모델은 반복 호출에 쓰지 않는다" 규칙을 어긴 것이었다. 경쟁 조사 단계의 429도 같은 이유다. 고친 것: 반복 단계는 flash-lite로, 호출 사이 5초, 시간 제한 25초.
