### [지적 1] 로컬 CLI 파일 자동 수집에 따른 비밀값 노출 경로 미통제

### [지적 2] 무료 엔진의 '판정 금지' 원칙과 비티(Gemini) 역할 정의 간의 내부 기준 충돌

- **심각도**: **중간**
- **지적 내용**: 비티 역시 Gemini 엔진 기반이며 '보안/설계 검토(판정 성격)'를 수행하고 있습니다. '무료 엔진은 판정하지 않는다'는 원칙을 문자 그대로 두면 비티의 검증 역할과 충돌합니다. 비티의 검토는 '최종 합격/불합격의 주관적 재단'이 아니라 **'반증 가능한 근거 제시 및 실측 측정(Verification)'**임을 명확히 구분하지 않으면, 덱스 도입 시에도 "어디까지가 초안이고 어디서부터가 판정인가"에 대한 경계 혼선이 발생합니다.
- **고치는 방법 한 줄**: "무료 엔진은 가치 판단·최종 승인을 하지 않고, 반증 가능한 사실 측정과 코드 초안 작성만 담당한다"로 문구를 정밀화해야 합니다.

### [지적 3] '코드 작성 독점' 전제와 덱스 도입 목적의 모순
- **해당 위치**: `## 이미 있는 것과 겹침` - *"코드 작성·수정은 클로드(노트 등)가 한다."*

*   **왜 비티와 다른가?**: 비티가 코드를 대량 생산하면 '자기 감사(Self-audit)의 오류'가 생깁니다. 덱스가 작성한 코드를 비티가 독립 검증함으로써 '작성자 ≠ 검증자' 원칙이 성립합니다.
*   **호출 및 권한 방식**:

    *   **권한 범위**: 특정 대상 디렉토리 하위 쓰기만 허용, 네트워크 아웃바운드 차단(로컬 실행만), `.env` 및 시크릿 경로 상위 탐색 절대 금지.

### (3) 탐 세션 토큰이 가장 많이 줄어드는 작업 유형

> **1순위: "테스트 실패 / 린트 에러 기반의 로컬 자가수정(Self-healing) 루프"**

*   **현재 탐의 토큰 낭비 구조**:
    1. 코드 실행 후 300줄짜리 파이썬 트레이스백이나 크롬 확장 컴파일 에러 발생.
    2. 이를 탐 세션에 붙여넣음 (입력 토큰 수천 개 소비).
    3. 탐이 수정 코드를 전체 출력함 (출력 토큰 소비).
    4. 다시 돌렸는데 사소한 오타로 또 실패 → 탐 세션에서 3~4턴 반복 시 수만~수십만 토큰 소진.
*   **덱스 이관 시 절감 효과**:
    *   로컬 터미널에서 `codex "pytest 실패 로그를 보고 test_*.py를 통과하도록 수정해"`라고 덱스에게 로컬 수렴 루프를 전담시킵니다.
    *   덱스가 무료 쿼터 안에서 수정과 로컬 테스트를 자체 반복한 뒤, 성공한 **최종 `git diff` 요약(수십 줄)**만 탐에게 전달합니다.
    *   **결과**: 탐 세션의 멀티턴 토큰 낭비가 90% 이상 제거됩니다.

### (4) 도입하지 않는 편이 나은 경우 (중단 기준)

1.  **데이터 학습 제외(Zero Data Retention / Opt-out) 검증 실패 시**:
    무료 계정 조건상 소스코드의 OpenAI 학습 제외 설정이 불가능하거나 실측으로 입증되지 않는다면 즉시 폐기해야 합니다.
2.  **무료 쿼터의 빈번한 쿨다운으로 작업 흐름이 단절될 때**:
    5시간당 작업 허용량이 3~5회 수준에 불과하여 에러 해결 도중 세션이 멈추고 탐이 개입해야 한다면, 도구 유지보수 비용이 이득을 초과합니다(규모 최적화 원칙 위배).
3.  **헤르메스(로컬 4090)로 동일 수준의 코드 수정이 가능해질 때**:
    외부 클라우드 의존성(OpenAI)을 하나 더 늘리는 것 자체가 1인 회사 시스템 복잡도를 가중시킵니다.

### (5) 첫 시험 과제 1개 및 합격 기준 (DONE = VERIFIED)

*   **선정 이유**: 상용 서비스(Carvit Pass) 핵심 금고 코드가 아니면서, 외부 API 호출 및 에러 핸들링이 명확하여 덱스의 로컬 코드 수정 역량을 안전하게 실측 가능.
*   **실행 방식**:
