## 1. 검토 대상 텍스트에 대한 보안·설계 지적

### [지적 1] 주기 작업 20여 개의 LLM 업무대장 상주로 인한 컨텍스트 오염
- **대상 절·문장**: `## 현재 부하` - *"인프라·자동화·감시(주기 작업 20여 개)..."*
- **심각도**: **높음**
- **문제점**: 상태가 정기적으로 변하거나 확인이 필요한 20여 개 주기 작업을 LLM 허브(탐)의 업무대장에 올려두면, 매 세션 인수인계 문서가 비대해지고 세션 리셋마다 수만 토큰이 상태 확인에 낭비됩니다. 모니터링은 LLM이 폴링하는 것이 아니라, 이상 발생 시에만 신호를 쏘는 이벤트 드리븐이어야 합니다.
- **고치는 방법 한 줄**: 주기 작업 20여 개를 업무대장에서 전면 제외하고, 실패 시에만 텔레그램으로 핑을 쏘는 OS 레벨 cron/systemd 알림 스크립트로 분리합니다.

### [지적 2] 진행(WIP) 16건 방치 상태에서의 스쿼드 도입 역효과
- **대상 절·문장**: `## 현재 부하` - *"탐(CTO 허브)의 업무대장 항목이 46건: 진행 16, 보류 14..."*
- **심각도**: **높음**
- **문제점**: 1인 회사 + 1허브 체제에서 동시 진행(WIP) 16건은 심각한 컨텍스트 스위칭 부하를 유발합니다. 이 상태에서 병렬 스쿼드를 도입하면 각 에이전트의 작업 맥락을 유지·스위칭하느라 코디네이터(탐)의 컨텍스트 소진 속도가 기하급수적으로 빨라집니다.
- **고치는 방법 한 줄**: 허브 세션의 동시 진행(WIP) 상한을 최대 3건으로 강제 캡핑(WIP Limit)하고 나머지는 전부 '대기' 큐로 동결합니다.

### [지적 3] 병렬 작업 시 파일 충돌 방지책의 물리적 격리 미비
- **대상 절·문장**: `## 이미 있는 분산 수단` - *"같은 파일을 여러 세션이 동시에 고치면 충돌 해소는 사람 몫이라 영역을 나눈다."*
- **심각도**: **중간**
- **문제점**: 에이전트 간 "영역을 나눈다"는 논리적 규칙만으로는 작업 중인 로컬 git index, 임시 파일, 번들 빌드 아티팩트의 동시 쓰기 레이스 컨디션(Race Condition)을 차단할 수 없습니다.
- **고치는 방법 한 줄**: 병렬 에이전트마다 별도의 `git worktree` 또는 격리된 디렉토리를 물리적으로 강제 할당합니다.

### [지적 4] 병렬 서브에이전트 확장에 따른 보안 공격 표면 증가
- **대상 절·문장**: `## 이미 있는 분산 수단` - *"규칙: 서브에이전트에 더 높은 등급을 주지 않는다. 판정·최종 결정은 부모."*
- **심각도**: **중간 (가설)**
- **문제점**: 서브에이전트가 부모와 동등하거나 유사한 CLI 실행 권한을 가진 채 독립 병렬 동작할 경우, 외부 입력(웹 캡처, 외부 패키지 분석 등) 처리 중 프롬프트 인젝션이나 오작동 시 시스템 변조·자격증명 노출 위험이 N배로 증가합니다.
- **고치는 방법 한 줄**: 병렬 서브에이전트는 쓰기 및 시크릿 접근이 원천 박탈된 Read-Only 샌드박스로 격리하고, 수정 권한은 검증된 1개 실행 에이전트에만 부여합니다.

## 2. 사장님 구상(유사 서브에이전트 스쿼드 + 탐 코디네이션)의 실효성 평가

**결론: 현재 상태에서의 '전면적 동종 스쿼드 병렬화'는 비효과적이며 비용과 실수를 폭증시킵니다.**

- **실효성이 떨어지는 이유**:
  1. **팬인 병목(Context Fan-in Bottleneck)**: 탐의 병목은 '코딩 타자 속도'가 아니라 '컨텍스트 포화'입니다. 서브에이전트 3~4개가 병렬로 작성한 자연어 보고서나 코드를 읽고 판정하는 순간, 탐은 호출 몇 번 만에 20만 토큰 한도에 도달합니다(오히려 직접 짤 때보다 입출력 토큰 소비가 2~3배 커짐).
  2. **1인 회사의 규모 최적화 위배**: 독립 에이전트 간 조율(Orchestration) 오버헤드는 작업자가 많을 때 가치가 생깁니다. 1인 개발사 환경에서는 '조율자 LLM'이 '일하는 LLM'을 감독하는 옥상옥 구조가 되어 토큰 비용 대비 산출물이 급감합니다.

## 3. 효과적인 역할 분할 및 코디네이션 아키텍처 (어떻게 나눠야 하는가)

'유사한 동종 에이전트 병렬'이 아니라 **'기능별 비대칭 파이프라인'**으로 나눠야 합니다.

### ① 분할 기준
- **비동기 Read-Only (서브에이전트 위임)**: 코드 탐색, 레퍼런스 분석, 테스트 실패 로그 원인 분석, 보안 정적 분석.
- **결정론적 작업 (스크립트/크론 위임)**: 빌드, 배포, 20여 개 주기 감시, 정기 백업 (LLM 배제).
- **판단 및 쓰기 (탐 허브 전담)**: 아키텍처 결정, 사장님 보고, 승인된 코드 머지.

### ② 코디네이터(탐)가 하는 일 vs 하지 않는 일
- **하는 일 (Gatekeeper)**:
  - 명확한 완료 조건(AC, Acceptance Criteria)과 입력 파일 경로만 담긴 단문 작업 지시서 작성.
  - 실행 브랜치(Git worktree) 생성 및 작업 완료 후 `git diff` 및 테스트 결과(Exit Code) 확인 후 머지.
  - 사장님 의사결정 필요 사항(자격증명, 데이터 삭제, 배포) 필터링 및 승인 상신.
- **하지 않는 일 (엄격 금지)**:
  - 서브에이전트의 중간 과정 중계 및 장문 자연어 보고서 읽기 (JSON 또는 Diff만 수신).
  - 서브에이전트 간의 갈등이나 의존성 실시간 중재 (의존성이 있으면 애초에 병렬 분할 금지).
  - 정상 동작 중인 주기 작업 상태 확인 및 기록.

### ③ 결과 통합·충돌 방지·검증 방법
- **충돌 방지**: Git Worktree로 물리적 디렉토리 격리 (`git worktree add ../agent-task-A`).
- **결과 통합**: 에이전트는 자연어 보고 금지, 오직 **`output.json` + `patch.diff`**만 생성하고 종료.
- **검증 (DONE = VERIFIED)**: 탐이 눈으로 읽어 검증하지 않고, 워크트리 내 자동화 테스트 스크립트 실행 결과(`exit 0`)로만 검증.

## 4. 비용과 실수가 늘어 병렬화를 '절대 하지 말아야 할 경우'

1. **작업 간 상태/데이터 의존성이 있는 경우**: A 작업의 결과가 B 작업의 입력이 되는 파이프라인을 병렬로 띄우면 레이스 컨디션과 환각이 발생합니다.
2. **요구사항이나 종료 조건(AC)이 모호한 경우**: "Carvit Pass UI 개선해줘"처럼 열린 질문을 서브에이전트에 던지면, 엉뚱한 방향으로 수만 토큰을 태우고 탐이 이를 원복하느라 세션을 날립니다.
3. **공통 설정 파일(`manifest.json`, `package.json`, 환경변수)을 수정해야 하는 경우**: 병렬 세션이 동일한 메타 설정을 건드리면 충돌 해소 비용이 개발 비용보다 커집니다.

## 6. 탐의 컨텍스트를 가장 많이 줄이는 떼어내기 1순위 (업무대장 46건 분석)

**떼어내기 1순위: [인프라·자동화·감시(주기 작업 20여 개)]의 탈(脫)-LLM 분리**

- **근거**:
  - 46건 중 **20건(약 43%)**이 주기 작업입니다.
  - 이 20건은 창의적 판단이 필요 없는 결정론적 반복 작업인데도 탐의 대장에 올라있어 인수인계 파일 용량을 절반 가까이 차지하고 세션 컨텍스트를 오염시킵니다.
- **해결 방안**:
  - 탐의 대장에서 즉시 20건 삭제.
  - 리눅스 cron / Windows 스케줄러 + bash/python 스크립트로 완전 이관.
  - **Fail-only 알림**: 정상일 때는 침묵하고, 에러 코드 발생 시에만 `notify.py`로 텔레그램 발송.
  - **효과**: 탐의 업무대장 즉시 **46건 -> 26건으로 축소**, 세션 내 불필요한 상태 확인 호출 0회로 감소.

## 7. 첫 시험 1건과 합격 기준

### [시험 과제] 독립 정적 분석 & 린트 패치 에이전트 1회성 시험
- **과제 내용**: Carvit Pass의 취약점 및 코드 스타일 검사를 위해, `sidepanel.js` 또는 `vault.js` 대상의 ESLint/보안 정적 분석 및 자동 수정 패치 생성을 별도 격리 세션(또는 서브에이전트)에 위임.
- **작업 방식**:
  1. 탐은 해당 세션에 파일 경로와 린트 룰만 전달하고 대화 중단.
  2. 에이전트는 별도 `git worktree`에서 린트를 돌리고 수정 diff(`patch.diff`)와 결과 요약 JSON만 생성.
  3. 탐은 JSON의 에러 건수와 `git apply --check`만 실행하여 검증.
