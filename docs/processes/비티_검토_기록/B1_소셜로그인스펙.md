### 1. [높음] GitHub 다중 이메일 매칭에 따른 타인 계정 탈취 및 식별자 충돌 위험
- **대상 절·문장**: `## 계정 처리 규칙` > *"GitHub 이메일: 확인된 이메일 중 하나라도 기존 계정이거나 승인 도메인이면 통과한다"* 및 *"기존 이메일 계정과 연결: 같은 확인된 이메일이면 같은 계정(같은 회사·같은 데이터)으로 들어간다."*
- **문제점**: GitHub 계정은 복수의 보조 이메일(Secondary Emails)을 등록·인증할 수 있습니다. 사용자의 GitHub 계정에 `[개인메일(A), 회사메일(B)]`가 모두 등록되어 있을 때, 스펙대로 "하나라도 승인 도메인이면 통과"시키면 계정의 기본 고유 식별자(PK)로 A와 B 중 무엇을 쓸지 정의되지 않아 충돌이 발생합니다. 특히 타인의 업무 이메일이나 퇴사자 이메일이 과거에 보조 이메일로 묶여 있던 GitHub 계정으로 로그인할 경우, 기존 타인 계정의 데이터로 직결되는 심각한 계정 탈취가 발생할 수 있습니다.
- **고치는 방법 한 줄**: GitHub 다중 이메일 중 승인 도메인과 정확히 일치하는 단일 업무 이메일만 명시적으로 선택·추출하여 계정에 매핑하고, 다중 매칭 시 자동 병합을 금지해야 합니다.

### 2. [높음] OAuth `state` 매개변수 및 PKCE 검증 누락으로 인한 로그인 CSRF(Account Injection)
- **대상 절·문장**: `## 사용자가 보는 흐름` > *"3. 소셜 로그인이 끝나면 누른 탭으로 돌아간다(없으면 대시보드)."* 및 `## 먼저 필요한 설정` > *"WorkOS 운영 환경과 Google·GitHub 소셜 연결"*
- **문제점**: 스펙에 OAuth 플로우 시 CSRF 방지를 위한 `state` 매개변수 생성 및 검증 절차가 완전히 빠져 있습니다. 공격자가 자신의 계정으로 소셜 로그인을 진행하다가 가로챈 인가 코드(Authorization Code)가 담긴 콜백 URL을 피해자가 실행하도록 유도하면, 피해자의 브라우저 세션이 공격자의 계정으로 강제 바인딩(OAuth Login CSRF)되어 피해자의 활동 데이터가 공격자에게 노출됩니다.
- **고치는 방법 한 줄**: 소셜 로그인 요청 시 암호학적 1회용 `state` 난수를 세션/쿠키에 바인딩하고, 콜백 검증 시 일치 여부를 확인 후 즉시 폐기해야 합니다.

### 3. [높음] `next` 매개변수 검증 부재로 인한 오픈 리다이렉트(Open Redirect) 및 인증 정보 탈취
- **대상 절·문장**: `## 사용자가 보는 흐름` > *"1. ... 누른 탭 주소를 기억한다(next)."* 및 *"3. 소셜 로그인이 끝나면 누른 탭으로 돌아간다(없으면 대시보드)."*
- **문제점**: `next` 파라미터에 대한 화이트리스트나 도메인 검증 규칙이 없습니다. 공격자가 `/login?next=https://attacker.com` 형태의 링크를 유포할 경우 로그인 완료 즉시 악성 외부 사이트로 리다이렉트되며, 브라우저 주소창 신뢰를 이용한 피싱이나 세션 토큰 탈취로 이어질 수 있습니다.
- **고치는 방법 한 줄**: `next` 파라미터는 슬래시(`/`)로 시작하는 내부 상대 경로(`/dashboard`, `/guide`, `/connect`)만 허용하고 외부 도메인 및 `//` 스킴은 차단해야 합니다.

### 4. [중간] 자동 계정 연결(Auto-linking) 시 재인증 부재로 인한 계정 탈취(Pre-Account Takeover)
- **대상 절·문장**: `## 계정 처리 규칙` > *"기존 이메일 계정과 연결: 같은 확인된 이메일이면 같은 계정(같은 회사·같은 데이터)으로 들어간다. 이메일이 같은데 소셜만 다르면(구글과 깃허브) 같은 계정에 묶인다."*
- **문제점**: 기존 이메일 기반 계정과 소셜 계정을 이메일 주소 일치만으로 무조건 자동 연결(Auto-linking)하고 있습니다. IdP 간 이메일 검증 신뢰 수준의 차이가 있거나, 기존 계정이 이메일 링크 인증 전 생성된 레코드일 경우, 공격자가 해당 이메일로 생성한 소셜 계정을 통해 기존 사용자의 회사 데이터에 즉시 무단 접근할 수 있습니다.
- **고치는 방법 한 줄**: 기존 계정과 소셜 계정의 최초 연결 시에는 기존 인증 수단(기존 등록 이메일로의 링크 확인 또는 비밀키 입력)을 통한 1회 재인증을 거치도록 설계해야 합니다.

### 5. [중간] 세션 고정(Session Fixation) 및 서버 측 세션 즉시 무효화 부재로 인한 재생 공격
- **대상 절·문장**: `## 사용자가 보는 흐름` > *"5. 로그아웃은 머리의 로그아웃 버튼 한 번(확인 창 없음). 세션 유효 기간은 노트가 정하되 기본 7일, 로그아웃하면 즉시 끝."*
- **문제점**: 
  1) 로그인 전(익명 세션 또는 기존 2시간 보기 전용 세션)의 세션 식별자가 소셜 로그인 완료 후 재발급(Regenerate)되지 않으면 Session Fixation 공격에 노출됩니다.
  2) 로그아웃 시 클라이언트 쿠키만 지우고 서버 측 세션 저장소나 WorkOS 세션 토큰을 즉시 폐기(Revoke)하지 않을 경우, 탈취된 세션 토큰이 7일 만료 시점까지 그대로 유효하게 재사용(Replay)될 수 있습니다.
- **고치는 방법 한 줄**: 로그인 성공 시 세션 ID를 반드시 새로 갱신(Regenerate)하고, 로그아웃 호출 시 서버 측 세션 저장소 및 IdP 토큰을 즉시 블랙리스트/폐기 처리해야 합니다.

### 6. [중간] [가설] 기존 `/recover` 공용 백엔드 핸들러에 의한 Claude Code MCP 비밀키 파괴
- **대상 절·문장**: `## 지금 상태 (코드 확인)` > *"/login의 메일 링크는 /recover/confirm을 그대로 가리켜 로그인이 비밀키 재발급으로 이어진다"* 및 `## 사용자가 보는 흐름` > *"4. 로그인은 비밀키를 건드리지 않는다. 기존 비밀키, Claude Code 연결은 그대로다. 비밀키 재발급은 /recover에서만..."*
- **문제점**: [가설] 현재 `/login`이 `/recover/confirm`으로 가던 구조상, 백엔드 내부 사용자 조회/처리 로직이 `issue_or_recover_key`와 같은 비밀키 갱신 함수에 강하게 결합되어 있을 가능성이 높습니다. 소셜 로그인 사용자 조회 로직에서 이를 완전히 분리하지 않고 신규/기존 계정 초기화 루틴을 공용으로 타게 되면, 소셜 로그인 시점에 기존 사용자의 `secret_key`가 덮어씌워져 사장님의 Claude Code MCP 연결이 즉시 단절될 위험이 있습니다.
- **고치는 방법 한 줄**: 소셜 로그인 인증 핸들러는 계정 조회(Read-only)만 수행하도록 구현하고, 비밀키 발급/갱신 DB 로직은 `/recover` 엔드포인트 전용 트랜잭션으로 물리적 분리해야 합니다.

### 7. [낮음] [가설] 이메일 대소문자 미정규화로 인한 승인 우회 또는 중복 계정 파편화
- **대상 절·문장**: `## 계정 처리 규칙` > *"처음 로그인: 소셜 계정의 확인된(verified) 이메일로 승인 회사 도메인을 찾는다."* 및 *"기존 이메일 계정과 연결: 같은 확인된 이메일이면 같은 계정...으로 들어간다."*
- **문제점**: [가설] IdP에서 전달된 이메일 문자열(예: `User@simplifier.co.kr`)을 소문자로 정규화(lowercase)하지 않고 DB 조회 및 `company_for_domain` 검증에 넘기면, 동일한 사용자임에도 기존 계정 매핑에 실패하여 중복 계정이 생기거나 도메인 매칭 로직의 대소문자 불일치로 승인이 오차단될 수 있습니다.
- **고치는 방법 한 줄**: IdP로부터 이메일을 수신하는 즉시 `email.strip().lower()`로 정규화한 뒤 도메인 승인 검사 및 DB 조회를 수행해야 합니다.
