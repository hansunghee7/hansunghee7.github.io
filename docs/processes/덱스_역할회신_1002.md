## 덱스 답 원문

## 1) 우리 팀에서 맡기기 좋은 역할

**알고 있는 것:** Codex는 Free 플랜에서도 사용할 수 있지만, 한도는 플랜과 작업의 복잡도·길이 등에 따라 달라집니다. 공식 안내에는 이 조건에서 쓸 수 있는 정확한 횟수나 토큰 수가 없습니다. [Codex 사용 안내](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan)

**맡기기 좋은 일 3가지**

1. **작고 범위가 분명한 코드 수정** — 실측상 미사용 import 수정은 30초에 통과했습니다. 파일·증상·완료 기준이 뚜렷한 버그 수정에 맞습니다.
2. **원인 후보와 재현 경로 찾기** — 표준입력 핸들 상속 문제처럼 실패 테스트의 원인을 좁히고, 주변의 거짓 경고 버그까지 찾은 사례가 있습니다. 최종 판정은 클로드 본 세션에 넘깁니다.
3. **독립적인 코드 검토와 diff 제안** — 운영 스크립트나 작은 변경을 살펴 누락·부작용을 짚고, 적용 가능한 diff와 종료 코드로 넘깁니다.

**맡기지 않는 게 좋은 일 2가지**

1. **최종 통과·반려 판정** — 팀 원칙상 판정은 클로드 본 세션의 몫이며, 2차 시험에서도 Codex가 샌드박스 제약으로 최종 통과를 직접 확인하지 못했습니다.
2. **임시 경로·git 내부 경로에 의존하는 작업, 또는 push·PR·병합** — 현재 윈도우 샌드박스에서 해당 경로 접근이 막혀 있고, 배포 흐름은 탐이 담당합니다.

## 2) 호출 방식

아래 수치는 **[추측]**입니다. 계정별 한도는 확인할 수 없으므로, 한도를 다 쓰지 않도록 시작은 보수적으로 잡는 편이 좋습니다.

- **[추측] 하루 1~2회, 주 5~8회 정도**로 시작하고, 사용량 화면이나 CLI의 `/status`에서 잔여량·재설정 시점을 살핍니다. 공식 안내도 한도 확인 경로로 사용량 화면과 `/status`를 안내합니다.
- **[추측] 한 번에 1개 이슈, 수정 파일 1~3개, 요청문 500자 안팎**으로 제한합니다. 재현 절차, 기대 동작, 검증 명령, 건드리지 말 범위를 함께 줍니다.
- **[추측] 같은 원인과 같은 완료 기준을 공유하는 수정·관련 테스트는 한 작업으로 묶고, 독립적인 이슈는 나눕니다.** 시험 사례처럼 한 작업이 2라운드로 길어질 수 있으니, 첫 요청에 범위와 중단 조건을 적어 불필요한 반복을 줄입니다.

## 3) 샌드박스 때문에 검증이 끝나지 않을 때

Codex는 접근 가능한 범위에서 수정과 검증을 하고, 막힌 경로와 실행 결과를 diff·종료 코드에 명시합니다. 탐은 그 diff를 재검사한 뒤, 임시 경로나 git 하위 경로가 필요한 최종 명령과 테스트를 실행합니다. 결과를 클로드 본 세션에 전달해 통과·반려를 판정받습니다. Codex의 자체 검증 성공과 팀의 최종 통과 판정을 구분하면 됩니다.

## 4) 실패·한도 도달 신호

탐은 종료 코드만으로 성공을 추정하지 말고, **diff가 있는지, 요청한 검증이 실제 실행됐는지, 종료 코드가 무엇인지** 함께 확인해야 합니다. 실패 원인이나 막힌 경로가 결과에 적혀 있는지도 봅니다. 한도에 닿으면 CLI 또는 화면의 한도 안내와 재설정 시점을 확인합니다. 공식 안내에 따르면 한도는 사용량 화면에서 확인할 수 있고, 활성 CLI 세션에서는 `/status`를 사용할 수 있습니다.
