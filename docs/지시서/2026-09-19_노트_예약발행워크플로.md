# 지시서: 예약 발행 워크플로 개발 (노트, 2026-09-19)

발주: 마야 (사장님 지시). 담당: 노트(개발 서브에이전트). 실행과 검증은 헤르메스에게 위임한다.
판정: 마야가 원문 증거를 보고 통과/반려를 정한다.

## 목적

글이 날짜에 맞춰 자동으로 공개되게 한다. 지금은 `published: true`로 바꿔 main에 병합해야만 공개되고, `date` 필드는 표시 날짜일 뿐 공개를 막지도 열지도 않는다(2026-09-19 CMS 설정 `admin/config.yml`과 스크립트로 확인). 주 4회 발행을 매번 수동 병합하지 않도록 자동화한다.

## 배경 (알아야 할 것)

- 글은 `log_assets/markdown/*.md`이고 front matter의 `published`가 공개 여부다. false는 초안이라 사이트에 안 나오고, true로 main에 병합되면 즉시 라이브에 나온다.
- main 병합은 PR과 auto-merge(squash)로 한다. 세션은 main에 직접 push하지 않는다. 예외로 github-actions 봇의 자동화 커밋은 PR 없이 main에 들어간다.
- `.github/workflows/publish-pipeline.yml`은 main에서 `log_assets/markdown/**`이 바뀌면 순번, 카드, posts.json, sitemap을 자동 갱신한다.
- 주의: GITHUB_TOKEN으로 한 push는 다른 워크플로의 `on: push`를 발화시키지 않는다. 다른 자동화 워크플로(fetch-*, sync-*)가 이를 어떻게 처리하는지 먼저 읽고 같은 방식을 따른다.

## 요구사항 (더 나은 안이 있으면 근거와 함께 보고)

1. 선택 필드 `publish_at: 2026-09-24T10:00:00+09:00`(ISO 8601, 한국시간 기준 해석)을 도입한다.
2. 대상: `published: false`이고 `publish_at`이 있고 현재 시각이 `publish_at` 이상인 글. 그 글의 `published`를 `true`로 바꾼다. `publish_at` 줄은 지우지 않고 기록용으로 남긴다.
3. 안전장치(중요)
   - `publish_at`이 없는 글은 절대 건드리지 않는다. 사장님이 컨펌하지 않은 초안은 false로 남아야 한다.
   - `published: true`인 글은 건드리지 않는다. 멱등이어야 한다(두 번 돌려도 같은 결과).
   - front matter 외 본문은 한 글자도 바꾸지 않고, 줄바꿈(CRLF/LF)을 보존한다.
   - `publish_at` 형식이 잘못된 글은 건너뛰고 이유를 로그에 남긴다. 워크플로 전체를 실패시키지 않는다(다른 글 발행을 막지 않게). 잘못된 형식이 있었다는 요약은 남긴다.
   - `dry_run` 입력(workflow_dispatch, 기본값 true)이 있어 dry_run이면 바꿀 목록만 출력하고 커밋하지 않는다. 스케줄(cron) 실행은 dry_run=false로 동작한다.
4. 실행: GitHub Actions 스케줄 워크플로(15분 간격 정도). GitHub cron은 지연될 수 있으므로 "정확한 시각"이 아니라 "publish_at 이후 첫 실행에 발행"임을 문서에 밝힌다. 시간대는 Asia/Seoul 기준으로 정확히 처리한다(러너는 UTC).
5. 스크립트는 Python(`scripts/` 아래, 표준 라이브러리 위주), 워크플로는 `.github/workflows/scheduled-publish.yml`.
6. 발행 커밋이 main에 들어간 뒤 기존 publish-pipeline이 이어서 도는지 확인하고, 그 연결 방식을 보고한다.
7. 인프라 변경이므로 `insight-7b3e9f2c/system-map.html`의 요약 숫자와 관련 표를 같은 PR에서 갱신한다. 저장소 `CLAUDE.md`를 먼저 읽고 규칙(check_writing_style.py 통과, 긴 대시 금지, 노출 범위 변경 절차)을 따른다.
8. 문서 `docs/예약_발행.md`에 사용법(publish_at 쓰는 법, 지연 가능성, 안전장치, 되돌리는 법)을 초보자도 따라 할 수 있게 쓴다.

## 하지 말 것

- `log_assets/markdown/`의 기존 글을 수정하지 않는다. 특히 파일명이 628_로 시작하는 글은 건드리지 않는다.
- 라이브에 실제 글을 새로 공개하는 테스트를 하지 않는다.
- main에 직접 push하지 않는다. 키, 토큰, 비밀값을 만들거나 출력하지 않는다.
- 이 저장소의 기본 작업 폴더는 다른 세션이 동시에 쓴다. 반드시 별도 worktree에서 작업한다: `git fetch origin && git worktree add C:/work/note-sched-wt -b claude/scheduled-publish origin/main`. 다른 브랜치나 worktree를 체크아웃하거나 삭제하지 않고, `gh pr close --delete-branch`도 쓰지 않는다.
- 커밋 메시지 끝에 `Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>`, PR 본문 끝에 `🤖 Generated with [Claude Code](https://claude.com/claude-code)`를 붙이고, PR을 열어 `gh pr merge <번호> --auto --squash`로 auto-merge를 켠다.

## 헤르메스 위임 (사장님 지시, CLAUDE.md 헤르메스 위임 우선 규칙)

- 노트는 설계, 코드 작성, 판정을 맡는다. 헤르메스는 실제 실행(단위 테스트, `gh workflow run`, 로그 수집)과 관찰과 재시도(최대 3회)를 맡는다.
- 발주: `hermes chat --oneshot --query "<지시문>"`. 사용법은 `C:\work\solar-bible\docs\딥리서치_파이프라인.md` 3~4절.
- 먼저 `C:\work\solar-bible\solar-bible.md` §10을 읽는다. 헤르메스는 이 저장소를 직접 수정하면 안 된다. 코드 작성과 커밋은 노트가 하고 헤르메스에게는 읽기, 실행, 로그 수집만 시킨다. §10 때문에 위임이 불가능한 단계는 노트가 직접 하고 "위임 불가 이유"를 보고서에 쓴다.
- 헤르메스에게는 절대 경로만 주고 산출물 경로를 지정하며 "재귀 스캔 금지"를 넣는다. 키, 토큰, 개인정보를 지시문과 결과에 쓰지 않는다.
- 결과는 TASK/EXECUTION/OBSERVATION/VERIFICATION/EVIDENCE/FAILURE-RECOVERY/STATUS 서식으로 받는다. "완료했다"는 말은 증거가 아니므로 원문 출력(테스트 출력, run 로그, exit code)을 받아 노트가 직접 대조한다.

- D. `python scripts/check_writing_style.py`와 이 변경에 관련된 `scripts/check_*.py` 통과 출력.

## 보고 형식

TASK / EXECUTION(실행한 명령) / OBSERVATION(원문 출력) / VERIFICATION(A~E별 통과/실패와 실행 주체: 헤르메스 또는 노트) / EVIDENCE(PR과 실행 로그 링크, 헤르메스에게 보낸 지시문 원문) / FAILURE-RECOVERY(막힌 것, 버린 길과 이유) / STATUS(DONE 또는 실패). 막히면 추측으로 메우지 말고 사실 그대로 보고한다. 비밀값(PAT, GitHub App 등)이 필요한 설계 선택은 임의로 진행하지 말고 선택지와 비용을 보고하고 멈춘다.
