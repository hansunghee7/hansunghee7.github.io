# 헤르메스 모델 자동 라우팅 조사·1차 구현 지시서 (2026-09-16)

발신: 탐(클라우드 세션) / 수신: 탐(로컬, 신PC) / 전달·승인: 사장님

목표: 헤르메스가 작업 난이도에 따라 비용이 다른 모델을 자동으로 골라 쓰게
한다. 사장님이 원안을 직접 작성했고(아래 원문 그대로 보존), 이 문서는 거기에
이 저장소가 이미 확보한 실측값과 이 환경의 제약(권한 분류기)을 얹은 것이다.
**공식 문서에 없는 기능을 있는 것으로 가정하지 않는다**(원안의 핵심 전제와
동일하다).

## 0. 이 세션이 이미 확보한 사실 (재조사하지 말 것)

- 신PC `config.yaml`의 현재 `model:` 섹션: `provider: openai-codex`,
  `default: gpt-5.6-sol-900k`, `reasoning_effort: medium`, `thinking: false`.
  `fallback_model:`은 파일에 예시 주석만 있고 실제 설정은 비어 있음(2026-09-15
  사장님 확인).
- `llm:` 섹션에 별도로 `provider: ollama`, `model: qwen2.5-coder:14b`,
  `endpoint: http://127.0.0.1:11434/v1`가 이미 설정돼 있음. **로컬 무료
  모델이 이미 하나 붙어 있다.** 어떤 하위 기능(STT? 다른 용도?)이 이걸
  쓰는지는 미확인이니 이번 조사 대상에 포함할 것. 저비용 delegation 후보로
  가장 먼저 검증 가치가 있음(API 키·과금 없음).
- **재현된 문제(2026-09-16 야간 2차 실측)**: 기본 설정 그대로 ad-hoc 직접
  호출(`hermes chat --query-file -`)을 하면 **HTTP 400**으로 실패함
  (`hermes doctor` 이슈 1번과 일치). 반면 신솔라 폴링 크론은 생성 시점의
  provider 스냅샷(`provider: nous`)을 그대로 쓰기 때문에 이 문제와 무관하게
  계속 정상 동작 중. 즉 **현재 config.yaml의 `model.provider: openai-codex`
  자체가 ad-hoc 호출 경로에서 깨져 있을 가능성이 있다.** 원안 8절이 요구하는
  "provider가 openai-codex로 설정됐는가/OAuth가 유효한가" 조사는 이 재현부터
  출발할 것.
- **환경 제약(중요, 원안에 없던 항목)**: 이 PC에서 Claude Code 세션이
  `hermes cron edit`이나 `config.yaml` 직접 수정을 시도하면 권한 분류기가
  "미승인 영속 변경/공유 자원 수정"으로 **두 번 연속 차단**했다(살아있는
  크론이 참조하는 파일이라는 판단으로 보임). **이번 작업도 config.yaml에
  손대는 단계(auxiliary/delegation 설정 추가 등)에서 같은 차단을 만날
  가능성이 높다.** 차단되면 강행하지 말고, 적용할 정확한 YAML 조각과 실행할
  명령을 스크래치패드 파일로 준비해 "사장님 직접 실행" 항목으로 넘긴다
  (아래 크론 프롬프트 사례와 동일한 패턴).
- **무료 모델 후보 추가(2026-09-16, 클라우드 세션 실측)**: 공식 Gemini API를
  인증 없이 직접 호출해 확인함. `generativelanguage.googleapis.com/v1beta/models`가
  살아있고, `gemini-flash-latest`/`gemini-2.5-flash-lite`/`gemini-pro-latest`
  전부 입력 1,048,576 토큰, 출력 65,536 토큰. OpenAI 호환 엔드포인트
  (`/v1beta/openai/chat/completions`)도 존재 확인(인증 없이 호출 시 정상적인
  "Missing Authorization header" 오류 응답). 즉 API 키만 있으면 Hermes의
  "커스텀 OpenAI 호환 엔드포인트" 방식(config.yaml 주석의 `base_url`+`key_env`)
  으로 붙일 수 있을 가능성이 높다. **미확인**: 무료 티어의 실제 분당/일일
  한도(`ai.google.dev`가 이 클라우드 세션에서 네트워크 차단이라 못 봄, 사장님이
  API 키 발급 화면에서 직접 확인 필요). `multi-llm-handoff` 규약의 "계정 간
  자동 라우팅·할당량 우회 금지" 조항은 세션 쿠키 추출 등 약관 우회 기술에만
  적용되고, 이 공식 API 경로는 해당 없음(같은 날 규약 갱신, 근거는
  `.claude/skills/multi-llm-handoff/SKILL.md` 참고).
- **다수 계정 풀, 3개 전부 처음부터 준비(2026-09-16, 최종 확정)**: 사장님이
  이미 쓰고 있는 제미나이 프로 유료 계정 3개(잉크 프로젝트·쇼츠랩
  딥리서치용, 본인 명의) 각각의 무료 API 할당량을 LiteLLM으로 로드밸런싱한다.
  역할 재배치(아래 항목)로 호출량 자체는 줄지만, 사장님 판단은 "지금 필요한
  만큼"이 아니라 회사의 공정자산·확장성 기준이라 **3개를 한 번에 설정한다**
  (계정 1개부터 시작하는 단계적 접근은 검토했으나 채택 안 함). `api_base:
  https://generativelanguage.googleapis.com/v1beta/openai/`,
  `api_key: os.environ/GEMINI_API_KEY_<n>`(1~3), `router_settings:
  routing_strategy: simple-shuffle`. 설정 예시와 배경은
  아티팩트(https://claude.ai/artifact/FM86igrvHaA6H5ztKM6g2G) 2·3절 참고.
  키 3개는 사장님이 로컬 탐에게 직접 전달(채팅에 남기지 않음).
- **역할 재배치(2026-09-16, 사장님 제안)**: 제미나이를 1차 지식 정제
  계층으로 쓰지 않는다. **1차 조사는 헤르메스+클로드 코드가 자체적으로
  하고, 제미나이는 그 결과를 검증하는 용도로만 쓴다**(비용·호출 낮춤).
  아티팩트 1·3절 참고. 헤르메스 delegation/auxiliary 설정 조사(2절)를 할

## 3. 설계 원칙 (원안 3절 그대로 적용)

Main model 자동교체(매 턴 `/model` 전환)를 먼저 만들지 않는다. 1차는
**delegation 기반 위임**으로 시작한다:

```
Main model (판단·복잡한 작업)
    ↓ 위임
간단한 독립 작업 → 저비용 delegation 모델(위 0절 ollama 후보 우선 검토)
```

# Hermes 모델 자동 라우팅 시스템 구축 지시서

## 0. 절대 전제

이번 작업의 목표는 Hermes가 작업 난이도/성격에 따라 적절한 모델을 선택하도록
만드는 것이다.

단, Hermes 기본 기능에 없는 것을 있는 것처럼 가정하지 마라.

현재 공식 Hermes 구조를 기준으로 다음을 사실로 취급한다.

1. Hermes에는 Main model과 Auxiliary model이 있다.
2. Auxiliary model은 compression, vision, approval, skill search 등
   작업별로 분리할 수 있다.
3. Auxiliary의 provider:auto는 기본적으로 Main model을 사용하고, 설정된
   fallback chain을 따른다.
4. Hermes에는 Subagent Delegation이 있으며, 부모 모델과 별도로
   delegation.model/provider를 지정할 수 있다.
5. /model은 이미 설정된 provider/model 사이를 전환할 수 있다.
6. /model로 모델을 바꾸면 해당 세션의 prompt cache가 리셋될 수 있다.
7. OpenAI Codex는 ChatGPT Plus/Pro OAuth로 Hermes에 인증할 수 있다.
8. ChatGPT Plus/Pro의 Hermes 사용량 차감 방식은 공식 문서상 명확히
   문서화되어 있지 않다.

따라서 "Hermes가 기본적으로 Main model을 자동으로 Luna/Terra/Sol/Astra 중
난이도별로 선택한다"고 가정하지 마라.

## 1. 목표

- Luna = 저비용/빠른 작업
- Terra = 일반 실무
- Sol = 고난도 작업
- Astra = 최고난도 작업

단순 작업은 가능한 한 저렴한 모델을 사용하고, 복잡한 작업만 상위 모델을
사용하도록 한다. 단, 실제 모델명/제공 여부/성능 특성은 현재 Hermes
설치환경과 provider가 제공하는 모델 목록을 확인한 뒤 확정한다.

## 2. 먼저 해야 할 일: 현황 조사

코드 수정 전에 반드시 현재 Hermes 환경을 조사한다. 확인 대상: Hermes 버전,
현재 main provider/model, OpenAI Codex OAuth 연결 상태, 현재
fallback_providers, auxiliary 설정, delegation 설정, 사용 가능한 OpenAI
Codex 모델 목록, 현재 config.yaml 실제 위치, 현재 세션/Gateway 실행 방식.
`hermes status`, `hermes config get model --json`, 현재 config.yaml, 현재
auth 상태, 현재 사용 가능한 provider/model 목록을 사실 기반으로 확보한다.
추정해서 쓰지 말고 실제 출력값을 근거로 기록한다.

## 3. 중요한 설계 원칙

Main model 자동교체를 먼저 구현하지 마라. `/model` 전환은 기존 세션의
prompt cache를 리셋할 수 있기 때문에, 매 턴마다 Main model을 변경하는
방식은 피한다. 대신 "작업을 적절한 모델에 위임하는 방식"을 우선한다.

## 4. 1차 구현: Delegation 기반

Hermes 공식 delegation 기능을 우선 활용한다. 부모 모델은 전체 목표와
판단을 담당하고, 간단한 독립 작업(파일 목록 확인, 간단한 코드 탐색, 형식
변환, 짧은 요약, 단순 반복 작업)은 저비용 delegation 모델에게 위임한다.
복잡한 아키텍처 판단, 대규모 코드 수정, 장애 분석, 중요한 의사결정은 Main
model이 맡는다.

## 5. 2차 구현: 난이도 기반 Router 검토

1차 구조가 안정적으로 동작한 후, 작업 복잡도를 사전에 분류하는 Router를
검토한다. 상태: EASY/NORMAL/HARD/CRITICAL → Luna/Terra/Sol/Astra. 이
Router가 Main model을 무조건 세션 중간에 교체해서는 안 된다. A. delegation
대상 모델을 Router가 선택 vs B. 새 세션 시작 시 Main model 선택, 두 방식을
비교한다. 매 턴 강제 `/model` 전환은 3순위.

## 6. Router 판단 기준

작업 단계 수, 필요한 추론 깊이, 코드 수정 규모, 여러 파일 간 의존성, 외부
도구 사용 수, 실패 비용, 보안/운영 위험, 결과 검증 난이도.

- EASY: 단순 조회, 상태 확인, 단일 파일의 단순 수정
- NORMAL: 여러 파일의 일반적인 수정, 테스트 추가, 일반적인 분석
- HARD: 복잡한 버그, 여러 컴포넌트의 연쇄 수정, 아키텍처 변경
- CRITICAL: 운영환경 변경, 데이터 손실 가능 작업, 인증/보안, 대규모
  마이그레이션, 복잡한 시스템 장애

## 7. 안전장치

EASY 작업은 상위 모델을 호출하지 않는다. NORMAL 작업은 Terra 수준을
우선한다. HARD 이상에서만 Sol/Astra를 고려한다. CRITICAL은 자동 실행보다
인간 승인 여부를 함께 판단한다. Router가 판단하지 못하면 임의로 최고
모델을 선택하지 말고 Main model로 fallback한다. 모델 호출 실패 시 Hermes
공식 fallback chain을 활용한다. 존재하지 않는 provider/model을 설정하지
않는다.

## 8. ChatGPT Plus OAuth 관련

provider가 `openai-codex`로 설정됐는가, OAuth 인증이 실제 유효한가, 선택
가능한 Codex 모델 목록이 무엇인가, 현재 설치된 Hermes에서
Luna/Terra/Sol/Astra라는 이름이 실제 어떤 모델 ID에 대응하는가를 검증한다.
모델명은 추측하지 말고 실제 provider model 목록을 확인한다. ChatGPT
Plus의 사용량이 Hermes에서 어떻게 차감되는지는 공식 문서가 명확히
정의하지 않았으므로, "Plus 사용량이 무제한"이라고 결론 내리지 마라.

## 9. 무료 모델 fallback

무료 모델을 추가하고 싶다면 우선 현재 Hermes가 실제로 지원하는
provider/model을 조사한다. 무료 모델 후보를 임의로 고정하지 마라. 확인 후
Main/Delegation/Auxiliary/Fallback 각 영역에 어떤 모델을 넣을 수 있는지
제안한다. 무료 모델은 단순 요약, 간단한 분류, 보조 분석, 실패 시
fallback에 우선 사용한다. 중요한 코드 작업의 기본 모델로 무료 모델을
강제하지 않는다.

## 10. 실제 구현 전에 반드시 할 비교

현재 Hermes의 기본 기능만으로 가능한 것과 추가 Router가 필요한 것을
구분해서 보고하라. 표 형식: 기능 | Hermes 기본 제공 | 추가 구현 필요 | 추천.
대상 항목: Main model 자동 난이도 전환, Auxiliary 자동 선택, Fallback, Delegation
model 선택, 난이도 Router, 작업별 비용 제어, 위험도 기반 상위 모델 승급.

## 11. 테스트 순서

한 번에 전체 자동화를 만들지 마라.

- Test 1: 단순 파일 조회 → EASY → 저비용 모델
- Test 2: 3~5개 파일 수정 → NORMAL → Terra 수준
- Test 3: 복잡한 버그 수정 → HARD → Sol 수준
- Test 4: 복잡한 아키텍처 변경 → CRITICAL → Astra/Sol 고려 + 승인 정책 검토
- Test 5: 저비용 모델 실패 → fallback 정상 동작

각 테스트에서 실제 사용된 provider/model을 증거로 남긴다.

## 12. 완료 조건

1. 현재 Hermes 버전과 실제 설정을 확인했다.
2. OpenAI Codex OAuth 연결 상태를 확인했다.
3. 실제 사용 가능한 모델 ID를 확인했다.
4. Hermes 기본 기능과 추가 Router의 역할을 분리했다.
5. Delegation을 이용한 1차 비용 최적화가 동작한다.
6. 최소 4개의 난이도 테스트를 통과했다.
7. 실제 어떤 모델이 사용됐는지 로그/증거가 있다.
8. 실패 시 fallback이 작동한다.
9. 기존 Hermes 기능과 충돌하지 않는다.
10. 현재 신솔라/구솔라 운영환경을 망가뜨리지 않는다.

## 13. 절대 하지 말 것

- 공식 문서에 없는 Hermes 기능을 있는 것으로 가정
- 존재하지 않는 모델 ID를 config에 입력
- ChatGPT Plus 사용량을 무제한으로 가정
- 매 턴마다 /model을 강제로 변경
- 검증되지 않은 자동 라우팅을 운영환경에 바로 적용
- 기존 Solar provider 제거
- OAuth credential 노출
- 현재 동작하는 Gateway/Telegram 설정을 작업과 무관하게 변경
- 전체 구조를 한꺼번에 리팩터링

달성하는 것이다.
