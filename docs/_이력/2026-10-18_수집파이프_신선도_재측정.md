## 3. 파이프라인별 실측 간격 및 현재 설정과의 차이

- **site_health**
  - 워크플로 정의상 스케줄은 `*/10 * * * *`(10분 간격)이나, GitHub Actions의 스케줄러 지연/조절로 인해 실제 실행 간격 중앙값은 4.82시간, p90은 7.03시간, 최대 9.48시간으로 관측됨.
  - 현재 `jobs.toml`에는 `period_min`이 명시되어 있지 않아 동적 추정(또는 기본값 24시간)에 의존함.

- **ink_queue**
  - 워크플로 정의상 스케줄은 `17 */2 * * *`(2시간 간격)이나, 실제 실행 간격 중앙값은 5.98시간, p90은 7.83시간, 최대 9.49시간으로 관측됨.
  - 현재 `jobs.toml`에는 `period_min`이 명시되어 있지 않음.

- **sync_agent_corpus**
  - 일일 스케줄(1일 1회, 19:29 UTC = 04:29 KST)과 마크다운 변경 푸시(`push`) 이벤트가 혼합되어 있음.
  - 커밋이 집중될 때는 실행 간격 중앙값이 2.39시간으로 짧으나, 커밋이 없는 구간에서는 일일 스케줄만 돌아 p90 간격이 24.04시간, 최대 26.48시간에 달함.
  - 현재 `jobs.toml`에는 `period_min`이 미설정 상태임.

- **youtube_deep_analytics**
  - 워크플로 정의상 일 2회(06:17, 20:17 KST, 공칭 간격 14시간 및 10시간) 실행되며, 실측 중앙값은 10.78시간, p90은 16.81시간, 최대 간격은 23.87시간(1회 누락 또는 지연 시)임.
  - 현재 `jobs.toml`에는 `period_min = 720`(12.0시간)으로 설정되어 있으며, `watch.py` 기본 감시 공식(`1.5 * period_min + 60분`) 적용 시 약 19시간에 stale 판정이 발생하여 단 1회 지연(최대 23.87시간)에도 거짓 경보가 발생할 수 있는 구조임.

- **instagram_insights**
  - 워크플로 정의상 일 2회(06:27, 20:27 KST) 실행되며, 실측 중앙값은 9.01시간, p90은 16.59시간, 최대 간격은 25.77시간임.
  - 현재 `jobs.toml`에는 `period_min = 720`(12.0시간)으로 설정되어 있어, `watch.py`의 stale 판정선(19시간)이 최대 관측 간격(25.77시간)보다 낮아 거짓 경보 위험이 있음.
