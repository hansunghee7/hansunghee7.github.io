# .claude/hooks 훅·설정 점검 (읽기 전용, 2026-10-07)

**결론: 등록 누락 자체는 거의 없지만(의도적 제외 1건만 확인), `tg_boss_persona_gate.py`는 Claude Code가 실제로 입력을 주는 방식(stdin JSON)이 아니라 `sys.argv`를 읽도록 짜여 있어 실전에서는 한 번도 작동하지 않는 것으로 보인다(시험은 내부 함수만 불러 이 배선 버그를 못 잡음) — 가장 급하게 볼 항목이다. 그 외에는 `check-tone.py`·`check-dash.py`가 stdin을 UTF-8로 강제하지 않아 로컬 Windows(cp949)에서 이모지 섞인 입력을 받으면 조용히 fail-open(검사를 건너뜀)할 수 있고, PreToolUse의 `Bash`·`Bash|PowerShell` matcher가 각각 3개·2개 훅에 겹쳐 등록돼 있다. 훅·설정 파일은 전혀 고치지 않았다.**

이 세션은 Windows 환경을 직접 실행할 수 없다(별도 pytest 분석 보고서 `docs/pytest_실패_원인_분석_1007.md` 참고). 아래에서 "Windows에서만"이라고 쓴 항목은 코드를 읽고 추론한 것이지 실측은 아니다 — 실측이 필요하면 로컬 Windows에서 돌려 확인해야 한다.

- `queue-gate.sh`/`queue-gate.py`: 파일은 있지만 `.claude/settings.json`에 등록돼 있지 않다. **버그 아님** — `docs/지투_프로세스표_자동소진.md:13`에 "2026-10-06 사장님 지시로 Stop 목록에서 제외, 파일은 남김"이라고 명시돼 있다. 우선순위: 낮음(문서화된 의도적 상태, 재등록 여부는 제품 결정).
- `.claude/hooks/ops-status.py`: `settings.json`에 직접 등록돼 있지 않다. 다만 이것도 등록 누락이 아니라, `session-start.sh:136`이 `run_with_timeout "$PY" ".../ops-status.py"`로 직접 호출하는 구조다(SessionStart 훅 안에서 보조 스크립트로 쓰임). 한 줄 제안: `.claude/settings.json`만 보고 "ops-status.py가 어디서 호출되는지" 찾으려는 사람을 위해 `session-start.sh:136` 근처에 "settings.json에는 없음, 여기서 직접 호출" 주석을 한 줄 추가하면 좋겠다. 우선순위: 낮음.
- 반대 방향(파일은 있는데 전혀 아무 데서도 안 불림)은 `queue-gate.py` 외에는 찾지 못했다 — `recall-hook.sh`도 등록돼 있고 `scripts/ops/recall.py --hook`을 호출하는 정상 구조다.

## (3) 실패 시 막는지(fail-closed) 통과시키는지(fail-open) 분류

전체적으로 "훅 자체의 파싱·실행 오류는 fail-open(`except Exception: sys.exit(0)`류), 정책 위반이 실제로 감지되면 fail-closed(`exit 2`/`return 2`)"라는 일관된 설계가 대부분 지켜지고 있다(예: `db-gate.py:38-42`, `subagent-blocking-gate.py:15-18`). 이 일반 패턴에서 벗어난 것만 적는다.

- **`tg_boss_persona_gate.py` — 확인된 버그, 우선순위 높음.** `main()`(55~67줄)이 `sys.argv[1]`을 명령어로 읽으려 하는데(60줄), Claude Code는 PreToolUse 훅에 도구 입력을 **stdin JSON**으로 준다(다른 22개 훅 전부가 `sys.stdin`을 읽음 — 예: `db-gate.py:40`, `main-checkout-gate.py:64`, `saegim-gate.py:162`). `tg_boss_persona_gate.sh`(등록 명령, `.claude/settings.json:67`)는 인자 없이 호출되므로 `len(sys.argv) < 2`(57줄)가 항상 참이 되어 `return 0`으로 즉시 통과한다 — **즉 이 훅은 한 번도 실제 `--persona` 검증을 하지 않고 항상 fail-open이다.** `test_tg_boss_persona_gate.py`는 내부 함수 `check_tg_boss_persona()`만 직접 불러 시험하므로(6~10줄) 이 배선 문제를 못 잡는다. 한 줄 제안: `main()`이 다른 훅처럼 `json.loads(sys.stdin.buffer.read())`로 `tool_input.command`를 읽도록 고치고, 차단 시 `return 1`(65줄)이 아니라 `return 2`로 바꿔야 한다(Claude Code는 exit 2만 "막음"으로 처리).
- **`tg_boss_persona_gate.py:65` — `return 1`은 차단이 아니다, 우선순위 높음(위와 같은 파일, 별도 지점).** 설령 입력을 제대로 받더라도 종료 코드 1은 Claude Code 훅 규약에서 "훅 자체 오류"로 취급돼 도구 호출을 막지 못한다. `return 2`가 맞다(다른 모든 차단형 훅이 전부 2를 씀: `db-gate.py:56`, `commit-gate.py:196` 등).
- **`tg_boss_persona_gate.sh` — python 부재 시 안전장치 없음, 우선순위 중간.** 다른 23개 `.sh` 전부 `command -v python3 ... else exit 0`로 python이 없으면 fail-open하는데, 이 파일(`tg_boss_persona_gate.sh:2`)은 바로 `python3 ...`을 호출해 python3이 PATH에 없으면 bash 자체가 "command not found"로 비정상 종료한다(통과·차단 어느 쪽도 아닌 정의되지 않은 실패).
- **상시 통과(관찰·알림 전용) 훅 — 설계상 fail-open, 버그 아님, 분류용으로만 기록.** `mail-wake.py`(11·15·18줄 전부 `sys.exit(0)`), `saegim-outage-notify.py`, `skill-nudge.py`(`.sh` 쪽도 `skill-nudge.sh` 끝에 `exit 0` 고정), `ops-status.py`는 코드 전체에 차단 경로(`exit(2)`/`return 2`)가 없다 — 이름 그대로 알림·표시용이라 당연하다.
- **Windows cp949 차이가 fail-open 빈도에 영향을 줄 수 있는 지점(미확인, 코드만 확인) — 우선순위 중간.** `check-tone.py:97-105`와 `check-dash.py:88-102`는 `json.load(sys.stdin)`을 `try/except Exception: sys.exit(0)`로 감싸(각각 104·102줄) 디코드 오류가 나도 "차단은 안 함"이 보장되지만, 그 대가로 **검사 자체가 조용히 스킵**된다. 로컬 Windows 콘솔 인코딩이 cp949인데 stdin에 이모지 등 cp949로 못 담는 문자가 섞여 들어오면(둘 다 대화 전체 텍스트·파일 경로를 담은 JSON을 읽음) `UnicodeDecodeError`로 매번 이 두 훅이 조용히 통과될 수 있다 — 별도로 올린 `docs/pytest_실패_원인_분석_1007.md`에서 로컬 Windows 31건 실패의 샘플 원인이 같은 cp949 `UnicodeDecodeError`였던 것과 같은 계열의 위험이다. 반대로 `commit-gate.py:158`·`stuck-process-gate.py:45`·`queue-gate.py:107`는 `sys.stdin.reconfigure(encoding="utf-8")`로, `saegim-gate.py:162`·`db-gate.py:40`·`token-leak-gate.py:70` 등은 `sys.stdin.buffer.read().decode("utf-8")`로 이미 방어돼 있다. 리눅스(CI)에서는 기본 인코딩이 UTF-8이라 이 차이가 안 드러난다 — **미확인**: 실제로 Windows에서 이 두 훅이 자주 조용히 스킵되는지는 실측하지 않았다.

## (4) 셸·경로 위험 패턴

- `set -e` 오용: **없음**. 24개 `.sh` 전부 확인했고 `set -e`를 쓰는 파일이 없다(유일하게 `session-start.sh:15`가 `set -uo pipefail`을 쓰는데, 중간에 실패해도 세션 시작을 막지 않으려고 의도적으로 `-e`를 뺀 것으로 보인다 — 적절함).
- 인용 부호 누락: `.sh` 래퍼 24개에서 따옴표 없이 쓰인 변수 확장을 찾지 못했다(`exec "$PY" "$DIR/xxx.py"` 패턴이 전부 큰따옴표로 감싸져 있음).
- `session-start.sh:130-131` — 사소한 가독성 위험, 우선순위 낮음. `tr '` 다음에 줄바꿈을 거쳐 `' ')"`로 이어지는데, 작은따옴표 문자열 안에 리터럴 개행이 그대로 들어 있다(`tr '\n' ' '`를 의도한 것으로 보임). 지금은 bash가 작은따옴표 안의 개행을 문자 그대로 받아들여 동작하지만, 다음에 이 줄을 손보다가 따옴표 짝을 잘못 맞추기 쉬운 모양이다. 한 줄 제안: `tr '\n' ' '`처럼 한 줄로 다시 쓰면 안전하다.
- 경로 하드코딩(`C:\work` 계열) — `.sh`에는 없고 `.py`에 여럿 있다. 전부 `os.environ.get("…", "C:/work/...")` 형태로 **환경변수 오버라이드가 가능**하다: `check-tone.py:81`(HUMAN_LOG), `db-gate.py:20`(LOG), `drive-gate.py:17-18`(DRIVE·LOG — 17줄 주석에 "CI에는 C:/work/_ops가 없음"이라고 스스로 적어 둠), `jitu-loop.py:158`(JITU_PO_DIR), `ops-status.py:13`(STATE), `queue-gate.py:21`(COUNT_FILE), `save-gate.py:13`(LOG). 이 패턴은 테스트에서 환경변수로 갈아끼울 수 있어 당장 위험하지 않다 — 우선순위 낮음.
- **`subagent-blocking-gate.py:54,57` — 환경변수 오버라이드가 없는 하드코딩, 우선순위 중간.** `lease_ok()`가 `open(r"C:\work\_ops\factory_browser_lease.json", ...)`를 그대로 열고(54줄), 로그도 같은 방식으로 고정 경로에 쓴다(57줄). 다른 훅들과 달리 환경변수로 바꿔 끼울 수 없다 — 전체를 `try/except`로 감싸(60~62줄) 파일이 없으면 그냥 "임대 없음"으로 fail-closed(차단 유지)하니 리눅스/CI에서 안전하긴 하지만, 이 "임대" 분기 자체를 테스트하려면 코드를 고치지 않는 한 불가능하다. 한 줄 제안: 다른 훅처럼 `os.environ.get("BROWSER_LEASE_FILE", r"C:\work\_ops\factory_browser_lease.json")` 형태로 바꾸면 테스트 작성과 이식성이 같이 좋아진다.
- `research-gate.py:23,37` — 하드코딩된 안내 문구("python C:/work/_ops/tools/vertex_research.py ...")는 실제로 그 경로를 열지는 않고 Claude에게 보여줄 안내 텍스트일 뿐이다. 우선순위 낮음(기능 위험 아님, Windows 전제 문구가 리눅스 세션에도 그대로 보임).

## (5) 시험 파일이 없는 훅 / 시험 추가 우선순위

- 파일명 기준으로는 **빠짐이 없다** — `.claude/hooks/`의 훅 `.py` 23개(관찰용 `ops-status.py` 포함) 전부 `test_<이름>.py`가 존재한다(`jitu-loop.py`는 4개: `test_jitu_loop.py`·`_ask`·`_owner`·`_req`).
- 다만 "시험 파일이 있다"가 "진입점(`main()`, 즉 Claude Code가 실제로 호출하는 stdin 배선)까지 검증한다"는 뜻은 아니다. 아래 7개는 해당 훅의 내부 판정 함수만 직접 import해서 부르고(`importlib.util.spec_from_file_location` 뒤 `gate.check(...)`류 직접 호출), `main()`을 서브프로세스나 stdin 모킹으로 실행해 보지는 않는다: `test_check_tone.py`, `test_skill_nudge.py`, `test_queue_gate.py`, `test_commit_gate.py`, `test_stuck_process_gate.py`, `test_saegim_gate.py`, `test_tg_boss_persona_gate.py`. 나머지(예: `test_db_gate.py`, `test_main_checkout_gate.py`, `test_guide_notice_gate.py`, `test_cite_note_gate.py` 등)는 `subprocess.run([sys.executable, 훅경로], input=...)`로 실제 stdin 경로까지 돌려 본다.
- **우선순위 1(높음): `test_tg_boss_persona_gate.py`에 진입점 시험 추가.** 지금 시험은 (3)에서 찾은 `sys.argv` vs stdin 배선 버그를 못 잡는다. `test_db_gate.py`나 `test_main_checkout_gate.py`처럼 `subprocess.run([sys.executable, "tg_boss_persona_gate.py"], input=json.dumps({"tool_name": "Bash", "tool_input": {"command": "python scripts/ops/tg_boss.py text x"}}).encode())`로 실제 호출해 보면 지금 구조로는 항상 통과(exit 0)한다는 게 바로 드러난다.
- **우선순위 2(중간): 나머지 6개(`check-tone`·`skill-nudge`·`queue-gate`·`commit-gate`·`stuck-process-gate`·`saegim-gate`)에 진입점(stdin) 레벨 스모크 시험을 1개씩 추가.** 코드를 읽어 보면 이 6개는 전부 `sys.stdin`을 올바르게 읽고 있어(`check-tone.py:98`, `commit-gate.py:164`, `stuck-process-gate.py:51`, `queue-gate.py:113`, `saegim-gate.py:162`, `skill-nudge.py:33`) tg_boss처럼 당장 깨져 있다는 증거는 없다 — 다만 `main()` 배선 자체가 시험 범위 밖이라 앞으로 같은 종류의 배선 버그가 생겨도 시험이 못 잡는 구조라는 뜻이다.
- **우선순위 3(낮음): `subagent-blocking-gate.py`의 `lease_ok()` 통과 경로(71줄, 임대가 유효할 때 통과시키는 분기).** 현재 시험(`test_subagent_blocking_gate.py`)이 이 분기를 다루는지는 이번 점검에서 깊이 보지 않았다 — (4)에서 지적한 하드코딩 경로 때문에 다루기 어려울 가능성이 있다. 경로를 환경변수화(위 (4) 제안)한 뒤 같이 보강하면 된다.

## 근거의 한계

- 이 점검은 `.claude/hooks/`와 `.claude/settings.json`만 읽었고, 훅이 호출하는 바깥 스크립트(`scripts/ops/recall.py`, `scripts/ops/tg_boss.py` 등)의 내부 구현은 이번 범위에 넣지 않았다.
- fail-open/fail-closed 분류는 코드를 정적으로 읽어 판단한 것이고, 실제로 각 훅을 stdin 입력과 함께 실행해 종료 코드를 재확인하지는 않았다(읽기 전용 지시이므로 스크립트를 실행하지 않음).
- Windows cp949 관련 서술은 전부 코드 구조로 추론한 것이며, 로컬 Windows에서 실제로 재현했는지는 **미확인**이다(검증은 `docs/pytest_실패_원인_분석_1007.md`와 같은 방식으로 로컬에서 실측해야 한다).
- `test_*.py`가 `main()`까지 덮는지 여부는 각 파일의 import/subprocess 사용 패턴만 보고 판단했고, 모든 개별 테스트 케이스의 입력값까지 하나하나 실행해 보지는 않았다.
- 비밀값은 변수 이름(`HUMAN_LOG`, `DRIVE_FILE` 등)으로만 인용했고 실제 값이나 토큰 형태 문자열은 옮기지 않았다.
