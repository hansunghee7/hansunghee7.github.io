## 1. 개요 및 전수 조사 결과

### 1-1. 배경 및 문제 의식
- `scripts/ops/jobs.toml`은 시스템 내 주기 작업과 서비스 생존을 감시하는 정본 대장이다.
- 현행 [watch.py](file:///home/goosloar/player-bt-20261018_125113/scripts/ops/watch.py) 점검 엔진은 작업 실패 시 `fail_after`에 따른 우편함 알림과 `severity = "warn"`에 따른 심각도 강등만 지원한다.
- 작업 실패 시 재시도, 지연(backoff), 데이터 덮어쓰기 방지, 폴백(fallback) 표기 등 **실질적 실패 제어 행동 필드가 전무**한 상태다.
- 이로 인해 실제 운영 현장에서 이미 치명적인 장애가 발생했거나 잠재적 위험이 누적되고 있다:
  - **도서 수집 덮어쓰기 사고**: 지연 실행된 수집 작업이 정상 축적된 기존 정본 값을 통째로 덮어쓰는 사고 발생 ([fetch_book_insight.py](file:///home/goosloar/player-bt-20261018_125113/scripts/fetch_book_insight.py), 커밋 `b18688aa5`에서 빈칸 병합으로 긴급 패치).
  - **모닝 브리핑 조용한 누락 사고**: 브리핑 생성 시 데이터 소스가 비어 있으면 섹션 자체를 조용히 누락(Silent failure)하여 운영진의 판단을 흐리게 한 사고 발생 ([brief_snapshot.py](file:///home/goosloar/player-bt-20261018_125113/scripts/ops/brief_snapshot.py), 커밋 `b2626a4de`에서 '조회 못 함' 명시로 개편).

## 3. 실패 정책 권고 및 정책 분포

### 3-1. 정책 정의 및 적용 원칙
능동 작업의 안전성을 확보하기 위해 다음 3대 정책 중 정확히 하나를 권고한다.

1. **`이전 값 유지(멱등 아니면 덮어쓰기 금지)` (22건 권고)**
   - **적용 대상**: 외부 수집(유형 1), DB/캐시 동기화(유형 2), 보고서/대시보드 생성(유형 3).
   - **핵심 원칙**:
     - 수집이나 쿼리가 부분 실패하거나 데이터가 비어 있을 경우, 기존의 유효한 직전 스냅샷을 보존한다.
     - 새로운 데이터는 "빈칸만 채우는 딥머지(deep merge)" 또는 신규 날짜 레코드 추가(append-only) 방식으로만 갱신하며, 정상값을 null/0으로 덮어쓰는 행위를 엄격히 차단한다.
     - 보고서 생성 시 원천 데이터가 누락되면 조용히 섹션을 누락하지 않고 `"조회 못 함 (기준: YYYY-MM-DD HH:MM 이전 값 유지)"` 형태의 대체 문구를 강제 출력한다.

2. **`재시도 0~1회+backoff` (17건 권고)**
   - **적용 대상**: 작업 큐/메시지 폴러(유형 4), 원격 프로브/헬스체크(유형 5).
   - **핵심 원칙**:
     - 일시적인 파일 잠금(lock), 순간적인 네트워크 지연, SSH 핸드셰이크 타임아웃을 해소하기 위해 **최대 1회**의 즉시 재시도만 허용한다.
     - **외부 API 및 원격 대상 무제한 재시도 절대 금지**: 재시도 횟수 상한은 엄격히 1회로 고정하며, 최소 15초에서 최대 60초의 백오프(backoff) 대기 시간을 둔다.
     - 1회 재시도 후에도 실패하면 추가 재시도를 멈추고 실패 상태로 확정하여 상태판에 반영한다.

3. **`사람 표시(알림만)` (10건 권고)**
   - **적용 대상**: 비용/예산/한도 감시(유형 6), 인프라 능동 제어(유형 7).
   - **핵심 원칙**:
     - 예산 초과 임계치 도달, 크레딧 고갈 위험, 러너 자동 전환 실패, 자율 에이전트 소환 장애 시 기계적 자동 재시도를 일체 금지한다.

## 5. jobs.toml 실패 제어 스키마 적용 방안 제안

### 5-1. 스키마 확장 설계안 (선언형 정책)
현행 [jobs.toml](file:///home/goosloar/player-bt-20261018_125113/scripts/ops/jobs.toml)의 `[[job]]` 테이블 구조를 그대로 유지하면서, 실패 시 동작을 제어하는 4개의 선택적(optional) 필드를 도입하는 방안을 제안한다. 기존 필드를 전혀 깨뜨리지 않는 100% 하위 호환 구조다.

```toml
# [[job]] 실패 행동 제어 스키마 확장안 (예시)
[[job]]
id = "fn:saegim-usage"
kind = "cmd"
cmd = ['python', 'C:/work/hansunghee7.github.io/scripts/ops/saegim_usage_fetch.py']
every_min = 720
fail_after = 1

# --- 신규 제안 실패 행동 필드 ---
# 1. failure_action: 실패 시 기본 행동 ("preserve_previous" | "retry_backoff" | "alert_only")
failure_action = "preserve_previous"

# 2. max_retries: 재시도 상한 횟수 (외부 API 및 무거운 작업은 0 또는 1로 강제)
max_retries = 1

# 3. retry_backoff_sec: 재시도 전 대기 시간 (초 단위, 기본 15초)
retry_backoff_sec = 30

# 4. fallback_text: 브리핑·보고서 원천 누락 시 대체 출력 문구 (조용한 누락 원천 차단)
fallback_text = "조회 못 함 (이전 상태 유지)"
```

### 5-2. 실행기(watch.py) 수용 구조 및 거버넌스 원칙
- [watch.py](file:///home/goosloar/player-bt-20261018_125113/scripts/ops/watch.py)의 `evaluate()` 함수에서 대상 작업 실행(rc != 0) 직후 `failure_action`을 판정한다:
  - `retry_backoff`: 지정된 `retry_backoff_sec` 동안 슬립 후 최대 `max_retries`회까지만 1회 추가 실행.
  - `preserve_previous`: 작업 스크립트 실행 실패 시 타깃 파일/DB를 건드리지 않도록 스크립트 인자로 전달하거나 래퍼에서 롤백을 보장.
  - `alert_only`: 즉시 실패 카운트를 올리고 상태판에 🔴/🟡를 점등하여 사람 개입 유도.
- **거버넌스 원칙**: 본 보고서는 정책 분석과 스키마 구조 제안에 국한하며, 실제 [jobs.toml](file:///home/goosloar/player-bt-20261018_125113/scripts/ops/jobs.toml) 스키마 변경 및 [watch.py](file:///home/goosloar/player-bt-20261018_125113/scripts/ops/watch.py) 파서 구현은 탐(주 설계자)의 검토 및 승인을 거쳐 진행한다.
