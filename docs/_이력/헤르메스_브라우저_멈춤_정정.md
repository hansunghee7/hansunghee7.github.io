# 헤르메스 브라우저 "멈춤" 정정 (2026-09-22, 탐)

**결론: 패치 불필요.** 이 PC의 헤르메스(v0.21.3, 업스트림 fdb7b216)는 브라우저를 정상 호출한다. 9/21~22 새벽에 세운 "헤르메스가 agent-browser를 출력 파이프로 불러서 멈춘다"는 가설은 틀렸다.

## 그러면 앞의 "멈춤"은 무엇이었나

추정(확정 아님): 무료 모델(네모트론)의 응답이 한 번에 수십 초 걸리고, 브라우저 요청은 왕복이 여러 번이라 총 100초를 넘는데, 시험 제한이 120~150초였다. 게다가 헤르메스 화면 출력을 파이프로 읽는 시험 방식이 겹쳐 "출력이 멈춘 것"처럼 보였다. 단독으로 `agent-browser ... | head`가 멈추는 현상은 사실이지만(윈도우에서 데몬이 파이프를 물려받음), 헤르메스는 그 방식으로 부르지 않으므로 무관하다.

## 다음에 시험할 때의 규칙

1. `hermes chat`을 시험할 때 제한시간은 **300초 이상**, 출력은 **파일로 리다이렉트**한다.
2. 브라우저 도구 자체가 의심되면 `browser_navigate`를 파이썬으로 직접 불러 1초대에 끝나는지 먼저 본다(모델 지연과 분리).
3. 이 PC는 `hermes update`를 하지 않았고 업스트림은 5천 커밋 앞서 있다. 업스트림 최근 수정은 윈도우 `.cmd`의 인자 인용 문제로, 이 증상과 무관하다. **업데이트는 필요해질 때까지 하지 않는다.**

## 남은 진짜 문제 (별개)

- **모델이 브라우저 도구 사용법을 헤맴**: 위 6번은 성공까지 도구를 12번 불렀다(`browser_exec` 도우미 함수의 async 여부를 몰라 시행착오). 수집 작업 지시서에 "`browser_navigate`로 열고 `browser_snapshot`으로 읽기"처럼 쓸 도구를 못 박는 편이 낫다(미시험).
- **로그인이 필요한 화면(구글 딥리서치)** 은 전용 프로필에 1회 로그인 방식이 미시험이고, 구글의 자동화 브라우저 로그인 차단 가능성이 있다. 사장님 별도 트랙 결과를 기다린다.
- **무료 모델 지연**: 도구 없는 단순 질문도 46~49초. 지연이 중요한 작업은 제미나이 API로 보내는 큐 7번의 근거가 된다.
