# 예약 발행

글에 "이 시각 이후에 공개해 주세요"라고 적어두면, 시각이 지난 뒤 자동으로 공개됩니다. 사람이 그 시각에 맞춰 PR을 병합하지 않아도 됩니다.

관련 파일: `.github/workflows/scheduled-publish.yml`(15분마다 실행), `scripts/scheduled_publish.py`(실제로 값을 바꾸는 스크립트), `scripts/test_scheduled_publish.py`(단위 테스트).

## 1. 쓰는 법

예약할 글의 맨 위 설정 칸(front matter)에 `publish_at` 한 줄을 추가하고, `published`는 `false`로 둡니다.

```yaml
publish_at: "2026-09-24T10:00:00+09:00"
published: false
```

1. 글 파일(`log_assets/markdown/...md`)을 엽니다.
2. `published: false` 줄 위나 아래에 `publish_at: "2026-09-24T10:00:00+09:00"` 한 줄을 넣습니다. 따옴표를 같이 쓰는 것을 권합니다.
3. 형식은 `연-월-일T시:분:초+09:00`입니다. 맨 끝 `+09:00`이 한국시간이라는 뜻입니다. 위 예시는 2026년 9월 24일 오전 10시(한국시간)입니다.
4. 글이 담긴 PR을 병합합니다. 이때 글은 아직 공개되지 않습니다(`published: false`).
5. 예약 시각이 지나고 다음 자동 실행이 돌면 `published: false`가 `published: true`로 바뀌어 main에 저장되고, 이어서 목록·사이트맵 갱신이 자동으로 돌아 사이트에 나타납니다.

성공하면: GitHub 저장소의 Actions 탭에 `Scheduled publish` 실행이 초록색으로 뜨고, 글 파일이 `published: true`로 바뀌어 있습니다. `publish_at` 줄은 기록용으로 그대로 남습니다.

## 2. 반드시 알아둘 것: 정확히 그 시각이 아닙니다

**"예약 시각 이후 첫 실행"에 공개됩니다.** 15분 간격으로 돌지만 GitHub의 예약 실행은 부하가 높으면 늦거나 한두 번 건너뛸 수 있습니다(이 저장소에서 다른 자동화가 실제로 이틀 연속 안 돈 적이 있습니다). 그래서 다음처럼 생각하세요.

- 보통은 예약 시각 기준 약 15분 안에 공개됩니다. 늦으면 30분 이상 밀릴 수 있습니다.
- 정확한 시각(예: 10:00 정각 뉴스레터 발송과 동시)이 중요한 글은 예약 발행에 맡기지 말고 직접 발행하세요.
- 공개까지 이어지는 흐름: 예약 시각 경과, 다음 실행에서 `published: true`로 변경, 사이트 목록 갱신 파이프라인 실행, GitHub Pages 배포. 마지막 두 단계에 몇 분이 더 걸립니다.

## 3. 안전장치

| 상황 | 결과 |
| --- | --- |
| `publish_at`이 없는 글 | 절대 건드리지 않습니다. 컨펌 안 된 초안은 계속 `published: false`입니다. |
| `published: true`인 글 | 건드리지 않습니다. 두 번 돌려도 결과가 같습니다. |
| 예약 시각이 아직 안 지남 | 대기합니다. |
| `publish_at` 형식이 잘못됨(`내일 10시`, 날짜만 쓴 값 등) | 그 글만 건너뛰고 Actions 로그에 노란 경고를 남깁니다. 다른 글 발행은 막지 않고 실행 자체는 성공으로 끝납니다. |
| 본문·줄바꿈 | `published:` 줄의 `false` 한 단어만 `true`로 바뀝니다. 본문, 다른 줄, 줄바꿈 형식(CRLF/LF)은 한 글자도 안 바뀝니다. |
| 시간대 | 끝에 `+09:00`(또는 `Z`)이 있으면 그대로 따릅니다. 아무것도 안 붙이면 한국시간으로 해석합니다. 서버(UTC) 시각과 헷갈릴 일이 없습니다. |

주의할 함정 두 가지.

- **과거 시각을 잘못 적으면 즉시 공개됩니다.** 예를 들어 `2025-09-24`처럼 연도를 틀려 과거로 적으면 다음 실행 때 바로 공개됩니다. 날짜만 쓰거나 형식이 아예 틀린 경우는 건너뛰지만, 형식이 맞는 과거 시각은 정상 예약으로 봅니다.
- `publish_at`을 넣은 글은 "사장님이 컨펌한 글"이라는 표시이기도 합니다. 컨펌 전 초안에는 이 줄을 넣지 마세요.

## 4. 미리 확인해 보기 (dry run)

무엇이 공개될지만 보고 싶을 때, 아무것도 바꾸지 않고 확인할 수 있습니다.

1. https://github.com/hansunghee7/hansunghee7.github.io/actions/workflows/scheduled-publish.yml 을 엽니다.
2. 오른쪽 `Run workflow` 버튼을 누릅니다. `dry_run`이 체크된 기본값 그대로 초록색 `Run workflow`를 누릅니다.
3. 잠시 뒤 새로 생긴 실행을 열어 `Publish due posts` 단계 로그에서 `[DRY-RUN] 공개 예정:` 줄과 맨 아래 요약을 봅니다. 파일은 바뀌지 않습니다.

로컬에서는 `python scripts/scheduled_publish.py --dry-run`을 돌리면 같은 결과를 봅니다.

## 5. 예약을 취소하거나 되돌리는 법

- **아직 공개 전**: 그 글에서 `publish_at` 줄을 지우는 PR을 병합합니다. 줄이 없으면 이 자동화는 그 글을 건드리지 않습니다.
- **이미 공개됨**: 글에서 `published: true`를 `published: false`로 바꾸는 PR을 병합합니다. `publish_at` 줄도 함께 지우세요(안 지우면 시각이 이미 지났으므로 다음 실행 때 다시 공개됩니다).
- **자동화 전체 정지**: Actions 탭의 `Scheduled publish` 워크플로 화면에서 오른쪽 `...` 메뉴의 `Disable workflow`를 누릅니다. 다시 켜면 재개됩니다.

## 6. 공개 뒤 목록·사이트맵은 어떻게 갱신되나

이 자동화는 `published` 값만 바꿉니다. 목록 카드(`log.html`), `posts.json`, 사이트맵은 기존 `Publish log pipeline` 워크플로가 만듭니다. 그런데 GitHub은 `GITHUB_TOKEN`으로 한 push가 다른 워크플로의 `on: push`를 깨우는 것을 막습니다. 그래서 예약 발행은 push 직후 `gh workflow run publish-pipeline.yml --ref main`(`workflow_dispatch`)으로 그 파이프라인을 직접 호출합니다. 이 호출은 GitHub이 허용하는 예외라 별도 토큰(PAT)이나 비밀값이 필요 없습니다. 필요한 권한은 워크플로 파일의 `permissions: actions: write`뿐입니다.

## 7. 테스트

```
python scripts/test_scheduled_publish.py -v
```

임시 폴더에 가짜 글을 만들어 과거·미래·`publish_at` 없음·공개 상태·잘못된 형식·CRLF·시간대 경계를 확인합니다. 저장소의 실제 글은 읽지도 쓰지도 않습니다. `docs/fixtures/scheduled-publish/`의 예시 글 5개는 Actions에서 `dir`와 `now` 입력을 주고 dry run으로 돌려 볼 때 쓰는 자료이고 `docs/`는 사이트 빌드에서 제외됩니다.
