# 예약 발행

글에 "예약 설정"을 켜 두면, "발행일" 시각이 지난 뒤 자동으로 공개됩니다. 사람이 그 시각에 맞춰 PR을 병합하지 않아도 됩니다.

관련 파일: `.github/workflows/scheduled-publish.yml`(15분마다 실행), `scripts/scheduled_publish.py`(실제로 값을 바꾸는 스크립트), `scripts/test_scheduled_publish.py`(단위 테스트).

## 1. 쓰는 법 (글쓰기 화면에서)

글 하나의 상태는 세 가지입니다. 아래 표의 조합으로 정해지고, 저장하면 바로 반영됩니다.

| 상태 | 공개 여부 | 예약 설정 | 발행일 |
|---|---|---|---|
| 노출(공개 중) | 켬 | 끔 | 글에 표시되는 날짜 |
| 비노출(숨김) | 끔 | 끔 | (쓰이지 않음) |
| 예약(발행일에 자동 공개) | 끔 | 켬 | **앞으로의 시각**(공개 시각) |

- **공개 여부(노출 설정)가 최상위입니다.** 이미 나간 글도, 아직 안 나간 글도 "공개 여부"를 끄면 숨겨집니다.
- 예약 글을 숨기려면 "예약 설정"을 끄면 됩니다(끄면 숨김 상태가 됩니다). 그래서 "숨겨 놨는데 예약도 걸려 있는 글"은 생기지 않습니다.

예약하는 순서:

1. https://simplifier.co.kr/insight-7b3e9f2c/write.html 을 엽니다(스튜디오 글쓰기). 성공하면 "Log 글" 목록이 보입니다. 로그인 화면이 나오면 GitHub 로그인을 합니다.
2. 예약할 글을 목록에서 클릭해 엽니다. 새 글이면 왼쪽 위 "새 글" 버튼을 누릅니다.
3. 본문을 다 쓰고 컨펌까지 끝났는지 확인합니다.
4. **"발행일"** 칸을 눌러 **공개하고 싶은 날짜와 시간**을 고릅니다. 한국시간으로 표시됩니다. 예: 2026-09-24 오전 10:00. 지금보다 앞선 시각은 예약이 되지 않습니다.
5. 발행일 바로 아래 **"공개 여부"** 스위치를 **끕니다**(꺼진 상태 = 숨김). 켜져 있으면 저장하는 즉시 공개됩니다.
6. 그 바로 아래 **"예약 설정"** 스위치를 **켭니다**.
7. 오른쪽 위 "저장"(Save)을 누릅니다. 성공하면 저장됐다는 알림이 뜨고, 이 시점에는 글이 아직 공개되지 않습니다.
8. 발행일 시각이 지나고 다음 자동 실행이 돌면 "공개 여부"가 자동으로 켜지고, 이어서 목록·사이트맵 갱신이 돌아 사이트에 나타납니다. 별도 조작은 필요 없습니다.

성공하면: GitHub 저장소 Actions 탭(https://github.com/hansunghee7/hansunghee7.github.io/actions/workflows/scheduled-publish.yml)에 `Scheduled publish` 실행이 초록색으로 뜨고, 글 파일이 `published: true`로 바뀌어 있습니다. "예약 설정"은 기록용으로 켜진 채 남습니다.

실패하면(발행일 시각이 한참 지났는데 글이 안 나옴): 위 Actions 링크에서 마지막 실행의 `Publish due posts` 단계 로그를 확인하고, 노란 경고가 있으면 내용대로 고칩니다. 흔한 원인은 두 가지입니다. ① 발행일을 지나간 시각으로 정하고 예약함(발행일을 미래로 고쳐 다시 저장). ② "공개 여부"가 켜진 채로 저장됨(이미 나간 글로 취급되어 예약은 무시됩니다). 원인이 안 보이면 로그 주소를 마야나 탐에게 넘기세요.

같은 값을 직접 파일에 적는 방법(개발자용): 글 파일(`log_assets/markdown/...md`)의 맨 위 설정 칸에 아래처럼 넣고 PR을 병합합니다. CMS가 저장하는 값과 형식이 같습니다.

```yaml
date: 2026-09-24T10:00:00+09:00
scheduled: true
published: false
```

참고: 예비 화면 `/admin-legacy/`(Decap)에는 "예약 설정" 칸이 없습니다. 예약은 평소 화면(`/admin/`, 스튜디오 글쓰기)에서만 하세요.

## 2. 반드시 알아둘 것: 정확히 그 시각이 아닙니다

**"예약 시각 이후 첫 실행"에 공개됩니다.** 15분 간격으로 돌지만 GitHub의 예약 실행은 부하가 높으면 늦거나 한두 번 건너뛸 수 있습니다(이 저장소에서 다른 자동화가 실제로 이틀 연속 안 돈 적이 있습니다). 그래서 다음처럼 생각하세요.

- 보통은 예약 시각 기준 약 15분 안에 공개됩니다. 늦으면 30분 이상 밀릴 수 있습니다.
- **실측(2026-09-20 마야 점검)**: 위 15분은 설계값이다. 최근 `Scheduled publish` schedule 실행 5건의 실제 간격은 약 116~129분이었다(표본 5건). 이 간격이면 발행일 뒤 첫 실행까지 최대 약 2시간 10분 걸릴 수 있다. 이 워크플로의 실제 push 경로(PUSH_TOKEN, 관리자 우회)는 아직 한 번도 통과한 기록이 없다. (참고: 「PM과 PL 차이는 뭘까요?」는 2026-09-20 사장님 지시로 예약 없이 바로 공개됐고, 이때 봇의 push가 통과한 기록이 처음 생겼다. 예약 경로 자체의 첫 실전은 9/24 「핵심가치」.)
- 정확한 시각(예: 10:00 정각 뉴스레터 발송과 동시)이 중요한 글은 예약 발행에 맡기지 말고 직접 발행하세요.
- 공개까지 이어지는 흐름: 예약 시각 경과, 다음 실행에서 `published: true`로 변경, 사이트 목록 갱신 파이프라인 실행, GitHub Pages 배포. 마지막 두 단계에 몇 분이 더 걸립니다.

## 3. 안전장치

| 상황 | 결과 |
| --- | --- |
| "예약 설정"이 없거나 꺼진 글(비노출 글, 컨펌 전 초안, 옛 글) | 발행일이 과거든 미래든 절대 건드리지 않습니다. 경고도 없습니다. 「핵심가치」 같은 초안과 2023~2025년 비노출 글이 여기에 해당합니다. |
| `published: true`인 글 | 건드리지 않습니다. 두 번 돌려도 결과가 같습니다. 노출이 켜져 있으면 예약보다 노출이 우선입니다. |
| 발행일이 아직 안 지남 | 대기합니다. |
| **지나간 시각으로 건 예약** | 공개하지 않고 노란 경고를 남깁니다. 발행일이 그 글의 마지막 저장(git 커밋) 시각보다 앞이면 "예약으로 인정하지 않음"으로 처리합니다. 발행일을 미래로 고쳐 다시 저장하세요. |
| 예약을 켰는데 발행일 형식이 잘못됨(`내일 10시`, 날짜만 쓴 값 등) | 그 글만 건너뛰고 Actions 로그에 노란 경고를 남깁니다. 다른 글 발행은 막지 않고 실행 자체는 성공으로 끝납니다. |
| 본문·줄바꿈 | `published:` 줄의 `false` 한 단어만 `true`로 바뀝니다. 본문, 다른 줄, 줄바꿈 형식(CRLF/LF)은 한 글자도 안 바뀝니다. |
| 시간대 | 끝에 `+09:00`(또는 `Z`)이 있으면 그대로 따릅니다. 아무것도 안 붙이면 한국시간으로 해석합니다. 서버(UTC) 시각과 헷갈릴 일이 없습니다. |

주의할 함정.

- "예약 설정"은 켰는데 **"공개 여부"도 켜 둔 채** 저장하면 저장 즉시 공개되고 예약은 의미가 없어집니다. 예약할 때는 공개 여부를 꺼 두세요.
- **"지나간 시각은 예약할 수 없다"는 저장 화면에서 막히지 않고**(CMS에 그 기능이 없습니다), 저장 뒤 봇이 공개하지 않는 방식으로 지켜집니다. "예약했는데 안 나왔다"면 발행일이 저장 시각보다 앞선 것은 아닌지 먼저 보세요.
- "예약 설정"을 켠 글의 본문을 **발행일이 지난 뒤에** 다시 저장하면 그 저장이 "마지막 저장 시각"이 되어 예약이 인정되지 않습니다(봇이 아직 못 돌았을 때 손대면 생김). 발행일 전에는 마음껏 고쳐도 됩니다.

## 4. 미리 확인해 보기 (dry run)

무엇이 공개될지만 보고 싶을 때, 아무것도 바꾸지 않고 확인할 수 있습니다.

1. https://github.com/hansunghee7/hansunghee7.github.io/actions/workflows/scheduled-publish.yml 을 엽니다.
2. 오른쪽 `Run workflow` 버튼을 누릅니다. `dry_run`이 체크된 기본값 그대로 초록색 `Run workflow`를 누릅니다.
3. 잠시 뒤 새로 생긴 실행을 열어 `Publish due posts` 단계 로그에서 `[DRY-RUN] 공개 예정:` 줄과 맨 아래 요약을 봅니다. 파일은 바뀌지 않습니다.

로컬에서는 `python scripts/scheduled_publish.py --dry-run`을 돌리면 같은 결과를 봅니다.

## 5. 예약을 취소하거나 되돌리는 법

- **아직 공개 전(예약 대기 중)**: CMS에서 그 글을 열어 "예약 설정"을 끄고 저장합니다. 끄면 숨김 상태가 되고 봇은 더 이상 그 글을 보지 않습니다.
- **이미 공개됨**: CMS에서 "공개 여부"를 끄고 저장하면 숨겨집니다. "예약 설정"이 켜진 채 남아 있어도 발행일이 이미 지났으므로 봇은 "지나간 시각 예약"으로 보고 다시 공개하지 않습니다(경고가 남을 수 있어 "예약 설정"도 같이 끄는 것을 권합니다).
- **자동화 전체 정지**: Actions 탭의 `Scheduled publish` 워크플로 화면에서 오른쪽 `...` 메뉴의 `Disable workflow`를 누릅니다. 다시 켜면 재개됩니다.

## 6. 공개 뒤 목록·사이트맵은 어떻게 갱신되나

이 자동화는 `published` 값만 바꿉니다. 목록 카드(`log.html`), `posts.json`, 사이트맵은 기존 `Publish log pipeline` 워크플로가 만듭니다. 그런데 GitHub은 `GITHUB_TOKEN`으로 한 push가 다른 워크플로의 `on: push`를 깨우는 것을 막습니다. 그래서 예약 발행은 push 직후 `gh workflow run publish-pipeline.yml --ref main`(`workflow_dispatch`)으로 그 파이프라인을 직접 호출합니다. 이 호출은 GitHub이 허용하는 예외라 별도 토큰(PAT)이나 비밀값이 필요 없습니다. 필요한 권한은 워크플로 파일의 `permissions: actions: write`뿐입니다.

## 7. 테스트

```
python scripts/test_scheduled_publish.py -v
```

임시 폴더에 가짜 글을 만들어 예약 켬/끔·발행일 과거/미래·공개 상태·잘못된 형식·지나간 시각 예약(임시 git 저장소 사용)·CRLF·시간대 경계를 확인합니다. 저장소의 실제 글은 읽지도 쓰지도 않습니다. `docs/fixtures/scheduled-publish/`의 예시 글 5개는 Actions에서 `dir`와 `now` 입력을 주고 dry run으로 돌려 볼 때 쓰는 자료이고 `docs/`는 사이트 빌드에서 제외됩니다.
