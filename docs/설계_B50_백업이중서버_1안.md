# 설계 초안: 새김 B50 백업 이중 서버 1안 (클라우드 작성, 검토 전)

상태: **초안**. 근거 자료(`r62.md` 점검서)는 로컬 PC에 있어 클라우드는 인수인계 요약만 보고 썼다. 아래 "확인할 것"이 대조되기 전에는 확정으로 보지 않는다.

## 한 줄 결론
서버를 한 대 더 두기보다, **GCP 계정을 유료로 전환하고 예산 알림과 인스턴스 상한으로 비용 폭주만 막는 것**을 1안으로 한다.

## 왜 이 방향인가
- 서버(Cloud Run)는 이미 데이터를 들고 있지 않는 구조(무상태)이고 최대 인스턴스가 2로 제한돼 있다. 한 대가 죽어도 같은 이미지가 다시 뜨므로 "서버 한 대 더"의 이득이 작다.
- 진짜 위험은 서버 고장보다 **무료 체험 크레딧이 끝나거나 결제 설정 문제로 서비스 전체가 멈추는 것**이다. 유료 전환이 이쪽을 직접 막는다.
- 대신 유료가 되면 비용이 새어 나갈 수 있으니 브레이크가 필요하다.

## 비용 근거 (업무대장 N164의 10/5 실측)
- 새김 서버는 요청 기반 과금 1 vCPU·512MiB, 최대 2대. 최근 30일 요청 약 1.9만 건, 과금 인스턴스 시간 약 75시간.
- 공개 단가로 월 비용은 [추정] 약 4천 원(무료 한도 적용) ~ 1만 3천 원(미적용). 레지스트리·빌드 저장은 미측정.
- 따라서 유료 전환의 비용 부담은 작을 가능성이 크다. 이 숫자는 추정이므로 로컬 검토에서 최근 결제 보고서와 대조한다.

## 설계
1. **결제**: 청구 계정을 유료로 전환한다. (돈이 걸린 설정이라 사장님 허용 필요)
2. **예산 알림**: 월 예산 대비 50%, 90%, 100%에서 알림을 보낸다. 알림은 텔레그램으로 받는다.
3. **진짜 브레이크는 인스턴스 상한**: max-instances 2를 유지한다. 비용이 폭주하려면 인스턴스가 늘어야 하므로 이 상한이 가장 단순하고 안전하다.
4. **자동 중지는 마지막 선**: 예산 초과 시 결제를 끊는 자동화(초안은 로컬에 있음)는 서비스를 스스로 멈추게 하므로, 정상 사용량보다 충분히 높은 선에서만 건다. 알림과 상한이 먼저다.
5. **데이터 백업**은 서버가 아니라 DB 쪽 문제다. 서버 이중화와 분리해서 본다.

## 확인할 것 (로컬이 r62.md·실제 설정과 대조)
1. B50이 말하는 "백업 이중 서버"가 서버 이중화인지 DB 백업인지, r62.md의 정의와 같은가.
2. Cloud Run 현재 설정(무상태, max-instances 2)이 인수인계 요약과 맞는가.
3. 현재 무료 크레딧 만료일과 만료 시 서비스에 일어나는 일.
4. 예산 초과 자동 중지 초안이 "서비스 전체 중지"인지, 어떤 선에서 걸리는가.
