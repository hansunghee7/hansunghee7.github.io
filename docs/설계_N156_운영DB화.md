# 설계: N156 운영 상태 표를 DB로 (클라우드 탐 작성, 2026-10-07, 초안 v1)

상태: **설계 초안**. 근거는 업무대장 N156 줄과 비공개 저장소 `reports/n155/`(스키마 v0~v3, 자문 종합)다. 클라우드는 운영 DB·로컬 파일을 못 봐서, 실제 표 상태와 대조하는 일(아래 "확인할 것")은 로컬 몫이다. 이 문서는 공개 저장소에 있으므로 프로젝트 ID·키·고객명은 쓰지 않았다.

## 한 줄 결론
저장소와 표준 스키마는 우리가, 화면은 외부 오픈소스로 간다는 큰 방향(10/5 결정)은 유지하고, **다음 투자는 "표마다 정본이 어디인지 정하기, 변경 이력 남기기, 쓰기 권한 좁히기, 가져오기 자동 점검"** 네 가지다. 화면(Metabase)과 판매용 일반화는 마지막이다.

## 지금 있는 것 (대장 기준, 10/5~10/7)
- 시험용 Supabase 프로젝트(운영 Carvit DB와 분리, 무료). 에이전트는 금고가 넣은 서비스 키로 읽고 쓴다(값은 못 봄). 왕복 시험 통과.
- 표: 영상 성과 3개(`channels`·`content_items`·`metrics_snapshots`)와 뷰, 이관 8개(`agent_calls`·`gpu_gate_log`·`vertex_usage`·`tasks`·`sns_posts`·`kpi_daily`·`video_perf`·`accounts`), 문서 검색용 `docs`(글자 검색 색인), 정본 지도 `canonical_map`, 자원 대장 `resources`, 합쳐 보는 뷰 `v_resource_usage`.
- 가져오기: `import_ops_tables.py`(md·csv → 표, 매번 비우고 다시 채움), 1시간마다 `fn:opsdb-sync`. GPU 관문은 DB에 직접도 기록(이중 기록).
- 실측: 같은 질문에 읽는 양이 md 대비 약 94~99% 감소(바이트 기준). 문서 검색은 하이브리드 65%, 정본 지도 방식이 더 나았으나 표본이 작고 지도가 질문을 본 뒤 만들어진 한계가 있다.

## 진단: 지금 구조의 약점 다섯 가지
1. **복사 방식의 정본 문제**: 가져오기가 "비우고 다시 채움"이라 에이전트가 DB에 직접 쓴 값은 다음 가져오기 때 사라진다. 사람이 md를 고치는 표와 에이전트가 쓰는 표가 섞여 있는데 구분이 없다.
2. **이력이 없다**: `tasks`는 매번 덮어쓴 스냅샷이다. 상태가 언제 바뀌었는지(진행→완료)를 못 센다. "성과→다음 계획 루프"와 "사람 손 갱신 횟수" 같은 판단 기준을 재려면 이력이 필요하다.
3. **칸이 거의 text**: 날짜·상태가 문자열이라 잘못된 값이 들어와도 막지 못한다. 대신 `raw`(jsonb)에 원본 전체가 있어 정보 손실은 없다.
4. **쓰기 권한이 넓다**: 서비스 키는 모든 표에 읽기·쓰기·삭제가 된다. 에이전트가 5개 이상 쓰기 시작하면 로그 표를 실수로 지우거나 고칠 수 있다.
5. **가져오기 결과가 DB 안에 남지 않는다**: "첫 자동 실행 확인"은 감시 대장·상태판에 있지만, 가져오기가 몇 행을 넣고 바꿨는지는 DB로 질의되지 않는다.

## 설계 원칙
- 표마다 정본을 하나로 정한다(아래 표). 정본이 아닌 쪽은 복사본이라고 표시하고 쓰지 않는다.
- 로그·이력은 **덧붙이기만**(append-only). 고치거나 지울 수 없게 DB가 막는다(트리거). 서비스 키가 있어도 막힌다.
- 값(키·비밀번호)은 어떤 칸에도 넣지 않는다(10/5 원칙 유지). 이름·상태·참조(`vault_ref`)만.
- 한 번에 한 가지만 바꾸고, 바꿀 때마다 증거 한 줄과 되돌리는 방법 한 줄을 남긴다.

## 표별 정본 정책 (제안)
- 정본이 DB: `agent_calls`, `gpu_gate_log`, `vertex_usage`(로그, 이중 기록 뒤 CSV 폐기), `content_items`·`metrics_snapshots`(API 수집, 덧붙임), `accounts`·`quota_snapshots`(값 없이 상태만), 새로 만들 `task_events`·`ingest_runs`.
- 정본이 md(사람이 편집): `tasks`(페르소나별 업무대장), `sns_posts`, `kpi_daily`, `video_perf`의 수기 부분. DB는 읽기용 복사본이고, 에이전트가 이 표에 쓰지 않는다. 쓰고 싶으면 md 편집 도구를 거친다.
- 이유: 사람이 md를 고치는 동안 DB를 정본으로 바꾸면 두 곳이 갈라진다. 사람 손 갱신이 주 1회 이하로 떨어진 표만 DB 정본으로 옮긴다(10/5에 정한 다음 단계 신호).

## 스키마 v4 초안 (기존 표 위에 추가, 값은 비어 있어도 되는 칸은 null)
```sql
-- 1) 변경 이력: 가져오기 때 이전 값과 비교해 바뀐 칸만 덧붙인다
create table task_events (
  id bigint generated always as identity primary key,
  owner text not null, task_no text, section text not null,
  field text not null, old_value text, new_value text,
  changed_at timestamptz not null default now(),
  source text not null           -- import-diff / agent-write
);
create index task_events_key on task_events (owner, task_no, changed_at desc);

-- 2) 가져오기 실행 기록: 감시와 별개로 DB에서 "몇 행 넣고 바꿨나"를 질의
create table ingest_runs (
  id bigint generated always as identity primary key,
  job text not null, started_at timestamptz not null default now(), finished_at timestamptz,
  rows_in int, rows_changed int, rc int, note text   -- 실패해도 기록(rc≠0)
);

-- 3) 계정·한도: accounts는 값 없이 상태만, 시점별 한도는 따로 쌓는다
create table quota_snapshots (
  id bigint generated always as identity primary key,
  account_id bigint references accounts(id), resource text not null,
  remaining numeric, unit text, measured_at timestamptz not null default now(),
  source text not null           -- manual / script
);
alter table accounts add column if not exists vault_ref text;  -- 금고 안의 이름만(값 아님)

-- 4) 상태값 목록: tasks.status의 변종("완료·증거" 등)을 한 곳에서 정리
create table task_status (code text primary key, family text not null, note text);
-- family: open / waiting / done / hold. 가져오기는 변종을 family로 접어 새 칸 status_family에 넣는다

-- 5) 로그 표 덧붙이기 전용: 고치기·지우기 차단
create or replace function block_mutation() returns trigger language plpgsql as $$
begin raise exception 'append-only table: % is not allowed', tg_op; end $$;
create trigger agent_calls_ro before update or delete on agent_calls for each row execute function block_mutation();
-- gpu_gate_log, vertex_usage, task_events, ingest_runs, metrics_snapshots에도 같은 트리거
```
- 주의: 이 SQL은 설계용 초안이고 아직 실행하지 않았다. 지금 `import_ops_tables.py`가 로그 표를 "비우고 다시 채움"으로 쓰므로, 로그 표에 트리거를 걸기 전에 가져오기를 "DB에 없는 줄만 이어 붙이기"(10/5 완료한 방식)로 바꿔야 한다. 순서가 뒤집히면 가져오기가 멈춘다.
- 영상 성과 3개와 뷰(`v_latest_metrics`)는 그대로 쓰고, 제목·KST 시각이 붙은 뷰 `v_content_perf`만 추가한다(10/5에 발견한 개선점).
- 문서 검색(N174)의 `doc_sections` 표는 같은 프로젝트에 두되 이 문서 범위 밖이다. 단, 이름 규칙(`source`, `imported_at`)은 맞춘다.

## 권한 설계
- 현실의 제약: Supabase의 비밀 키는 모두 서비스 역할로 통한다. 에이전트마다 서로 다른 DB 역할을 주려면 별도 Postgres 역할과 접속 방식이 필요해 이 규모에 과하다.
- 그래서 **두 겹**으로 한다. ① 공통 코드 `opsdb.py` 단계에서 에이전트가 부를 수 있는 명령을 허용 목록으로 제한(로그·이력 표는 insert만, 읽기 전용 에이전트는 select만). ② DB 단계에서는 위 트리거로 로그 표의 수정·삭제를 막는다. 서비스 키가 유출돼도 로그가 지워지지 않는 것이 효과다.
- 키 등급: 읽기 전용 키를 따로 만들 수 있으면 일반 구역, 쓰기 키는 중요 구역으로 금고에 담는다(카빗 패스 규칙). 가능한지는 확인할 것.

## 마이그레이션 절차 (한 단계씩, 되돌리기 포함)
1. **M0 사전 점검(읽기만)**: 실제 표·행 수·가져오기 로그를 이 문서와 대조, 무료 한도·일시정지·백업 정책을 공식 문서로 확인. 증거: 대조 결과 5줄. 되돌릴 것 없음.
2. **M1 가져오기 개선**: `ingest_runs` 기록과 `task_events` 비교 기록을 `import_ops_tables.py`에 추가하고, 로그 표 가져오기를 이어 붙이기 방식으로 통일. 증거: 같은 명령 2회 실행에 행 수 동일, `ingest_runs` 2행. 되돌리기: 이전 스크립트 버전으로 복귀(표는 복사본이라 손실 없음).
3. **M2 스키마 v4 적용**: 위 SQL 중 표 4개와 칼럼(트리거는 제외)을 SQL 편집기로 한 번(운영 DB 쓰기는 사장님 몫, 시험 프로젝트라도 승인 1회). 증거: 표 존재 조회. 되돌리기: 새 표만 drop(기존 표는 건드리지 않음).
4. **M3 덧붙이기 전용 잠금**: M1이 2회 이상 자동 실행되어 안정된 뒤에 트리거 적용. 증거: update 시도가 오류로 막힘. 되돌리기: 트리거 drop 한 줄.
5. **M4 로그 정본 전환**: 이중 기록 2주간 행 수 일치 확인 뒤 CSV 폐기, 필요한 곳엔 DB에서 읽기용 md 자동 생성(`opsdb.py to_md`). 증거: 일치율 100% 2주. 되돌리기: CSV 복구(원본은 폐기 전까지 보존).
6. **M5 영상 성과 자동 수집**: 유튜브 공식 API로 `metrics_snapshots`에 덧붙임(주기 작업, 감시 대장 등록, 첫 자동 실행 확인, 사람 빈도 규칙 유지). 증거: 하루 1행 이상 증가.
7. **M6 화면**: 읽기 전용 Metabase 한 장(영상 성과, 자원 사용, 열린 일). 마지막이고 호스팅 위치(로컬 PC 또는 클라우드)는 그때 정한다.

## 성공 판정과 다음 단계
- 판단 기준(10/5 확정): 사람 손 갱신 횟수, 에이전트 읽기·쓰기 가능, 키 값 비저장, 성과→다음 계획 루프, 비용 무료~월 수만원, 팔 수 있는 형태.
- 이번 설계가 더하는 측정: `task_events`로 사람 손 갱신 주당 횟수를 세고, `ingest_runs`로 가져오기 실패율을 센다. 다음 단계 신호는 기존 그대로(주 1회 이하, 에이전트 5개 이상이 2주간 스키마 변경 없이 1,000건, 계획 루프 1회).

## 공정자산 관점
- 스키마(v1~v4), 가져오기 스크립트, `opsdb.py`, 정본 정책 표는 "1인 회사 운영 DB 스타터" 템플릿 후보다. 고객 판매는 외부 사용자 발생 신호 전에는 하지 않는다. 지금은 우리 운영에서 먼저 돌려 증거를 쌓는다.

## 확인할 것 (로컬이 대조)
1. 시험 프로젝트의 실제 표 목록·행 수가 위 "지금 있는 것"과 같은가, `ingest` 로그가 어디에 남는가.
2. Supabase 무료 프로젝트의 비활성 일시정지·백업·용량 한도(공식 문서로 확인, 이 설계는 이를 미확인으로 둠). 한도에 닿는 시점이 유료 전환 신호다.
3. 읽기 전용 키를 따로 발급할 수 있는지, 금고 등급으로 분리 가능한지.
4. `import_ops_tables.py`가 어떤 표를 "비우고 다시 채움"으로 쓰는지 목록(트리거를 걸 수 있는 표 판별용).
5. 사람이 md를 편집하는 표와 에이전트가 쓰는 표의 실제 구분(이 문서의 정본 정책 표 검증).
