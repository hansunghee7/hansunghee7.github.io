# 에이전트 × 헤르메스 위임 연동 설계 (N91)

> 상태: 설계 제안 + 탐의 첫 위임 과업 1회 실행 검증(2026-09-30). 마야·핏·지투의 실제 반복 업무는 아직 본인들에게 확인하지 않았다. 아래 각 에이전트 항목은 역할 노트 머리말만 보고 세운 가설이다.

## 먼저 바로잡을 것: "헤르메스 = 로컬"이 아니다

- **헤르메스 에이전트 런타임**(`scripts/hx.sh ask-pure`): 도구를 쓰는 에이전트 틀이고, 실제 두뇌는 Upstage 호스팅 API(solar-pro4)다. 문장이 우리 장비 밖으로 나간다.
- **Ollama 로컬 모델**(4090, `qwen2.5-coder:14b` 등): 문장이 우리 장비 밖으로 나가지 않는다. 백서 v1.1의 로컬 재현이 이쪽이다.
- 그래서 위임에는 층 표시가 필요하다: `local`(고객·비공개 내용 가능)과 `hosted`(공개 가능한 내용만). 카드마다 층을 못 박는다.

## 제안: 별도 페르소나 문서 없이, 공용 엔진 + 작업 카드

**결론: 헤르메스에게 페르소나 문서는 주지 않는다.** 공용 고속 실행 엔진으로 두고, 페르소나 대신 작업 유형별 "작업 카드"를 둔다.

- 이유 1: 헤르메스의 답은 사람이 아니라 검증기가 판정한다(정책상 기준 해석 판정에 안 쓴다). 성격 문서는 검증에 도움이 안 되고, 유지할 문서만 늘린다.
- 이유 2: 페르소나를 주면 "누구의 말투로 쓰는가"가 답에 섞이고, 우리 실측에서 성패를 가른 것은 출력 형식과 가드였다(백서).
- 이유 3: 호출자가 4명(탐·마야·핏·지투)이라, 에이전트별 페르소나가 아니라 과업별 카드여야 재사용된다. 이미 `.hermes/roles/reviewer.md`가 이 모양의 카드다.
- 이유 4: 상태를 기억하지 않는 엔진이 틀려도 되돌리기 쉽다. 정체성이 생기면 "헤르메스가 그렇게 말했다"는 권위가 생긴다.
- 뒤집을 신호: 같은 카드로 반복 호출하는 사용자가 늘어 카드가 열 개를 넘고 서로 겹치면, 그때 카드 묶음 단위의 역할 문서를 검토한다.

## 연동 구조

호출자 -> `작업 카드` -> 엔진(층 선택) -> 결정적 검증기 -> 결과 봉투(strict JSON) -> 호출자의 최종 판단.

- **작업 카드**: 입력 JSON Schema, 출력 JSON Schema, 엔진 층(local/hosted), 결정적 검증기, 실패 시 처리, 최대 크기. 카드 하나가 파일 하나다.
- **결과 봉투**: 위 출력 스키마(`additionalProperties: false`)로 검사한다. 스키마를 못 지키면 호출자에게 내용을 주지 않고 실패만 알린다.
- **적용은 호출자가 한다**: 엔진은 제안(diff, 초안)만 만든다. 저장소 파일·발행물을 직접 바꾸지 않는다.
- 호출 통로는 CLI 하나(`scripts/ops/` 아래 카드별 스크립트)로 시작하고, 카드가 셋을 넘으면 공통 호출기로 합친다. 지금 합치면 과잉이다.

## 에이전트별 후보 과업(가설, 각자 확인 필요)

- **탐**: ① 린트 수정(검증기 = ruff와 py_compile, 지금 시범 적용) ② 로그 1차 분류(검증기 = 인용한 줄이 원문 로그에 실제로 있는가).
- **핏**: 산출물 검증은 해상도·길이·파일 존재처럼 결정적인 검사가 대부분이라 엔진 없이 스크립트가 낫다. 엔진은 검증이 아니라 "실패 로그 요약" 정도에만 맞다.
- **지투**: 상태 요약·포맷 정리(검증기 = 원문에 있던 숫자·고유명이 그대로 남았는가).
- **마야**: 번역·1차 초안(검증기가 확인할 수 있는 것은 형식, 자리표시자, URL·숫자 보존까지). 품질은 검증기가 못 정하므로 초안 전용이고 판정은 마야가 한다. 미공개 내용은 `local` 층만 쓴다.
- 각 에이전트가 자기 반복 과업 하나를 스스로 고르게 하고, 카드는 그 뒤에 만든다(무엇을 맡길지의 결정은 그 업무의 주인 몫).

## 첫 시범: 탐의 린트 수정 위임

`scripts/ops/delegate_lint.py`가 저장소 `scripts/`의 실제 F401·F811·F841 지적을 로컬 작업자에게 맡긴다.

- 저장소 파일은 건드리지 않고 임시 복사본에서 고친다. 통과한 파일만 diff로 `.hermes/data/delegations/<시각>/`에 저장한다.
- 오케스트레이터가 작업자의 PASS를 믿지 않고 봉투 스키마, ruff 재검사, py_compile, "다른 규칙 오류 증가 없음"을 다시 확인한다.
- 300줄을 넘는 파일은 로컬 모델 컨텍스트(8192토큰) 때문에 제외한다.

**1회 실행 결과(2026-09-30, `--max-files 5`)**: 후보 8개 파일 중 큰 파일 1개 제외, 5개 실행. 4개는 제안 생성(모두 1회차 통과, 미사용 import 한 개 제거), 1개(`sns_read.py`)는 PASS 못 해 거절(미사용 변수 줄까지 얽힌 경우). 총 13.8초. 제안된 diff 4개는 탐이 읽어 검토했고 모두 정확히 미사용 이름 하나만 지운다. 저장소에는 적용하지 않았다.

한계: 표본은 1회, 파일 5개다. 미사용 import를 지울 때 그 모듈의 부작용(import만으로 실행되는 코드)은 검증기가 못 본다. 그래서 적용 전 탐이 diff를 보는 단계를 빼지 않는다.
